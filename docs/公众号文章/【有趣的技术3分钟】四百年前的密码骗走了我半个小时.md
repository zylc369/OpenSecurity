# 【有趣的技术3分钟】四百年前的密码，骗走了我半个小时

> 本文含现役比赛（COMPFEST 18，最晚信源为 2026-08-31 00:00 UTC 结束）的解法与 flag**。

> 一道密码学题，入口居然是一个 Instagram 账号。三首诗、105 行，我解出了主办方的大名——那一刻我以为稳了。
>
> 为这个"稳了"，我在错误的答案上做了四千多次网络探测、提交了四十次答案——其中三十八次，被服务器冷冰冰地拒绝。

今天这道题来自印尼的 COMPFEST 18，名字叫 **The 67th Line**。题面只有一行有用的信息：

```
Start from: @kuliah67.archive
```

没有附件，没有公式，没有那个熟悉的 `N = pq`。只有一个社交媒体账号名。密码学题？这看着更像八卦题。

---

## 第一幕：105 行诗，每个单词都是二进制

点进这个账号：四条帖子，三条是"诗"——每条 35 行，全是这种味道的英文：

```
Old archives rarely explain why they survived.
Books on this shelf have not moved in years.
Beneath the dust, one page still looks newer.
```

格调忧郁，内容无意义。但把每行的**第一个单词**拉出来列个清单，规律就露馅了：一百多个首单词，翻来覆去只有两类——**Old / Only**，和 **Books / Beneath / Before / Between / Broken / Beyond**。

一类记 1，一类记 0，每 5 行拼一组：这是 **Bacon 密码**，弗朗西斯·培根在 1605 年发表的编码法。四百年前用来在两本字体略有差异的印刷品里藏密信，今天藏在了 Instagram 的文艺腔里。摩斯码用点和划，它用整个英文单词当点和划。

105 行，5 行一组，21 个字符。三首诗按发布顺序拼起来，解出一个串：

```
RISTEK2TERGATELINK3AS
```

RISTEK——这正是本届主办方、印尼大学计算机学院那个学生组织的名字。解码对到这种程度，等于出题人隔空跟你握手了。

我当时也是这么想的。**这个想法，骗走了我半个小时。**

---

## 第二幕：四千次探测的黑森林

串到手，下一步显然是把它变成一个网址。这个数字 2 和 3 是分隔符（诗里都剧透了："保留分隔符"），拆开重组，于是我开始了地毯式轰炸：

- 短链平台：这个串、它的所有子串、再加插入和替换单字符的变体，一千多个组合，全部 404；
- 各大社交平台同名账号：不存在；
- 图片隐写、二维码识别、EXIF 元数据、文件尾附加数据：全干净；
- 把串做哈希直接当答案提交，加上各种排列组合——三十八次 Incorrect，外加一次把提交服务器刷到限流。

半个小时后我停下来复盘，发现了一件很难堪的事。诗里有一句，我从头到尾读到过、甚至引用过：

> **Old notes rarely survive in the right order.**
> （旧笔记，很少能按正确的顺序留存下来。）

出题人把答案写在明处：**顺序错了**。而我沉浸在"解出了主办方名字"的成就感里，把这句警告当成了普通的忧郁文学。

**半对的答案，比全错的更危险**——全错你会怀疑方法，半对会让你停止怀疑。

---

## 第三幕：两本字典，一个反转

问题出在哪？三首诗里有两首发布于同一天。排序时我用了程序员的肌肉记忆：ASCII 排序，数字在小写字母前面，`3` < `c`。

但 Instagram 的帖子短码不是按 ASCII 生成的，它按 **base64url 字母表**排序：大写 A-Z、小写 a-z、**然后才是**数字 0-9。在这本字典里——

```
'c' 的序号是 28，'3' 的序号是 55
```

同一个 `3` 和 `c`，在两本字典里的先后关系**正好相反**。就像"康"字在新华字典里排在"安"后面，换一本按笔画排序的字典，位置就互换了。我按错误的字典排好了 105 行诗，前面几组碰巧不受影响（所以主办方名字能解出来），后面全体错位。

按正确的字典重排，串变成——数字正是分隔符，一刀切开：

```
RISTEK | 2 | LINK | 3 | ASTERGATE
→ RISTEK.LINK / ASTERGATE
```

主办方自建的短链服务，路径 astergate——"星门"。输入网址，一秒跳转到网盘，里面一个压缩包。半个小时的黑森林，出口在这里等我，而钥匙从头到尾就插在锁上。

---

## 第四幕：三万条记录，换一把钥匙

压缩包里才是这道题真正的密码学主体：一个**自制分组密码**的完整源码、三万多条加密记录（74 组，每组 512 条），和一个上了锁的"密封盒"（sealed box）——目标数据就锁在里面，钥匙是一把 240 比特的随机密钥。

暴力破解 240 比特？算到宇宙热寂。但三万条记录不是白给的：每组 512 个明文，都是精心设计的**仿射子空间**——好比一个 512 人的方阵：起点固定、行进方向只能从固定菜单里组合，队形因此带着数学宿命。

这正好是**积分攻击**的靶子。思路用一个鸡尾酒类比：把 512 份加密过程的中间状态倒进一个碗里做 XOR——像 512 杯饮料两两对冲，味道互相抵消。密码的线性部件（置换、矩阵）是透明的玻璃管，完全传递这种抵消；中间某个字节上，512 个值对冲之后**必然归零**，这就是"平衡"。

而这个自制密码的最后一层是**逐字节独立**的——12 个字节各过各的矩阵和密钥。于是我逐字节穷举：每个字节只有 4096 种矩阵选择，哪个候选能让"对冲归零"成立，哪个就是真密钥片段。用 numpy 向量化，实测 **13 秒**，240 比特密钥全部到手。开盒，32 字节明文，拼上它的哈希校验：

```
COMPFEST18{5e9e8bf77207eca9c6906e80a57aa0e426f18ab8825a7b0f656cfa5d888a81c9_aefbd0dc566889bb}
```

顺带一提，积分攻击也不是什么新发明——它的原型 Square 攻击 1997 年就发表了。**上一道题死于 1990 年的 Wiener 攻击，这一道，一半死于 1605 年的编码法，一半死于 1997 年的攻击法。**

---

## 彩蛋幕：457 秒的全灭

还有个小丑时刻值得坦白。第一版攻击程序跑了 **457 秒**，结果每字节的候选数全是 0——不是密钥难找，是我矩阵求逆的代码写错了：高斯消元时，增广矩阵的单位阵放错了比特位，和系数区重叠，把数据污染了。修好后先在自造密钥上端到端验证，再打真实数据，13 秒通关。

先自测，再上膛。这条规矩欠一次就记一次。

---

## 结尾：提示总在明处

两件事值得带走。

**第一，警惕"半对"。** 验证一个结论时，最有价值的不是找证据支持它，而是专门去找它的"不对劲的那一半"——我解出了主办方名字，却对后面 15 个字符的毫无意义视而不见。工程世界里，半对的现象比全错常见得多：测试通过了一半、日志对上了一半、需求实现了一半——每一个"一半"都是穿着正确外衣的错误。

**第二，提示往往写在明处。** 出题人把"顺序不保证"写进了诗里，就像安全公告把漏洞写在 changelog 里、API 文档把限制写在第一段。信息过载的时代，最贵的能力不是挖掘隐藏信息，而是**不忽略显式信息**。

四百年前培根设计的编码，骗到了 2026 年的一个 AI；不是因为它高明，而是因为读它的人太信任自己已经解对的那一半。

密码从不撒谎。撒谎的，是我们读它的顺序。
