# Qwen3.8 本地部署：能跑、好用、划算，是三件事

> 2026 年，以 Qwen3.8 为代表的开源模型一轮轮刷屏：旗舰级模型开放权重，"35B 的知识、3B 的算力成本"成为现实，"一台 Mac 能跑 27B"成了社区热词。
>
> 很多人开始盘算：是不是该把工作流搬回本地？
>
> 我们把这件事从头到尾算了一遍——硬件、速度、成本，以及最容易被忽略的一环：人。
>
> 先说结论：**能跑、好用、划算，是三件不同的事。**

---

## 一、总：先把结论摆出来

关于 Qwen3.8 与本地部署，我们的调研结论可以浓缩成三句话。

**第一，技术上确实能跑，但在绝大多数设备上，实际效果比想象中的差。** 消费级设备确实能跑 27B 级的模型，但速度、上下文、内存都有硬约束；"跑得起来"和"用得顺手"之间，隔着一条工程鸿沟。

**第二，经济上，本地在绝大多数个人场景打不过 API。** 明面的账：只算硬件和电费，买硬件的钱就够用 API 十几年；隐形的账：搭建、调参、维护这套环境要持续投入时间——一次性 20-80 小时，之后每月还要维护（第四章细列），占用你的休息时间但没有收益。两笔账加起来，差距只会更大。

**第三，真正的瓶颈不是算力，是人的时间。** 设备买回来只有两类用法，都不成立：做简单的事——大部分时间闲置，买它等于浪费；做复杂的事——AI 产出必须经人复核才能交付（现在的 AI 还撑不起无人看管的商业项目），而复核期间 AI 只能停下等待。一个人一天能高强度陪跑 AI 的时长有硬上限（打满 6 小时已属高强度，有正职的人在业余时间更少），设备利用率注定被人的时间锁死。

所以，本地部署的合理动机只有两类：**它给了你 API 给不了的东西**（数据主权、不受审查、离线可用），或者**你有持续打满它的负载**。

至于三个流行的理由——"省钱""性能更好""随时能用"——下面逐层说明它们为什么站不住。

---

## 二、物理账：能跑，但在绝大多数设备上，实际效果比想象中的差

"能跑"和"能干活"是两回事。一台设备能不能真的拿来干活，只看两个问题：

1. **上下文装得下吗**——干活要用的资料（代码、工具结果、提示词）塞得进去吗？
2. **一份活要等多久**——以它的速度，干完一份真实的活要花多少时间？

先划一条资格线：权重必须整体装进内存。16GB 的普通办公本连 27B 的权重都放不下，32GB 勉强，所谓"一台 Mac 能跑 27B"，说的是 48GB 以上的配置。下面就用一台 48GB 的 M4 Pro MacBook 做样本，把两个问题各算一遍。

### 2.1 第一问：上下文装得下真实的活吗？

先看这台设备能开多大上下文——三笔开销挤同一块内存：

- **系统与软件**：macOS 加日常软件（Docker、浏览器、编辑器）常驻 15-27GB；
- **模型权重**：27B 的 4-bit 量化约 16-18GB，必须整体驻留（CPU 卸载会慢到无法交互）；
- **剩下的才是上下文**：工具默认给到 32K；手动开 64K，内存余量已经紧张。标称的 262K 只是"能加载"的上限，在这台设备做不到。

再看真实的活要多少。以"用 OpenCode 写代码"为例：

- **提示词与工具底座**：OpenCode 空项目裸装约 7 千 token（系统规则约 2 千 + 10 个内置工具定义约 5 千）；配上一份 72KB 的项目说明文件（AGENTS.md 这类，约 +2 万）和 5 个 MCP 服务器（约 +5-7 千），第一轮请求就从 3 万 token 起；重度配置（十几个 MCP、近 200 个工具）实测能到 9 万+——你还没开始打字；
- **代码与工具结果**：读一个 200 行的源文件约 1 万 token，跑一轮测试、看一次报错又是几千到几万，一轮典型的开发动作就是 2 万 token 上下；
- **多轮累积**：agent 每走一步，整段历史都要再带上。一个"8 步修改 + 3 次测试修复"的常规任务，第 10 轮时单轮输入冲到 **9.5 万 token**，全程累计输入接近 **60 万**。

对比：**这类任务要 10 万 token 量级的上下文，而 48GB 设备能稳定开的只有 3-6 万。** 缺口只有两个结局——被"自动压缩"切碎后反复忘事（"刚才改的文件怎么又错了"），或者干脆干不了。标称 262K 的模型，在这台设备上装得下的只有演示级的活。

### 2.2 第二问：一份活要等多久？

先分清两笔账：上一节算的是"读"——每轮要带上的上下文（输入）；这一节算的是"写"——模型要生成的内容（输出）。这类任务读得远比写得多，但本地最慢的一环恰恰是"写"。

先看速度本身（同机实测）：

- 27B 稠密：**14-26 token/s**；
- 35B MoE：**60-85 token/s**——总参数决定内存（35B 全驻留），激活参数决定速度（每个 token 只叫醒 3B），所以"更大"反而更快；
- 这是物理天花板，不是配置问题：M4 Pro 的内存带宽 273 GB/s，17GB 的 4-bit 权重每出一个 token 都要整体过一遍——理论上限约 16 token/s，实测基本贴着它。指望软件更新提速，空间很小。

把"一份活"换算成 token，做除法：

| 一份活的模型输出（含思考 token） | 27B（14-26 token/s） | 35B MoE（60-85 token/s） |
| --- | --- | --- |
| 一次对话级回答（1-2 千 token） | 1-2 分钟 | 半分钟 |
| 一次小编码任务（约 1 万 token） | 6-12 分钟 | 2-3 分钟 |
| 一次中等重构（3-5 万 token） | 20-60 分钟 | 6-14 分钟 |

这还只是"纯出字"的时间，另有三笔附加：

- **每轮先重读**：第一个字出来前，输入要被读一遍——4K 新内容等约半分钟，64K 等约三分钟（无缓存命中时）；
- **越长越慢**：有实测从短上下文的 63 token/s 滑到 3 万上下文时的 11 token/s——真实长任务里，上表还要往下打折；
- **压缩重启**：上下文一爆，压缩本身耗时间，压完进度还受影响。

作为对照：公开对照实验里，云端 agent 完成一个常规任务的中位耗时是 **3-6 分钟**。同一类活，本地要按几十分钟来等，重一点就按小时算——而这些时间，你要真的坐在机器旁边等。

**两问合起来：能跑是真的，但离"能干活"还隔着两道硬墙——上下文装不下、速度等不起。**

## 三、经济账：公式里藏着一个致命分母

### 3.1 两条成本公式

- **本地**：成本 = 硬件摊销 + 电费 + 运维时间 + 学习时间；
- **API**：成本 = 用量 × 单价（+ 可选订阅）。

本地是固定成本（买不买都花了），API 是变动成本（不用不付钱）。后面所有结论，都从这个差别里长出来。

公式里的"运维时间 + 学习时间"不是零头：第四章已细列这些时间（一次性 20-80 小时，之后每月还要维护）。这笔时间折不折算成钱都真实存在，而且不小；本节的回本测算先只摆硬件与电费的"明面账"——把折腾时间加进来，只会更差。

### 3.2 API 的价格，便宜得超出直觉

以 2026 年 8 月调价后的 DeepSeek 为例（工作日白天为高峰价，其余时段为半价；调价后涨幅不小，但绝对价格仍然很低）：

- V4-Flash：输入（缓存未命中）约 ¥1.5/百万 token，输出 ¥4.5；缓存命中的输入低至 ¥0.05；
- V4-Pro：输入约 ¥4.5，输出 ¥13.5。

一个重度个人用户的月账单（约 9000 万输入 + 3000 万输出）：**约 ¥166-270/月**。走订阅的话：GLM Coding Plan 年付约 $12.6/月、Qwen Token Plan ¥39/月起、Claude Pro $20/月。

### 3.3 硬件的价格，贵得超出直觉

- 128GB 统一内存的桌面机型：约 $4,800 起（笔记本形态约 $7,000）；
- 256GB 档：$9,499 起；
- 想本地跑 70B 级、大上下文：轻松过 $10,000。

注意这是**追加投入**——为跑本地模型专门购置的硬件。电费反倒是小头（消费级设备约每百万 token $0.1 量级）；真正的分母是利用率。

### 3.4 回本测算：十几年起步

多家独立测算的结论一致：

- 一台 $6,999 的 128GB MacBook Pro，对比 DeepSeek V4-Flash 空闲价，**回本需要约 190 个月——16 年**；
- 一台三年期的二手显卡主机（约 $2,700），其总成本能买 **130 亿+ token** 的 API 用量——超过这张卡三年满负荷能产出的总量；
- 原文结论：**"对便宜模型，自部署在成本上永远不回本。"**

### 3.5 最致命的分母：利用率

这是所有测算里最多人忽略、也最能改变结论的变量。

公式：**每百万 token 成本 = 总成本 ÷ 实际产出的 token**。设备买回来，你不是 24 小时都在用它。

两层损耗相乘：

- **占空比**：设备实际有推理在跑的时间。对个人使用，可能是每天 6 小时、每周 5 天——30/168 ≈ **18%**；
- **饱和度**：单人交互根本喂不满算力，可能只有峰值吞吐的 20%。

相乘：**有效利用率 ≈ 3.6%**。

后果：同一台机器，满利用率下每百万 token 成本 $0.56；**3.6% 利用率下变成 $15.65**——比大多数云端模型还贵。

还有一个"回本利用率"的算法（以单 GPU 节点为例）：想跑赢 $3/百万 token 的中档 API，需要全年维持约 **19%** 的峰值吞吐利用率；想跑赢 $0.60/百万 token 的廉价端点，需要 **94%**——除批处理队列外，物理上不可达。

实践结论：**如果实测利用率低于 40%，不要为"省钱"买机器——没有省钱这回事。**

### 3.6 时间站在 API 一边

最后一刀：**API 价格在持续下降**。行业测算显示，达到同等智能水平的成本每年下降 9 倍到 900 倍。你按今天的价格算回本，一年后对手便宜一个数量级——回本所需的利用率随之飙升。

而硬件是三年锁定的固定成本。**用固定成本对抗一条持续下降的价格曲线**，是这场博弈里最不利的位置。

## 四、人的账：真正的瓶颈是人的时间

前两本账算的是设备与钱，这一本算的是人——它比钱更残酷。

设备买回来只有两类用法，在"人的时间"这道墙前都不成立：

- **拿它做简单的事**（批量提取、格式转换、顺手写的小工具）：你自己几下就做完了，或者 API 更快更省心——设备大部分时间闲置，买它等于浪费；
- **拿它做复杂的事**（需要交付质量的项目）：AI 产出必须经人复核才能交付（现在的 AI 还撑不起无人看管的商业项目），而复核期间 AI 只能停下等待。

而且别忘了：搭建、调参、维护这套系统，消耗的也是同一份时间。**设备的利用率上限，不取决于它多快多强，取决于你能陪它多久。**下面的数据，就是把这句话展开。

### 4.1 复核才是瓶颈

2026 年全年的行业数据都指向同一个事实：AI 没有消除瓶颈，只是把瓶颈从"写"搬到了"审"。

- 每 **60 分钟** AI 产出，人工需要约 **34 分钟**复核（多项工程团队调研的中位数），安全相关的变更更高；
- AI 生成的 PR 等待首个复核者的时间，是人工 PR 的 **4.6-5.25 倍**；
- 30 天内合并率：AI PR **32.7%**，人工 PR **84.4%**；
- 资深开发者在真实项目上用 AI 后**慢了 19%**——但他们自我感觉快了 20%；
- 通过 QA 的 AI 代码，仍有 **43%** 需要生产环境人工调试；
- 26% 的开发者（以及同样比例的技术负责人）把"复核与验证 AI 产出"列为头号约束——**排在成本前面**。

对个人用户同样成立：AI 生成得越快，待复核的队列越长。**你坐下来复核的时候，AI 是闲置的。**

### 4.2 无人看管 = 无法交付

"让 AI 跑一晚上出成果"在演示里好看，在交付里不成立。

行业数据：86% 的组织报告资深工程师返工时间增加，78% 报告事故增加，89% 的组织至少经历过一次 AI 相关的生产事故。商业交付的质量门槛，目前仍然要求人在回路——**人在回路，AI 的利用率上限就被人的时间锁死**。

### 4.3 使用强度的现实上限

即使排除万难，一个人一天能高强度使用 AI 的时长也有限：

- 满负荷 6 小时已是高强度脑力劳动；
- 有正职工作的人，业余时间再打一折；
- 周末、假期，设备闲置。

叠加起来：**个人用户的长期设备利用率，大概率落在个位数百分比**——低于上述任何回本阈值。

### 4.4 它要人养：维护是另一笔时间税

本地部署不是"装上就完"，而是"养一套系统"——装好只是第一天，之后的每一天都需要人：

- **版本追不完**：引擎和模型都在月更，升级要重新验证，有时升级本身就把原来的配置带崩；
- **故障不会自己好**：OOM、静默失败、睡眠唤醒后失联、和 Docker/浏览器抢内存——出了事都得人来查；
- **换代换不换**：新模型一波接一波，换了要重测重调，不换就眼看着落后。

投入有明确的时间口径：**一次性搭建 20-80 小时，之后每月数小时到十几小时**——这笔时间折不折算成钱都真实存在，占用你的休息时间但没有收益。

关键是记住：**维护花的时间和复核花的时间，抢的是同一份人的时间。** 你用来排障、升级、重测的每一个晚上，都是从"陪 AI 干活"的预算里扣出来的——而这份投入换来的只是"它能继续用"，不是"它能替你交付"。

### 4.5 "随时可用"的隐藏成本

还会碰到这个悖论：

- 本地模型跑在主力笔记本上——合上盖子就断线；
- 想"随时可用"，就要一台常驻设备加公网访问架构（内网穿透、VPN、反向代理）——**又一笔硬件和运维成本**；
- 而 API 天然随时可用，这项便利已经包含在单价里。

"本地部署更省心"，在这一点上恰恰相反。

## 五、边界：什么时候本地是对的

写到这里，本地部署似乎一无是处。但它有几类 API 无法替代的场景——注意，这些场景的价值都不建立在"省钱"上：

**1. 数据不能出门。** 合规要求、客户协议、隐私数据——当"数据不出内网"是硬需求，这是控制权采购，不是经济决策。

**2. 不受审查的需求。** 安全研究是典型场景：恶意代码分析、C2 复现、漏洞利用验证，云端 API 会拒答或过滤。但要注意：去审查模型的长上下文表现与可靠性参差，适合研究，不适合无人看管交付。

**3. 离线/隔离环境。** 没有网络的地方（气隙网络、现场作业），本地是唯一选项。

**4. 批量负载。** 这是唯一能真正"吃满"利用率的负载类型：夜间批处理、索引重建、嵌入计算、大规模分类。不需要人工逐条复核的活，才配得上"拥有算力"。

**5. 控制权。** 模型不被下架、不改价、不变行为——对版本稳定性有硬要求的场景，这是真实价值。

一句话：**本地部署买的是控制权，不是便宜。** 如果控制权确有所需，价格是另一个话题；如果只是"想省钱"，前面的账已经给出了答案。

## 六、总：一份决策清单

全文可以浓缩成三个问题：

**问题一：你的数据能不能出门？**
→ 不能：本地是刚需，参考第五节。
→ 能：进入下一题。

**问题二：你有没有能持续打满设备的负载？**
→ 有（且不需要逐条人工复核）：可以认真评估本地。
→ 没有（个人、业余、间断使用）：不要为省钱买硬件。

**问题三：你的瓶颈是算力，还是人的时间？**
→ 算力：继续评估本地。
→ 人的时间（大多数人的真实情况）：**买质量，不买产能**——API 让你只为用得上、用得好的部分付费，而且始终用得上最强的模型。

给三类人的一句话建议：

- **个人 / 业余开发者**：用 API 和订阅覆盖需求；现有设备可以跑本地模型做实验与隐私任务，但别为它专门买硬件。
- **工作室**：先实测共享利用率（多人共享会聚合利用率，可能过线）；确有合规或安全研究需求时，按"专项能力"立项，别按"省钱"立项。
- **组织**：合规和交付质量先于成本；真要做，采购前必须用真实流量测出"回本利用率"。

回到标题：**能跑、好用、划算，是三件事。**

这个时代真正的福利是：你花几块钱，就能用上别人花几万块硬件也追不上的模型。**把预算花在能力上，把硬件留给控制权。**

> 省钱的正确方式，是别为用不满的算力买单。
