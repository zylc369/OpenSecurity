# 02 Cookie 与会话

> **本章一句话**：Cookie 是浏览器替某个网站保存的一小段数据，之后**自动**随发往该网站的请求一起发出；"会话（Session）"则是把这些数据放进服务器端保管、Cookie 里只放一个查表编号的做法。
>
> 这一章解释"登录状态是怎么被自动带上的"——它是全书中所有攻击的通行证问题。

## 2.1 Cookie 是什么

生活类比：去游乐园时工作人员给你戴的手环。之后每个游乐项目（每次请求）你什么都不用说，工作人员看手环（Cookie）就知道"你是已购票的游客"。

技术定义：**服务器让浏览器保存的一小段键值数据**（名、值、若干属性）。之后浏览器**自动**在发往该网站的请求里附带它——不需要任何页面代码参与。

三个关键性质：

| 性质 | 含义 |
|------|------|
| 按网站隔离存储 | 每个网站（更准确地说是每个域）有自己的一格；`challenge.com` 的 Cookie 只有发往 `challenge.com` 的请求会带，`evil.com` 的请求带不上 |
| 自动携带 | 满足条件就带，页面代码不需要（也无法直接控制） |
| 页面与凭证分离 | Cookie 住**浏览器**里，不属于任何页面；页面被关掉它还在，换一个页面照样带 |

## 2.2 两个方向的动作：Set-Cookie 与 Cookie

| 动作 | 头名 | 方向 | 谁写 | 例子 |
|------|------|------|------|------|
| **下发**（服务器→浏览器） | `Set-Cookie` | 响应头 | 服务器 | `Set-Cookie: sid=s%3Aabc; Path=/; HttpOnly; SameSite=Lax` |
| **携带**（浏览器→服务器） | `Cookie` | 请求头 | 浏览器自动 | `Cookie: sid=s%3Aabc; view=8d7b1188` |

一次完整的登录接力（本例机器人的登录）：

```text
① 机器人浏览器带口令请求登录接口
   GET /reports/session   （请求头 X-Bot-Token: <机器人口令>）

② 服务器核对口令，把这份会话标记为管理员，并把会话 ID 下发出来
   HTTP/1.1 200 OK
   Set-Cookie: sid=<会话ID>; Path=/; HttpOnly; SameSite=Lax

③ 从这条响应之后，机器人浏览器发往该网站的**每个**请求都自动多出一行
   Cookie: sid=<会话ID>
   服务器读到它，查会话存储，认出"管理员来了"
```

注意时序：**Cookie 是"第一次响应"种下去的**，第一次请求里不会有它；从第二次请求起才自动携带。

## 2.3 Cookie 的属性

一条 Cookie 可以带多个属性，每个都是一种"携带规则"：

| 属性 | 作用 | 例子 |
|------|------|------|
| `Domain` | 允许哪些域携带（默认=设置它的主机本身） | `Domain=challenge.com` |
| `Path` | 允许哪些路径携带 | `Path=/reports/check` |
| `Expires` / `Max-Age` | 何时过期；都不写=**会话 Cookie**，关浏览器即清 | `Max-Age=3600` |
| `HttpOnly` | 网页 JS 读不到它（`document.cookie` 里看不到），只能随请求自动发送 | 防脚本偷凭证 |
| `Secure` | 只在 HTTPS 请求上携带 | 防明文网络截获 |
| `SameSite` | 跨站请求带不带（下一章专题） | `SameSite=Lax` |

一条重要的分工：**服务器只能"声明"这些属性；每个请求实际带哪些 Cookie，由浏览器按规则决定**。安全分析里两者的行为都要会推。

## 2.4 Path 实战：一条只随特定路径发送的 Cookie

本例审查页首访时，服务器种下一条 `view` Cookie：

```js
res.cookie("view", id, { httpOnly: true, sameSite: "lax", path: "/reports/check" });
// 实际响应头：Set-Cookie: view=8d7b1188...; Path=/reports/check; HttpOnly; SameSite=Lax
```

它限定了 `Path=/reports/check`，于是：

```text
GET /reports/check?rid=...   → 路径与 Path 匹配 → 附带 Cookie: view=8d7b1188...
GET /api/flag                → 路径不匹配     → 不附带 view
```

`Path` 只影响"带不带"，不影响"存不存"——Cookie 只有一条（存在浏览器的 cookie 存储里），只是携带时会被路径过滤。它的用途（为什么需要让"下一次访问审查页"带上一个标记）在 10 章（HTTP 缓存）里揭晓。

## 2.5 会话（Session）：把身份放服务器端

**动机**：如果把身份数据（用户名、权限）直接写进 Cookie，等于把身份证交给浏览器保管，容易被伪造或篡改。会话模式改为：

- **服务器端**存一份数据（本例：内存里的一张键值表，键=随机的**会话 ID**，值=会话数据，如 `{ name: "reviewer", admin: true }`）；
- **浏览器端**只拿会话 ID，存在 Cookie 里（本例 Cookie 名叫 `sid`）。

流程（机器人换取管理员身份）：

```js
app.get("/reports/session", (req, res) => {
  if (req.get("x-bot-token") === BOT_TOKEN) {  // 验口令
    req.session.name = "reviewer";
    req.session.admin = true;                  // 把这份会话标记为管理员
  }
  ...
});
```

服务器用的是 `express-session` 中间件，几个必须知道的行为：

| 行为 | 说明 |
|------|------|
| 无 Cookie 时新建会话 | 生成新会话 ID，用 `Set-Cookie: sid=...` 下发 |
| 有 Cookie 时复用 | 用请求带来的会话 ID 找回那份数据，挂到 `req.session` 上 |
| 修改何时落盘 | 请求处理中对 `req.session` 的修改，在**响应发送完成时**写回存储 |
| 存储位置 | 本例是进程内存（MemoryStore）：服务器重启数据即消失；条目过期也会失效 |
| 防篡改 | 会话 ID 由 `SESSION_SECRET` 签名，服务器收到后验签，伪造的 ID 不予受理 |

一个实用的理解：**服务器判权限的单位是"请求"，不是"页面"**。同一个 `/review` 地址，带管理员会话的请求得到工作台页面，不带的得到 403——服务器只看请求里的凭证，不关心这个请求是哪个页面、用什么方式发出的。

## 2.6 攻击者视角：为什么必须"借机器人的浏览器"

把本章结论合并成三条，这是全书攻击链的立足点：

| 障碍 | 原因 |
|------|------|
| **读不到** | `HttpOnly` 让页面脚本读不到 `sid`；跨域页面对别的域的 Cookie 更是完全隔离 |
| **带不上** | 攻击者自己页面里 `fetch("challenge.com/api/flag")` 属于跨站请求，Cookie 不随行（下一章 SameSite） |
| **伪造不了** | 会话 ID 是随机值 + 签名；机器人口令（`X-Bot-Token`）是部署时配置、服务器与机器人共享的独立秘密 |

结论：管理员身份**只存在于机器人的浏览器里**。攻击者唯一可行的路，是让**机器人的浏览器**（而不是自己的）去发出那些关键请求——这就是攻击链后面所有"弹窗、导航、回退"技巧存在的理由。

## 2.7 易混点

| 混淆 | 正解 |
|------|------|
| Cookie 存储 vs HTTP 缓存里的"Cookie 记录" | 前者是凭证仓库（决定"带什么"）；后者是缓存复用条件的留底（10 章），两者本不相关，靠 `Vary: Cookie` 才建立联系 |
| `Set-Cookie` 每次响应都有？ | 只在需要种/更新 Cookie 时出现；本例 `view` Cookie 只在首访那一次响应里下发 |
| 会话 Cookie 关掉浏览器就没？ | 不写 `Expires`/`Max-Age` 的才是；写了的会在磁盘上留存到过期 |
| "浏览器带的 Cookie 是页面代码设置的" | 页面代码只能"请求服务器种 Cookie"，实际存储与携带全由浏览器机械执行 |
