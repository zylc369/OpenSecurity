# 01 Web 基础与 HTTP

> **本章一句话**：浏览器与网站之间的一切交互，都是"请求（要什么）→ 响应（给什么）"；安全分析中 90% 的线索藏在消息头里。
>
> 本章是全书地基，后面的每一章（Cookie、缓存、请求头检查……）都建立在这些概念上。

## 1.1 请求-响应模型

网页访问的本质是浏览器（客户端）和网站（服务器）之间的一次对话：

- 浏览器发出一条**请求**（request）："我要这个地址的内容"；
- 服务器回一条**响应**（response）："给你，这是内容"，或"不给你，原因如下"。

每条 HTTP 消息都分两部分：

| 部分 | 是什么 | 例子 |
|------|--------|------|
| **头**（header） | 一行行的"说明标签"：谁发的、要什么格式、带没带凭证、能不能缓存…… | `Content-Type: text/html` |
| **体**（body） | 真正的内容：网页 HTML、JSON 数据、表单数据…… | `<!doctype html>...` |

请求有请求头 + 请求体；响应有响应头 + 响应体。安全分析中要养成习惯：**先逐行读头，再看体**。

## 1.2 URL 的结构

```text
http://challenge.com:3000/reports/check?rid=8d7b1188&state=ff7a3620
└┬─┘   └─────┬──────┘└┬┘└─────┬─────┘ └──────────┬──────────────┘
协议   主机（域名）   端口     路径            查询串（参数）
```

- **协议**：`http://`（明文）或 `https://`（加密）。
- **主机 + 端口**：定位"哪台服务器、哪个门"。省略端口时用协议默认值（http 80 / https 443）。
- **路径**：定位服务器上的哪个功能。如 `/reports/check`、`/api/flag`。
- **查询串**：`?` 之后、用 `&` 分隔的键值对，如 `?rid=xxx&state=yyy`。也叫"URL 参数"。

同一个功能可能同时用两种方式收参数，读源码时要分清：

| 方式 | 长相 | 服务端读取 | 浏览器页面里读取 |
|------|------|-----------|----------------|
| 路径参数 | `/note/c350151803f0f8f3d507` | `req.params.id` | 从 `location.pathname` 解析 |
| 查询参数 | `/reports/check?rid=abc&state=def` | `req.query.rid` | `new URLSearchParams(location.search).get("rid")` |

**URL 编码**：URL 里只允许一部分字符，其余要写成 `%XX` 形式（空格 `%20`、`{` `%7B`、`/` `%2F`）。当一段数据要"拼进 URL"时（比如把脚本地址放进 `?u=` 参数）必须先编码，否则会和 URL 语法打架。JavaScript 里的 `encodeURIComponent()` 就是做这个的。

> **一个值得记住的历史攻击面**：同一段 URL 在不同解析器里可能被理解成不同东西（"解析差异攻击"）。现代浏览器和 Node.js 都遵循同一套 WHATWG URL 标准，差异空间已经很小；但遇到老旧组件或自定义解析代码时，它仍是排查方向之一。

## 1.3 请求方法：GET 与 POST

方法声明"这次请求想干什么"：

| 方法 | 用途 | 参数放哪 | 例子 |
|------|------|---------|------|
| `GET` | 获取内容（打开页面、读接口） | 拼在 URL 查询串里 | `GET /reports/check?rid=...` |
| `POST` | 提交数据（创建、修改） | 放在请求体里 | `POST /create`（表单字段在体内） |

读源码时常见的写法：`app.get("/note/:id", ...)`、`app.post("/complete", ...)`——路径 + 方法共同确定一个"端点"（endpoint，服务器对外的功能入口）。

两个对安全很重要的差别：

- **GET 的参数在 URL 里**，会进入浏览器历史、服务器日志、`Referer` 头；**POST 的参数在请求体里**，但这些都不构成保密性。
- 浏览器对 GET 与 POST 有**不同的自动行为**：跨站请求时 Cookie 带不带、缓存怎么处理，都可能因方法而不同（见 03 章 SameSite 行为表）。

## 1.4 状态码

响应第一行里的三位数字是状态码，一句话告诉你"结果如何"：

| 码 | 含义 | 本例场景中出现处 |
|----|------|----------------|
| `200` | 成功 | 正常打开页面 |
| `302` | 临时重定向：响应头带 `Location`，浏览器自动跳到新地址 | `POST /create` 成功后跳转预览页 |
| `304` | 内容没变（配合缓存，无响应体） | 条件请求（10 章） |
| `400` | 请求本身不合法（缺字段等） | 创建笔记缺 title/body |
| `403` | 服务器认得你，但不放行（权限/条件不满足） | 非管理员访问 `/api/flag` |
| `404` | 找不到（路径不存在、编号对不上） | 无效笔记编号；rid 不匹配 |
| `429` | 请求太多（限流） | 上一轮审查没结束时又提交 |

**403 与 404 的分工技巧**（读源码/调试很实用）：同一个接口对"不存在"和"没权限"返回不同的码，可以帮你判断"我是被认出来了还是压根没找对地方"。比如审查页源码里：rid 不匹配 → `404`；rid 对了但某项检查不过 → `403`。

## 1.5 请求头与响应头

**头**是消息的"备注栏"，一行一个 `名字: 值`。请求头由浏览器（或客户端程序）写；响应头由服务器写。头**不区分大小写**（`X-Bot-Token` 与 `x-bot-token` 是同一个头）。

看一个真实响应（`POST /create` 成功后）：

```text
HTTP/1.1 302 Found
Cross-Origin-Opener-Policy: same-origin        ← 一批安全头（09 章逐个讲）
X-Frame-Options: SAMEORIGIN
Location: /note/c350151803f0f8f3d507           ← 跳转目标
Vary: Accept
Content-Type: text/plain; charset=utf-8        ← 体是什么格式
Content-Length: 48

Found. Redirecting to /note/c350151803f0f8f3d507
```

**读响应时先分清"框架默认"和"应用自定义"**，能省很多翻源码的时间：

- `Cross-Origin-Opener-Policy`、`X-Frame-Options` 等十来个安全头，来自 `helmet` 库（一个给 Express 应用自动加安全头的中间件）的默认配置——应用代码其实只写了一行 `app.use(helmet(...))`；
- 响应体里那句 `Found. Redirecting to ...` 也不是应用代码写的，是 Express 的 `res.redirect()` 默认生成的文案（并且会按请求的 `Accept` 头返回不同版本——这就是响应里 `Vary: Accept` 的来源，内容协商见 10 章）；
- 真正属于应用自己逻辑的，只有 `Location` 这类少数头。

```js
// 应用代码：res.redirect() 一行，框架自动配上 302 + Location + 文案
res.redirect(`/note/${encodeURIComponent(id)}`);
```

## 1.6 表单提交

网页上的 `<form>` 是"把用户填的数据装进请求体发出去"的标准方式。表单字段名对应对服务端收到的键名：

```html
<form action="/create" method="post">
  <input name="title"><textarea name="html"></textarea>
</form>
```

默认编码格式是 `application/x-www-form-urlencoded`（长的像查询串：`title=x&html=y`）。用命令行模拟同样一次提交：

```bash
curl -si -X POST http://localhost:3000/create \
  --data-urlencode "title=manual" \
  --data-urlencode "html=<img src=q onerror='...'>"
```

另外两种常见体格式：

- `application/json`（`/complete` 接口用它提交 `{id, state}`）；
- `multipart/form-data`（带文件上传时用）。

## 1.7 HTML 与 JavaScript 速览

读懂 payload 需要的最小 HTML/JS 知识：

- **标签与属性**：`<img src="q">` 里 `img` 是标签、`src` 是属性。属性值可以用双引号、单引号或不加引号包裹——写 payload 时常省掉引号来省字符。
- **内联事件处理器**：`onclick=`、`onerror=` 这类写在标签里的属性，内容是 JavaScript，**事件触发时执行**。图片加载失败会触发 `onerror`，这是 XSS payload 最经典的载体之一（见 08 章）。
- **脚本的两种写法**：页面里内联的 `<script>代码</script>`，和引用外部文件的 `<script src="地址">`（浏览器下载目标当 JS 执行）。**给 `src` 的地址返回什么后缀不重要，内容会被整份当 JavaScript 解析**。
- **一个坑**：内联脚本里出现完整的 `</script>` 字样会被 HTML 解析器当场当作脚本结束（后面内容变成普通文本）。需要时可以用字符串拼接写：`'</scr' + 'ipt>'`。
- **`<pre>` 不阻止解析**：`<pre>` 只影响显示格式（保留空格、等宽字体），里面的标签照常被解析执行。让标签失效的是**转义**（把 `<` 变成 `&lt;`），不是 `<pre>`（见 08 章）。

## 1.8 本章易混点

| 混淆 | 正解 |
|------|------|
| "POST 参数看不见 = 安全" | 参数都不构成保密，POST 只是不落在 URL/历史里 |
| "403 = 没登录，401 = 没权限" | 示例系统里 403 承担"权限/条件不满足"；401 未认证在简单系统里常不用 |
| "响应里没见过的头就是应用代码写的" | 先想框架（Express/helmet）默认，再查应用代码 |
| "对象存储里的 `document`" | 同一文档里可能既有"网页文档对象"又有"业务字段名叫 document"，读代码时按上下文区分（02/04 章会再遇到） |
