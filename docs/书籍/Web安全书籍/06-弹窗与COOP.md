# 06 弹窗与 COOP

> **本章一句话**：弹窗（`window.open`）会在两个窗口之间建立一条"遥控通道"；`COOP` 响应头决定这条通道在加载目标页面时被保留还是被**折断**——折断后，你的代码握着对方窗口的"死引用"，一切操作**不报错、也不生效**。

## 6.1 window.open 与 opener：遥控通道

```javascript
// A 页面（开窗人）：
const w = window.open("https://b.com/page");   // 打开弹窗 B，返回值 w 是 B 的"遥控器"
// B 页面（弹窗）：
window.opener;   // 反过来找到 A：我的开窗人是谁
```

双方自动获得对方的引用：**开窗人拿弹窗**（返回值 `w`），**弹窗拿开窗人**（`window.opener`）。有了引用，双方就能互相发消息、互相导航。

引用"能干什么"受**同源策略第三层**管（4.2）：同源时几乎无所不能（读对方 DOM、调对方函数）；跨源时只剩一份白名单（07 章详列）——能发消息、能导航对方、**不能读对方内容**。

两个术语先定义：

- **opener（开窗人）**：谁调 `window.open` 开的我，谁就是我的 opener。
- 注意用词：本章说的"弹窗"专指 `window.open()` 打开的新窗口，**不是** `alert()` 那种只能显示文字、点确定关掉的原生提示框——后者加载不了页面，两回事。

## 6.2 浏览上下文组（BCG）

浏览器把"互相认识的窗口"分成小组（Browsing Context Group），**同一个小组里的窗口才能互相引用、按名字互相找到**；跨组的引用全部作废。

分组怎么定：由**开窗关系**决定——A 开的弹窗 B 默认和 A 同组。iframe 不单独成立分组：它嵌在哪个标签页里，就跟着那个标签页的组走。

`COOP` 就是"**分组的裁决者**"：它让某些窗口在加载的瞬间被"踢出"开窗人的组。

## 6.3 COOP 的档位与判定矩阵

`COOP`（Cross-Origin-Opener-Policy，跨源开窗人策略）是服务器写在**响应头**里的一条规矩：

| 档位 | 含义 |
|------|------|
| `unsafe-none` | 默认档（不设 COOP 就是它）：不设防 |
| `same-origin` | 最严档：只接受"同源且同档"的开窗关系 |
| `same-origin-allow-popups` | 放宽档：别的照严，唯独"我亲手开的普通弹窗"可以留下（跨站也留，OAuth/支付场景靠它） |

> 另有第四个值 `noopener-allow-popups`（Chrome 88+）：本页面开出的弹窗**不建立 opener 关系**（隔离更彻底，适合"需要开窗但不想要 opener 通道"的场景）。本书矩阵以三档主线值为主。

分组的判定**不只看弹窗 B 的档位，还看开窗人 A 的档位**，两边凑在一起才决定"断还是不断"。设 A 是开窗人、B 是它 `window.open` 出来的弹窗，"普通页"= 没设 COOP 的 `unsafe-none` 页面：

| A 开的弹窗 B 是…… | A 带 `same-origin` 档 | A 带 `allow-popups` 档 |
|---|---|---|
| 普通页（没设 COOP，不管同源跨站） | ❌ 断 | ✅ **同组（跨站都留）** ← 两档唯一的实质区别 |
| 同源 + 档位字面相同（和 A 一致） | ✅ 同组 | ✅ 同组 |
| 同源 + 档位不同（一个 same-origin 一个 allow-popups） | ❌ 断 | ❌ 断 |
| 跨站 + 设了任何档 | ❌ 断 | ❌ 断 |

口诀：**`same-origin` 是"洁癖档"**——除了"同源且同档"的，谁进我的组都断（连自家不设防的弹窗都嫌弃）；**`allow-popups` 是"洁癖但宠自己开的娃"**——别的规矩照旧，唯独我亲手开的普通弹窗可以留下（OAuth/支付就靠这格）。"被别人开"的方向两档一样挑剔：都要求开窗人"同源且同档"。

**判决时机**：分组判定**只发生在"窗口被打开/导航"的那一刻，之后不再重算**（这个细节后面会踩到：主页面后来导航成同源页面，也救不回之前被踢出去的弹窗）。

## 6.4 折断的后果：死引用

一旦被判"断"，开窗人手里的遥控器变成**死引用**（broken reference）：

```javascript
// A 页面（evil.com）
const w = window.open("https://challenge.com/review");  // B 带 COOP: same-origin
w.postMessage("hello", "*");   // ❌ 不报错、看起来调用成功、消息被静默丢弃
```

死引用的三个特征（分析时必须记住，它专门坑"想当然"）：

| 特征 | 说明 |
|------|------|
| **不报错** | 调用任何方法都不抛异常——你以为成功了 |
| **消息静默丢弃** | `postMessage` 根本不入队，对方什么都收不到 |
| **`w.closed` 显示 true** | 这不是"从对方读到了数据"，是浏览器给作废引用立的**墓碑**；对方窗口明明还活着 |

电话类比：**同源策略**是"电话打通了，但只许你说规定的话"；**COOP 死引用**是"号码被注销，听筒里永远忙音"。听到忙音（`closed=true`）不等于听到对方说话。

注意"死引用"和"白名单"是两个层面的关卡：**同源策略**管"通道活着，只许白名单操作"；**COOP** 是"通道整个不存在"——白名单、黑名单一起作废。

## 6.5 COOP 的三个边界事实

| 事实 | 说明 | 实践含义 |
|------|------|---------|
| **分离是永久的** | 一旦断开，无论之后怎么操作都不恢复，没有"重连"机制。验证方式：给被断开的弹窗里跑一个自增计数器脚本，主页面重新用同名 `window.open` 打开——如果复用的还是原窗口，计数应继续累加；结果计数从头开始，说明创建的是全新窗口、旧的从未"复生" | 一条路走死之后不要浪费任何时间在"怎么重连"上 |
| **清空 `window.name`** | 页面被 COOP 隔离后，它的窗口名标签被浏览器清空 | 想靠"按名字找回窗口"的路也断了 |
| **opaque 弹窗有豁免** | 加载"被 CSP 沙箱没收身份证"页面的弹窗，**不会**与开窗人断开（双向通道存活）；但反方向（主标签页加载 COOP 页面时，组里的无国籍成员仍被隔离）不豁免。此行为与浏览器实现/版本相关 | 属于边界行为，遇到"需要弹窗但 COOP 挡路"的场景可以作为实验方向 |

## 6.6 命名窗口与复用

`window.open(url, "名字")` 的规则是：

- 能在**同组**里找到叫这个名字的窗口 → **复用它**（把它导航到新 url，不另开窗口）；
- 找不到 → 新建一个。

和 COOP 联用的一个常见现象：**弹窗被 COOP 踢出组后，后续的同名 `window.open` 再也找不到它**，于是每次都"新建"。这在攻击脚本里通常无害（新建的窗口缺参数、打不开目标页），但审计时必须意识到：**不要假设"同名 open 一定复用同一个窗口"**。

## 6.7 两个"隔离"的分工（本章收束）

| 隔离机制 | 收走什么 | 引用还在吗 | 信还能寄吗 |
|---------|---------|-----------|-----------|
| 同源策略 / sandbox | "直接操作"（读 DOM、读变量） | 在（活引用） | ✅ 能（postMessage 正常工作） |
| COOP | "通道"本身 | 不在（死引用） | ❌ 不能（静默丢弃） |

落到本例的地图：

- `review`（父页面）↔ 沙箱 iframe：跨源隔离但**引用活着** → 是 postMessage 攻防的主战场（12 章）；
- `stage1`（攻击者页面）↔ 它打开的 `review` 弹窗：**被 COOP 折断** → "直接用弹窗给审查页发消息"这条路从根上不存在（这是分析中大量失败实验的共同死因）。

## 6.8 易混点

| 混淆 | 正解 |
|------|------|
| "弹窗" = `alert` 提示框 | 弹窗=新窗口（能装完整网页）；提示框加载不了页面 |
| COOP 会阻止我的页面被 iframe 嵌入 | 不管。防嵌入是 `X-Frame-Options` / `frame-ancestors`（05 章） |
| "COOP 只对被打开的页面生效" | 它是一个响应头，任何页面都能设；效力体现在"作为开窗人/被开窗人参与分组判定" |
| 读 `w.closed` 得到 true = 对方关了 | 死引用上也返回 true（墓碑），与对方真实状态无关 |
