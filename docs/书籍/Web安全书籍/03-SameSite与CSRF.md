# 03 SameSite 与 CSRF

> **本章一句话**：Cookie 的自动携带是一把双刃剑——方便登录，也让"别的网站"能借走你的身份发请求（CSRF）；`SameSite` 属性就是管"跨站的请求要不要带 Cookie"的闸门，而 CSRF 的根治手段是 token。

## 3.1 从"自动携带"到 CSRF

先看一个攻击场景（CSRF，Cross-Site Request Forgery，跨站请求伪造）：

1. 你登录了 `bank.com`，浏览器里存着会话 Cookie；
2. 你打开了 `evil.com`，它的页面里藏着一张图片：`<img src="https://bank.com/transfer?to=attacker&amount=100">`；
3. 浏览器加载这张"图片"时，自动向 `bank.com` 发出请求——**并且自动带上了你的会话 Cookie**；
4. `bank.com` 的服务器看到"带合法凭证的请求"，以为是你本人要转账，照办。

攻击者全程**不需要读到任何响应**：他只需要"请求被服务器执行"这个效果。这就是 CSRF 与 XSS 的根本区别（XSS 要在别人页面里跑自己的代码，CSRF 只是借你的浏览器发一条请求）。

CSRF 能成立的两个前提，正是第二章讲的两个机制：

| 前提 | 说明 |
|------|------|
| Cookie 自动携带 | 请求带不带凭证不由页面（更不由用户）控制 |
| 服务器只认"请求里的凭证" | 不区分这条请求是用户真心发的，还是被别的页面诱导发出的 |

## 3.2 两个基础概念：同站/跨站、顶级导航/子请求

要理解 SameSite，先掌握两组术语。

**站点（site）**：按"注册域"划分，如 `a.bank.com` 与 `b.bank.com` 属于**同一个站**（`bank.com` 的注册域），`evil.com` 是另一个站。

**请求的两种产生方式**：

| 方式 | 是什么 | 例子 |
|------|--------|------|
| **子请求** | 页面打开后，内部偷偷发出的请求（不换页面） | `fetch()`、`<img>`、`<script src>`、加载样式 |
| **顶级导航** | 整个页面跳到新网址（换页面） | 地址栏回车、点链接、提交表单、按后退键、`location.href=...`（脚本发起的整页跳转） |

> 注意"同站"与"同源"是两把不同的尺子：**同源**=协议+域名+端口三者完全相同（04 章）；**同站**=注册域相同。本章用的是"站"这把尺。

## 3.3 SameSite 三档

`SameSite` 是服务器种 Cookie 时给的一个属性，控制"从**别的站**发起的请求，浏览器还带不带这条 Cookie"：

| 档位 | 规则 |
|------|------|
| `Strict` | 最严：只要当前页面不是本站，任何发往本站的请求都不带 |
| `Lax` | 中间档（浏览器默认推荐值）：**子请求不带；GET 方式的顶级导航照带** |
| `None` | 不限制（现代浏览器要求同时加 `Secure`） |

`Lax` 的完整行为表（设你在 `bank.com` 已登录，下面看浏览器发往 `bank.com` 的请求带不带 Cookie）：

| 你正在做什么 | 请求类型 | 带 Cookie？ |
|------|------|------|
| 地址栏输入 bank.com 回车 | 顶级导航（GET） | ✅ |
| 在 `google.com` 点一个指向 bank.com 的链接 | 顶级导航（GET） | ✅ ← Lax 的"宽"处：跨站来的整页跳转也带 |
| bank.com 自己页面里的 `fetch()` / `<img>` | 同站子请求 | ✅ |
| `evil.com` 页面里 `fetch("bank.com/...")` | 跨站子请求 | ❌ ← Lax 的"严"处 |
| `evil.com` 页面里 `<img src="bank.com/...">` | 跨站子请求 | ❌ |
| 在 `evil.com` 点按钮提交表单、目标设为 bank.com（POST） | 顶级导航（POST） | ❌ ← Lax 的放宽只覆盖 **GET** 方式的顶级导航 |

> 注：表单用 `method=get` 时也算"GET 顶级导航"，会带；`POST` 不在放宽范围内。

## 3.4 关键推论：让机器人"整页打开"就等于借到身份

把 Lax 规则用到本例：

> 机器人浏览器里存着 admin 会话 Cookie（`SameSite=Lax`）。只要让**机器人的浏览器发起一次顶级导航**去打开目标网站的页面，那条 Cookie 就自动随行——被打开的页面因此"以管理员身份运行"。

这条推论是攻击链能成立的根本原因，它解释了两件事：

1. 攻击者页面里直接 `fetch("challenge.com/api/flag")` **读不到**东西（跨站子请求不带 Cookie）；
2. 但攻击者页面调用 `window.open("challenge.com/review?...")` **能打开**管理员页面（顶级导航带 Cookie）——"让浏览器替我打开一个带凭证的页面"就是全部要害。

## 3.5 冷知识：Lax 的 2 分钟宽限期

Chrome 有一条不那么广为人知的规则（官方名 **Lax-allowing-unsafe**）：

- **内容**：对**创建后 2 分钟内、且没有显式声明 `SameSite`** 的 Cookie，"跨站的 POST 表单提交"也会带上它（正常 Lax 规则下 POST 顶级导航是不带的）。
- **背景**：这是 Chrome 2020 年把 Cookie 默认值改成 Lax 时留的兼容窗口——避免弄断海量老网站"登录表单跨站 POST → 服务器种 Cookie → 跳转"的既有登录流。
- **边界（关键）**：该宽限**只管"没显式声明 SameSite"的老式 Cookie**；显式写了 `SameSite=Lax` 的 Cookie 不享受它（官方口径与当前 Chrome 行为一致）。要依赖这条行为时，必须用目标浏览器版本实际验证。
- **攻击含义**：如果目标站点的会话 Cookie 是"没声明 `SameSite`"的写法，攻击者页面在 Cookie 刚创建的两分钟内用跨站 POST 就可能"蹭"到身份——这是它值得记住的唯一理由；而对显式 `SameSite=Lax` 的会话 Cookie（本例的写法）不适用。

一句话总结：**宽限期是浏览器兼容性设计带来的窗口，不是可依赖的安全边界。**

## 3.6 CSRF 的完整防御

| 防御手段 | 原理 | 局限 |
|---------|------|------|
| `SameSite=Lax/Strict` | 让跨站请求带不上凭证 | 粗粒度（整站一刀切）；有兼容窗口（3.5）；老浏览器不支持 |
| **CSRF token**（根治） | 表单/请求体内带一个攻击者猜不到的随机值，服务器核对；攻击者能借到 Cookie，但借不到页面里的 token | 需要服务端配合改造；泄露（XSS）则失效 |
| 校验请求来源头 | 检查 `Origin` 或 `Sec-Fetch-Site`（09 章） | 只能作为纵深防御；对用户主动发起的导航天然放行 |
| 敏感操作二次确认 | 重新输密码等 | 体验代价 |

**为什么推荐 token 打底、SameSite 辅助**：SameSite 是"浏览器实现的行为约定"，token 是"服务器手里的确定性校验"。任何依赖"客户端会遵守约定"的防线都只能算纵深防御。

## 3.7 易混点

| 混淆 | 正解 |
|------|------|
| "跨站" = "跨源"？ | 跨站按注册域（`a.bank.com` 与 `bank.com` 同站）；跨源按协议+域名+端口（两者不同源）。SameSite 用"站"，同源策略用"源" |
| Lax 放宽所有顶级导航？ | 只放宽 **GET** 方式；跨站 POST 表单不带 |
| CSRF 需要攻击者能读到响应？ | 不需要；"请求被执行"本身就是攻击效果 |
| `SameSite=Strict` 就没有体验问题？ | 从别的网站跳转过来会"变成未登录状态"，很多站点因此用 Lax |
