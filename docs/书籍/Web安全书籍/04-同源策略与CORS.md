# 04 同源策略与 CORS

> **本章一句话**：浏览器给每个网页发一张"身份证"（源，origin），并规定"跨源时请求能发但默认读不到响应、更不能碰对方页面"——这套隔离叫**同源策略**；**CORS** 是服务器主动开出的"放行授权书"。
>
> 本章是 05-07 章的前置：不懂同源策略，就看不懂沙箱、COOP、postMessage 的任何一条规则。

## 4.1 origin：浏览器的身份证

浏览器给每个网页发一张身份证，内容是三样东西：**协议 + 域名 + 端口**。

```text
http://bank.com:80/page    → origin = http://bank.com
https://bank.com/page      → origin = https://bank.com        （协议不同，不同源）
http://bank.com:8080/page  → origin = http://bank.com:8080    （端口不同，不同源）
http://a.bank.com/page     → origin = http://a.bank.com       （域名不同，不同源）
```

"同源"= 三样全部相同。页面里可以用 `window.origin`（或 `location.origin`）查自己的身份证。

## 4.2 同源策略的三层管辖

网页之间"谁能对谁做什么"，按三件事分开管。**必须分三层记住**——很多混乱来自把三层混成一句"看不见"：

| 层 | 做什么 | 跨源时的规则 | 谁能开门 |
|----|--------|------------|---------|
| 第一层 | **发请求**给别的网站 | 完全不管：任何页面都能向任何地址发请求，服务器照常收到 | —— |
| 第二层 | **读响应内容**（JS 拿到返回数据） | 默认读不到；对方服务器用 CORS 授权后才能读 | 对方服务器（CORS 头） |
| 第三层 | **互操作对方页面**（读 DOM、页面变量、互相调用） | 一律禁止，**连 CORS 也救不了** | 没有任何令牌能开 |

逐层举例（`evil.com` 的页面想读 `bank.com/api`）：

- **第一层**：`fetch("https://bank.com/api")` —— 请求发出去了，`bank.com` 服务器也收到了。（CSRF 攻击钻的就是这个空子，03 章。）
- **第二层**：响应回来了，但**没配 CORS 时** `evil.com` 的 JS 就是读不到返回的数据。你平时见过"跨站也能调公开 API"，其实是对方配了 `Access-Control-Allow-Origin: *` 主动开门——门卫一直都在，只是有人主动开了门。
- **第三层**：跨源的 iframe，外面的页面读不到里面的 `document`（页面内容对象），反过来也一样。**没有任何响应头能打开这一层。**

> 顺带分清两把尺子：**同源** = 协议 + 域名 + 端口完全相同（管第二、三层）；**同站** = 注册域相同（`a.bank.com` 与 `b.bank.com` 同站但不同源；03 章的 Cookie SameSite 用的是"站"）。

## 4.3 CORS：服务器递给浏览器的授权书

CORS（Cross-Origin Resource Sharing，跨源资源共享）**不是**与同源策略平行的另一套系统，而是"服务器给浏览器开的授权书"：

```text
① 浏览器发跨源请求时自动带上身份证：
   Origin: https://friend.com

② 服务器如果同意，在响应头里抄写回来：
   Access-Control-Allow-Origin: https://friend.com

③ 浏览器比对：①和②一致 → 放行 JS 读取响应内容；否则拦截
```

服务器"开门"的两种常见写法：

| 写法 | 效果 | 使用场景 |
|------|------|---------|
| `Access-Control-Allow-Origin: *` | 任何来源都能读 | 公开 API |
| **白名单回显**：核对 `Origin` 后把**通过的那个值抄回来** | 只有指定网站能读 | 需要授权的业务接口 |

**一个真实存在的危险配置**：有些运维遇到 `null` 报错，图省事直接配 `Access-Control-Allow-Origin: null`——这等于对全世界所有"无国籍页面"（05 章）开门。安全审计看到这个头要立刻警觉。

还有两个必须记住的边界：

- **CORS 拦的是"读"，不是"发"**：简单请求照样送达服务器（效果已产生）；只有"非简单请求"（自定义头、JSON 体等）会先发预检请求（`OPTIONS`），未获批准时**正式请求根本不发出**。外传数据时这决定了能用什么手法（08 章）。
- **所有门的最终执行者始终是浏览器**：服务器只能"提出授权"，拦不拦是浏览器的事。绕过浏览器（用 curl 直接发包）时这些规则全部不存在——这也是攻击脚本模拟请求时能"伪造"请求头的原因。

## 4.4 document.domain：历史遗迹

早期有一个例外设置：同站但不同源的页面（`a.bank.com` 与 `b.bank.com`）可以双方主动声明 `document.domain = "bank.com"` 来互访 DOM。这个机制因安全风险已被主流浏览器废弃禁用（Chrome 115 起默认移除）。**旧资料里的"跨子域互访技巧"在今天基本不可用**，遇到时先查目标浏览器版本。

## 4.5 实战推演：为什么读 flag 的四条路全被堵死

拿本例做一次完整的"攻击面收敛"（这是安全分析中与"找漏洞"同样重要的动作）。目标：读走管理员接口 `/api/flag` 的响应。攻击者站在 `evil.com` 页面上，逐种尝试：

| 尝试 | 拦在哪 | 依据章节 |
|------|--------|---------|
| ① `fetch("http://challenge.com/api/flag")` | 跨站子请求不带 admin Cookie → 服务器 403 | 02/03 章 |
| ② `<iframe src="http://challenge.com/api/flag">` 嵌进来读 | `X-Frame-Options: SAMEORIGIN` 直接拒绝加载 | 05 章 |
| ③ `<script src="http://challenge.com/api/flag">` 当脚本加载 | `Cross-Origin-Resource-Policy: same-origin` 直接拦下 | 09 章 |
| ④ `window.open("/api/flag")` 弹窗打开 | 能打开！flag 显示在弹窗里——但 COOP 把遥控器折断，攻击者代码**碰不到**那个窗口的内容 | 06 章 |

四种姿势全灭，共同点：**都不在目标域的"同源圈"内，读不到内容**。由此得到结论（它决定了整条攻击链的形态）：

> **要读数据，必须让 JavaScript 跑在目标网站自己的页面上**——也就是需要一个目标域上的 XSS（08 章）。

## 4.6 易混点

| 混淆 | 正解 |
|------|------|
| "跨源请求被浏览器拦下了" | 第一层不拦：请求已发出、服务器已收到；被拦的是"读响应" |
| "CORS 开了就能跨源操作对方 DOM" | 第三层连 CORS 都无效；跨源页面互操作只有 `postMessage` 一条正道（07 章） |
| "Origin 头是页面代码写的" | 由浏览器自动填写，页面 JS 改不了 |
| 同源 vs 同站 | 同源=三要素全同；同站=注册域相同。两把尺子并存，用的场景不同 |
