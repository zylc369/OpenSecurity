# 11 BFCache 与历史栈

> **本章一句话**：浏览器把访问过的页面记成一条**历史栈**；按后退/前进时优先从 **BFCache**（back/forward cache，前进后退缓存）解冻旧页面——**不发网络请求**；想让回退产生一次真实请求，必须先把目标页从 BFCache 里"挤出去"。

## 11.1 历史栈模型

每个标签页有一份"访问过的页面"清单（**历史栈**）：每访问一个新页面就在末尾压一条记录，当前页面是栈顶。代码操作它的 API：

| API | 作用 |
|-----|------|
| `history.back()` / `history.forward()` | 后退 / 前进一格 |
| `history.go(-N)` / `history.go(N)` | 后退 / 前进 N 格 |
| `history.length` | 当前栈里有几条记录 |
| `history.pushState()` / `replaceState()` | 不换页面、只往栈里加/改记录（配合单页应用） |

"**历史导航**"= 用户点浏览器后退/前进按钮，或代码调用 `back()` / `forward()` / `go()` 导致的页面切换。

本例中机器人浏览器的历史栈（攻击开始时）：

```text
历史栈（最新在下）：
┌────────────────────────────────────────────┐
│ 1. /reports/check?rid=xxx&state=NONCE       │ ← 机器人流程第 1 件事
│ 2. /api/flag                                │ ← 机器人流程第 2 件事
│ 3. http://evil.com/stage1?note=...&rid=xxx  │ ← 机器人流程第 4 件事（攻击者的页面）
└────────────────────────────────────────────┘
```

## 11.2 一次导航的三种结局

浏览器处理"打开一个网址"时，按顺序尝试更省的办法：

| 结局 | 条件 | 是否产生网络请求 |
|------|------|----------------|
| ① 命中 HTTP 缓存 | 有可用的新鲜副本（10 章） | 否（或只发一条条件请求） |
| ② 命中 BFCache | 这个历史条目在缓存里 | 否（连条件请求都没有） |
| ③ 真实请求 | 两者都没有 | 是 |

BFCache 的覆盖范围比 HTTP 缓存**更广**：它保存的是整页内存快照，所以连"不允许被 HTTP 缓存的响应"也能被它留一份。

## 11.3 BFCache 机制

| 问题 | 答案 |
|------|------|
| 保存什么 | **整个页面**：DOM、JS 变量与运行状态（定时器、未完成的逻辑），原样冻结 |
| 解冻 | 后退/前进命中时瞬间恢复，页面"像没离开过一样"继续运行 |
| 容量 | Chrome/Chromium 同一标签页的条目数**上限约为 6 条**（随版本可能变化） |
| 淘汰 | 容量塞满后，最旧的条目被移出（"挤出"） |
| 与网络的关系 | **命中时服务器完全不知道有人来过**——没有请求、没有日志、没有门检查 |

最后一条是本例的关键：审查流程的所有条件检查都在**服务器代码**里；如果回退命中了 BFCache，服务器根本不执行检查，等于白退。

## 11.4 为什么要"挤出"（目标与策略）

本例要求：对审查页产生一次"**真实到达服务器**、且带用户操作级标记的第二次访问"。直接 `history.go(-2)` 回退会发生什么：

> 浏览器心想"这页我冰箱里还冻着一份呢，不用重新做"——把缓存里冻着的旧页面原样端出来。**服务器一无所知**。

所以要先让缓存里没有这份"冻货"：

**策略：连续自导航 8 次塞满容量。** 在攻击者页面上连续让它跳转到自己（同一文件、不同网址参数，效果像刷新自己），每次自导航都会在历史栈压一条新记录、并让 BFCache 腾位置：

```text
挤之前的历史栈：         挤之后（8 次自导航后）：
1. check  ← 在缓存里    （第 1、2 条被挤出 BFCache）
2. flag                  3. stage1
3. stage1                4. stage1?ph=evict&nn=1
                         5. stage1?ph=evict&nn=2
                         …（8 个新条目）
                         11. stage1?ph=evict&nn=8
```

**为什么跳 8 次而不是刚好 6 次**：容量"约 6 条"是实现细节、不是官方承诺（不同版本可能不同）。多跳两次成本极低（每步约 120 毫秒），但少跳一次就可能导致挤出不完全。宁多勿少。

## 11.5 挤出链的工程化：把网址当"程序计数器"

**难点**：每次自导航都会重新加载页面、销毁当前页面的 JS——代码怎么"跑完 8 步"？

**解法**：把"进行到第几步"写进**网址参数**。页面每次加载时先读网址，就知道该干什么；跳转时把"步数 +1"写进下一个网址。脚本死一次、重启一次、接力一次：

```javascript
const params = new URLSearchParams(location.search);
const nn = parseInt(params.get("nn") || "0");       // 从网址读"现在第几步"

if (params.get("ph") === "evict") {                  // 已进入挤出阶段
  if (nn < 8) {
    setTimeout(() => {
      location.href = location.pathname + "?ph=evict&nn=" + (nn + 1);  // 下一步
    }, 120);                                          // 间隔 120ms，8 步共约 1 秒
  } else {
    setTimeout(() => history.go(-10), 200);           // 挤完，回放审查页
  }
} else {
  // 首次加载：先做别的准备工作（弹窗竞态，12 章），3.5 秒后进入挤出阶段
  setTimeout(() => { location.href = location.pathname + "?ph=evict&nn=1"; }, 3500);
}
```

四个实现细节都有原因：

| 细节 | 原因 |
|------|------|
| 间隔 120ms（不能更快） | 自导航过快时浏览器会**合并历史条目**：把间隔压到 0 毫秒，8 次跳转后栈里只多了 2 条记录，回退根本到不了目标条目 |
| 用 `location.href` 整页跳转（不能用 `#hash`） | 只改 `#` 后面部分**不会重新加载页面**，也不会生成新的 BFCache 存档——白改，挤不动 |
| 不能去弹窗里跑挤出 | 弹窗是**全新窗口，历史栈是空的**；目标条目（审查页访问记录）只在主窗口的历史里 |
| `history.go(-10)` 而不是 `go(-2)` | 从栈顶往回数：8 步自导航 + flag 接口页 + 审查页 = 10 条 |

## 11.6 回退：历史回放自动凑齐条件

`history.go(-10)` 落到栈底的审查页条目上。因为该条目已被挤出 BFCache，这次回退变成**真实的网络请求**，并且自动带上三组关键条件：

| 条件 | 哪来的 |
|------|--------|
| 完整原网址（含 `rid` 与随机暗号 `state`） | 历史记录里存的就是当年那条网址，**原样重发** |
| `Sec-Fetch-Site: none` + `Sec-Fetch-Dest: document` | 历史导航语义上等同"用户操作"且是整页导航（09 章） |
| admin 会话 Cookie | 顶级导航，`SameSite=Lax` 不拦（03 章） |

这里藏着全题最巧的一点：**攻击者从头到尾不知道暗号（nonce）的值**。答案是"不需要知道"——让浏览器把当年那条带暗号的网址**原样重发**一遍，暗号自动随网址回来了。这类"历史回放"技巧的通用价值：**当请求必须携带你不知道、但曾出现在浏览器历史里的凭证时，回退重发是最自然的绕过方式**。

## 11.7 防御视角

| 防御点 | 说明 |
|--------|------|
| 一次性令牌 | 暗号（nonce）这类凭据必须"**消费即失效**"，否则历史里任何一条旧网址都是长期有效的通行证 |
| 响应加 `Cache-Control: no-store` | 减少响应被缓存留存的可能（但注意 BFCache 与 HTTP 缓存是两套机制） |
| 不要假设"回退不会发请求" | BFCache 的容量与淘汰策略因浏览器/版本而异；攻击者可以主动把它挤出去，让回退"退化为"真实请求 |
| `Sec-Fetch-Site: none` 不可过度信任 | 它无法区分"真人回退"与"被脚本驱动的回退"（12 章） |

## 11.8 易混点

| 混淆 | 正解 |
|------|------|
| BFCache vs HTTP 缓存 | 快照 vs 响应；历史导航 vs 任何 GET；两套机制，见 10.7 对比表 |
| "`history.go(-N)` 回退 N 个'页面'" | 按**条目**数算；自导航、同文档跳转都会产生条目 |
| "回退一定重新请求" | 只在 BFCache 未命中时才会；命中时连请求都没有 |
| "暗号必须知道才能用" | 历史回放不需要知道值——浏览器替你原样重发 |
