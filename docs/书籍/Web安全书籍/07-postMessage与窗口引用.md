# 07 postMessage 与窗口引用

> **本章一句话**：被同源策略隔开的窗口之间，只剩一条正当通道——`postMessage`（寄信）；信件上"寄件人"（`e.source`）指向寄出它的窗口（投递时源文档已销毁则为 `null`）——这个细节是后面竞态攻击的胜负手。

## 7.1 窗口引用从哪来

要通信，先得有对方的"遥控器"（引用）。窗口关系分两大类，每类都有固定的拿引用写法：

**第一类：同一个标签页里的 iframe 家族**

| 方向 | 写法 | 说明 |
|------|------|------|
| 父拿子 | `iframe元素.contentWindow` | 父页面里用 iframe 元素取它里面那个窗口 |
| 子拿父 | `window.parent` | "装着我的那个父窗口" |
| 子拿顶层 | `window.top` | "这个标签页最外层的窗口"；只有一层嵌套时 `top` 和 `parent` 是同一个 |
| 兄弟互拿 | `window.parent.frames[1]` | 父页面里的第 2 个子窗（从甲窗出发经父页面中转） |

`frames` 是**浏览器给每个窗口出厂自带的属性**（不是页面自己定义的变量），表示"我的直接子窗清单"。三个细节：

- 排序按 iframe 标签在 HTML 里**从上到下**出现的顺序（DOM 树顺序），与加载先后、id 名、CSS 位置无关；
- 只存**直接**子窗：孙 iframe 要两跳（`frames[0].frames[0]`）；
- 清单是**活的**：删掉第一个 iframe，原第二个自动变成 `frames[0]`。

**第二类：开窗关系的两个独立窗口（弹窗场景）**（详见 06 章）

| 方向 | 写法 |
|------|------|
| 开窗人拿弹窗 | `const w = window.open(url)` 的返回值 |
| 弹窗拿开窗人 | `window.opener` |

> 写法说明：`window.` 前缀可以省略，`parent.postMessage(...)` 和 `window.parent.postMessage(...)` 完全等价。

## 7.2 WindowProxy 与跨源白名单

你拿到的跨源窗口引用其实是一个"**遥控器外壳**"（术语 **WindowProxy**）：页面脚本访问 `window`、`contentWindow` 时得到的都是它。**每次**通过它读写属性，浏览器内核都先拦截检查：属性在白名单里就放行，不在就返回 `undefined`、静默忽略或抛 `SecurityError`。网页代码关不掉它，服务器也管不着。

跨源白名单（规范名 "cross-origin accessible properties"）的设计原则是一条：**只许做动作、不许读数据**。

| 允许（动作类） | 说明 |
|---------------|------|
| `postMessage` | 发消息（对方听不听由对方决定） |
| `focus` / `blur` | 聚焦 / 失焦 |
| `close` | 关窗 |
| `location` **赋值** | 把对方导航走（注意：**读** `location.href` 被禁，那是读数据） |
| 读 `closed` / `length` | 两个例外：分别只泄露一比特 / 一个小数字，判定无害放行 |
| 家庭关系引用 | `top` / `parent` / `frames` / `opener` 等 |

| 禁止（读数据类） | 说明 |
|-----------------|------|
| 读对方 `document` | 整个页面内容 |
| 读对方页面变量 | 页面内数据 |
| 读 `location.href` | 对方当前地址 |

白名单由谁定、由谁执行：**制定者是行业规范**（WHATWG 的 HTML Standard，一份持续更新的活文档，逐项列死）；**执行者是浏览器**（Chrome 的 Blink、Firefox 的 Gecko、Safari 的 WebKit 各自按同一份规范实现）。网站自己改不了规则。

顺带一个常见误解：**iframe 不设 sandbox 时，父子能不能互操作 DOM，取决于同不同源**——同源父子可以完整互读互改；是 `sandbox`（05 章）把同源关系打散成无国籍的。

## 7.3 postMessage 的用法

```javascript
// 发送方（任何源都可以寄，寄信本身不查身份）：
targetWindow.postMessage(
  { cmd: "hi" },   // 信件内容（数据）
  "*"              // targetOrigin：投递条件（"*" = 不挑剔收件人的网站身份）
);

// 接收方：登记一个 message 监听器，每封到达的信都会触发这段代码
window.addEventListener("message", (e) => {
  e.data;    // 信件内容
  e.origin;  // 寄件人来自哪个网站（如 "https://challenge.com"）
  e.source;  // 寄件人窗口的引用（"信封上的寄件人地址"）
});
```

几个必须记住的点：

- **送达的前提**：你手里握着对方窗口的**有效引用**。跨源、沙箱都不影响引用有效性（05 章的玻璃房照样能寄信）；只有 COOP 死引用会成为"空调用"（06 章）。
- `targetOrigin` 是**发送方**设的投递条件：写 `"*"` 表示不挑剔；写具体来源则对方网站不一致时消息不投递。
- 接收方**必须自己校验 `e.origin`**（决定"听不听"）——监听器对任何来源的来信都会触发。

## 7.4 消息的身份校验：正确姿势与坑

防线常在监听器里"校验寄件人身份"。最经典的一种写法是拿窗口引用做全等比较：

```javascript
if (e.source === viewer.contentWindow) return;   // "寄件人就是自家 iframe → 拒收"
```

`===` 比较的不是"内容是否一样"，而是"**是不是同一个东西**"——好比张三和张三的克隆人长得一样也不是同一个人。问题在于：`e.source` 和 `viewer.contentWindow` **根本不是同一时刻取到的值**——`e.source` 在寄出那一刻指向寄件窗口，**若投递时源文档已销毁它会变成 `null`**；`contentWindow` 每次处理消息时现场重读。两者之间一旦发生"文档切换且旧文档已销毁"，比较结果必然翻转（`null` 不等于任何窗口引用）。**这正是竞态攻击的入口**（12 章完整展开）。

正确的校验姿势（防御建议）：

| 手法 | 为什么 |
|------|--------|
| 校验 `e.origin` | 它是网站身份，**不随文档切换而变** |
| 来源白名单 | 只接受指定网站的消息 |
| 消息体带一次性令牌 | 由服务器生成、服务端核验，攻击者伪造不了 |
| 点对点场景用 `MessageChannel` | 通道显式建立，不依赖"谁的窗口引用" |
| 不做单独授权 | 浏览器侧的**任何信号**都不应单独作为授权依据（12 章） |

## 7.5 e.source = null 技巧（已知玩法）

安全社区公开过**一类技巧：让发送方在消息被处理前"消失"**——接收方处理这条消息时，`e.source` 变成 `null`（`null` 不等于任何窗口引用，从而绕过窗口身份比较）。

核心条件只有一个：**消息被处理时，源文档已经销毁**。由谁"促成销毁"有两条路径：

- **被移除**：iframe 挂在接收方的页面上，只有接收方页面的代码能删它（发送方跨源访问不到自己的 `frameElement`，删不了自己）——这条路径要求"接收方页面自己会删除 iframe"；
- **自导航/自行销毁**：发送方自己导航走。若消息被处理时旧文档已经销毁，`e.source` 同样为 `null`；若在销毁前就被处理，则仍指向当前窗口、比较不变——**是否得手取决于处理时序**（与 12 章 pagehide 竞态是同一条原理）。

本例的接收方页面代码固定写死、没有任何删 iframe 的逻辑，这条路径未被采用。

## 7.6 MessageChannel：点对点消息通道

浏览器还提供了一个更"结构化"的通信方式：`MessageChannel`。它创建一对绑定的端口（`port1` / `port2`），一方把其中一个端口**通过 postMessage 交给对方**，此后双方直接经端口收发：

```javascript
const ch = new MessageChannel();
targetWindow.postMessage({ port: ch.port2 }, "https://challenge.com", [ch.port2]);
ch.port1.onmessage = (e) => { /* 只在建立时约定的双方之间流通 */ };
```

相比裸 `postMessage` 的优势：**通道是显式建立的**（不依赖"当前谁握着谁的窗口引用"）、双方在建立时就绑定、第三方难以中途插话。它是"授权类消息"的推荐实现方式（12 章防御部分再提）。

## 7.7 实例精读：审查页的消息监听器

```javascript
window.addEventListener("message", (e) => {
  if (!closing || e.source === viewer.contentWindow) return;
  // 两道检查都过 → 用页面体内的 nonce 替发信者提交批准
  fetch("/complete", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(report),   // report 里含服务器渲染进页面的 nonce
  });
});
```

逐行读：

- `closing`：一个开关，`viewer`（iframe）第一次加载完成后才置 true——意味"审查流程已开始"；
- 拒收条件：开关未开，**或**寄件人就是 `viewer` 里当前那个窗口；
- 两道都过 → 这个页面**亲自**替寄件人发批准请求（请求自带它体内的 nonce 与管理员身份）。

翻译成人话，这段代码的意图是：**"在我加载完 viewer 之后，任何一个不是 viewer 自己的窗口给我发消息，我就替它按下批准按钮。"** 于是攻击问题变成：怎么制造一条"不是 viewer 自己"的消息？（12 章。）

## 7.8 易混点

| 混淆 | 正解 |
|------|------|
| `e.origin` vs `e.source` | 前者是"寄件人网站"（字符串，不随文档切换变）；后者是"寄件人窗口引用"（对象，可能在文档切换时对不上） |
| "消息没到" vs "消息被过滤" | 外观完全一样（都不报错）。排查时必须专门设计实验验证"对方到底收到没有" |
| `targetOrigin` 写 `"*"` 会泄露数据？ | 不会——它只决定"投给哪个窗口"；收件人网站不对就不投递。真正要防的是接收方不校验 `e.origin` |
| "跨源窗口引用什么都做不了" | 动作类操作（发消息、导航、关窗）照做；禁的只是读数据 |
