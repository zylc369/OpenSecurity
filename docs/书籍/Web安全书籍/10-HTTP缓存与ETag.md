# 10 HTTP 缓存与 ETag

> **本章一句话**：HTTP 缓存保存"GET 请求的响应原件"，下次相同请求可以直接复用、**跳过服务器**；`ETag` 是服务器给内容发的"指纹"，用来做"内容变没变"的快速核对；`Vary` 决定"按请求头里的哪些字段把响应分版本存放"。

## 10.1 HTTP 缓存是什么

通常说的"浏览器缓存"就是它。四个要点：

| 问题 | 答案 |
|------|------|
| 保存什么 | `GET` 请求的**响应**本身（状态码 + 响应头 + 响应体）；条目还会附上复用判断所需的少量请求信息（请求方法、URL、被 `Vary` 指名的请求头值） |
| 谁的内容会进 | 不限定类型（HTML、CSS、图片、JSON……），不限定发起者（页面跳转、`fetch`、图片/脚本加载都走同一套）；是否真的保存与复用，由响应头和浏览器实现决定 |
| 怎么用 | 之后遇到请求时先检查本地记录；判断"某份保存的响应可以使用"就直接用，**不再发出网络请求** |
| 谁管理 | 浏览器自己。页面 JS **没有直接读写它的接口**（`fetch` 的 `cache` 选项只是"指示这次用不用"，读不到也删不掉条目）；服务器也读写不到，只能用响应头（`Cache-Control`、`Vary` 等）提要求 |

> 别混淆：页面里 `caches` API 是另一套**程序缓存**（Service Worker 用的），不是 HTTP 缓存。

## 10.2 与缓存相关的响应头

| 头 | 作用 |
|----|------|
| `Cache-Control: no-store` | 完全禁止缓存（敏感接口常用） |
| `Cache-Control: max-age=N` | N 秒内可直接复用（"新鲜期"） |
| `Expires` | 老式过期时间写法 |
| `ETag` | 内容指纹：一般是内容哈希，也可以是版本号或修改时间 |
| `Last-Modified` | 内容的最后修改时间 |
| `Vary` | 复用条件里附加的请求头字段（10.4 详讲） |

## 10.3 有效期过了怎么办：条件请求与 304

缓存条目有有效期。有效期一过，浏览器有两种选择：直接重新下载整份响应；或者先问一句"我本地这份还能用吗"。后者更省流量、更快。

问法（**条件请求**）：

```text
GET /note/c350151803f0f8f3d507 HTTP/1.1
If-None-Match: W/"2c4-vk0cnITZv6PybK/b0EOva9fTmFM"     ← 带上上次响应里的 ETag
```

服务器拿当前内容的 ETag 与请求里的比对：

| 结果 | 响应 | 含义 |
|------|------|------|
| 一样 | `304 Not Modified`（只有响应头，**无响应体**） | 内容没变，浏览器继续用本地那份，并把有效期延后 |
| 不一样 | `200` + 新内容 + 新 ETag | 内容变了，完整发一份新的 |

**为什么值得这么做**：比对 ETag 是服务器本地的一步（很便宜），省下的是**整份响应体的网络传输**（`304` 只有几百字节响应头，完整响应可能几 KB 或更大）。同一个 ETag 会出现在两个地方：服务器生成时写在**响应头 `ETag`** 里；浏览器做条件请求时把它放进**请求头 `If-None-Match`** 捎回去。

一个容易误解的点：**动态页面（服务端渲染）也照常算 ETag**——服务器**照常执行**渲染逻辑，完成后对这次的响应体算指纹；"没变就返回 304"由框架自动完成。也就是说它省的是**传输**，不是服务器的计算（除非应用自己设计一张轻量版本表来跳过渲染，那是应用层的额外优化）。

## 10.4 Vary 与缓存变体

`Vary` 的完整含义一句话：**服务器告诉缓存："以后想复用这条响应，除了 URL 要对得上，我点名的那几个请求头也必须和生成它时一模一样。"**

- 它写在**响应头**里；
- 它的**值是请求头的名字**：写 `Cookie` 就比 `Cookie` 头；也可以写多个；
- 比较的一方永远是**新请求的请求头**（拿新请求和存下的响应比）。

例子：同一 URL 按请求语言返回中/英文版——`Vary: Accept-Language` 让缓存把两个版本**分别存成两条**（`zh-CN` 一条、`en-US` 一条），谁来了命中谁那份；不写 `Vary` 的话缓存只存一条，英文用户会拿到先被缓存的中文版。

> 术语：同一 URL 按不同条件分开缓存，叫不同"**变体**"（variant）。`Vary: Cookie` 就是"按 `Cookie` 头分变体"。

## 10.5 实战：用 `Vary: Cookie` 让"第二次访问"必然打到服务器

本例里有一条容易被忽略但极精巧的设计。目标：**保证第二次访问审查页的请求不会被 HTTP 缓存截走**（否则渲染分支根本没机会执行）。机制由两个部分配合：

**第一步：首访的响应被保存进缓存时，多记了一个字符串。**

首访 `/reports/check` 的响应头里有两行关键内容：

```text
Vary: Cookie                          ← 服务器要求：复用这条缓存，要按 Cookie 头比对
Set-Cookie: view=8d7b1188...; Path=/reports/check   ← 同时给浏览器种下一个新 cookie
```

`Vary: Cookie` 指名了匹配条件，缓存规范要求"必须把当时的值留在手边"——于是这条缓存条目里多记了一个字符串：**产生这条响应的那个请求的 `Cookie` 头的值**（此刻机器人的浏览器里只有登录用的 `sid`，还没有 `view`）。

**第二步：第二次访问前，缓存做两级检查。**

```text
① URL 比较：新请求 URL 与条目 URL 相同 → 通过
   （如果没有 Vary: Cookie，检查到此为止、允许直接复用这条缓存）
② Cookie 头的值比较（条目带 Vary: Cookie 才会做）：
     条目里记下的：第一次访问时请求里 Cookie 头的值（只有 sid）
     新请求携带的：第二次访问时请求里 Cookie 头的值（sid 之外**还多了 view**）
     结果：不相同 → 这条缓存条目不可用 → 请求真的发到服务器
```

为什么新请求会多出 `view`：第一步的 `Set-Cookie` 把它存进了浏览器的 cookie 存储，而 `view` 的 `Path=/reports/check` 恰好覆盖这次请求的路径，浏览器按规则自动带上它（02 章）。于是 ② 的比较**必然不同**，第二次访问**必然落在服务器上**。

两个缺一不可的反向推演：没有 `Vary: Cookie` → 检查停在①、直接复用缓存；没有 `view` → 两次该头的值相同、缓存同样被复用。

> 特别澄清：缓存条目里那份"Cookie 记录"**不是 cookie**。cookie 只有一份（在 cookie 存储里，决定"请求带什么"）；条目里的记录只是"产生这条响应的那个请求头值"的留底（决定"这条缓存能不能复用"）。两个机制本来互不相关，是服务器写的 `Vary: Cookie` 这一行把它们联系起来；缓存不解析 cookie 的含义（身份、会话等它都不懂）。

## 10.6 缓存与安全的关系

| 视角 | 要点 |
|------|------|
| 共享缓存风险 | 浏览器缓存是"每台设备一份"；**代理/CDN 缓存**是"多用户共用一份"，敏感页面的响应被共享缓存留存会向其他用户泄露内容 → 敏感响应应带 `Cache-Control: no-store` |
| 攻击的必要条件 | 攻击者要构造"被服务器实时处理的请求"，就必须让请求**绕开一切缓存**——HTTP 缓存是一条路径，BFCache 是另一条（11 章），本章的 `Vary: Cookie` 是服务器侧的"反缓存"设计 |
| 防重放 | `no-store` 也是防"历史回放/重复消费"类攻击的手段之一（12 章防御） |

## 10.7 与 BFCache 的区别（预告）

| | HTTP 缓存 | BFCache |
|---|----------|---------|
| 保存什么 | 响应内容（状态码+头+体） | **整个页面的内存快照**（DOM、JS 运行状态） |
| 何时生效 | 任何 GET 请求 | **只有历史导航**（后退/前进） |
| 命中后 | 不发请求 | 不发请求（连条件请求都没有） |
| 生命周期 | 可跨会话持久 | 进程内存，会话级 |

两者都会"跳过服务器"，但机制、层级、触发条件完全不同——下一章专讲 BFCache。

## 10.8 易混点

| 混淆 | 正解 |
|------|------|
| "ETag 相同 = 直接复用本地响应" | 复用条件是一组（URL、Vary 指名的头等）；ETag 只是"内容指纹核对" |
| "浏览器缓存 = `caches` API" | 前者由浏览器自动管理（HTTP 层）；后者是页面代码显式操作的另一套存储（Service Worker 场景） |
| "Vary 写在请求头里" | `Vary` 是**响应头**；它"点名"的是**请求头**的名字 |
| "动态接口不用管缓存" | 返回 JSON 的 GET 接口同样会被缓存；不希望被缓存就要显式 `no-store` |
