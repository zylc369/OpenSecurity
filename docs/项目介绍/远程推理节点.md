# 远程推理节点：把 7.6GB 模型搬去闲置机器，人在外也照样调用

> 本文是 OpenSecurity 的机制详解系列之一。OpenSecurity 是一套 AI 驱动的多领域安全分析 Agent 平台（前作：[无人值守完成 CTF 挑战](./2.0-实战博文/01-无人值守完成CTF挑战.md)、[知识与记忆体系](./知识与记忆体系.md)）。这次要讲的是它的一个基础设施组件：**远程推理节点**——把本地模型搬到另一台机器上跑，本机内存立刻松一口气；人在外面也照样调用：一台便宜 VPS 负责信令协调与兜底中继，主控与节点打洞直连为主——链路全程加密，VPS 只见密文，未通过认证的流量在节点上一个响应字节都换不到。

## 先算一笔内存账

OpenSecurity 2.0 有三个模型常驻本地：**BGE-M3**（向量化，4.3GB）、**Reranker**（重排序，2.1GB）、**GLM-OCR**（图像文字识别，1.2GB），权重合计约 **7.6GB**，加上加载与推理峰值，实际要预留 **约 12GB 内存**。在我的测试机（MacBook Pro / M4 Pro / 48GB）上，这笔开销能承受，但也仅仅是能承受——浏览器自动化、扫描工具、Docker 一拥而上时，余量并不豪华。

另一边，家里躺着一台闲置的 Mac Mini（16GB 内存），大部分时间在吃灰。

于是问题自然成形：**能不能让模型在 Mac Mini 上跑，MacBook 只管调用？** 顺手还能满足三条硬约束：

1. **省钱**：本地（或自家局域网内）推理的边际成本几乎为零，不用为向量化和 OCR 付 API 费；
2. **数据不出门**：分析对象、截图、知识库内容都在自己的机器之间流转，不经过任何第三方云；
3. **机器不挑位置**：Mac Mini 在家里路由器下也行、搬到异地也行——异地场景需要一台 VPS 做协调（后面细讲，1G 小鸡即可）。

整个方案分两步走，也是实际开发的顺序：**先把局域网内的"能用"做扎实，再解决异地无公网 IP 的"可达"**。

## 形态一：局域网直连，先让它能用

### 节点就是同一份代码的第二种部署形态

远程推理节点不是一个新的服务，而是**同一套 backend 代码的第二个角色**：MacBook 是"主控"，Mac Mini 是"节点"。节点机上跑同样的 server，只是配置不同——设置一个 `CONTROL_API_KEY`，它会做三件事：

- 监听地址从 `127.0.0.1` 切到 `0.0.0.0`（局域网可达）；
- 启动即预加载三个模型（节点嘛，模型常驻是本职）；
- 进入"常驻模式"（`CONTROL_RESIDENT=1`），禁用主控侧的空闲自杀机制——节点 7×24 在线，不该因为没人用而退出。

节点机的启动是一等公民入口，一条命令全自动：venv 自举 → 装依赖 → 交互式补齐配置 → 下载模型（HF 端点官方/镜像双端实测择优，镜像快过 2 倍才固化，避免抖动）→ 以独立会话启动（SSH 断开进程不死）：

```bash
./start-remote-node.sh          # 全自动；--check 只预检；--skip-tts --skip-models 快速启动
```

### 主控侧：消费方一行代码都不用改

这是整个一期设计里我最满意的一个决策。调用模型的代码散布在记忆库读写、事件图谱写入、OCR 服务等多个消费方手里，如果切换远程需要每个消费方自己判断"走本地还是走远程"，改造面会失控。

实际做法是**路由收敛在模型加载层内部**：以向量化为例，`LockedEmbedder.encode()` 的对外签名与返回类型完全不变，内部先看远程链接状态机的快照——远程健康就走远程，失败就落回本地。对上层（图数据库、向量库、MCP 服务）来说，这一切不存在。**远程化是基础设施的私事，业务层无权知晓。**

### 分层信任：谁能碰什么

节点绑了 `0.0.0.0`，鉴权就要跟上下功夫。节点控制台的信任模型分三层：

| 来源 | 信任级别 | 能做什么 |
|------|---------|---------|
| 本机（127.0.0.1 / ::1） | 全放行 | 完整管理与推理 API |
| 局域网（私网地址 + 节点模式） | 信任放行 | 推理 API + 管理 UI（免令牌，方便节点机旁边的浏览器直接管理） |
| 公网来源 | 最小暴露 | 仅白名单推理端点 + Bearer 令牌；管理面一律 403 |

最后一层是给"`0.0.0.0` 被意外暴露到公网"兜底的——即便发生，攻击者拿到的也只是"一个需要令牌的推理入口"，管理面根本不可见。

## 形态二的铺垫：让"断"不致命——心跳状态机与降级

远程方案最怕什么？**节点不在眼前，它挂了你不知道。** 所以在讲异地连通之前，先讲可靠性——这部分是两种形态共用的底座。

主控侧有一个独立的状态机（`remote_link`），后台每 **5 秒**心跳探测一次节点健康，三态流转：

```
OFF ──切换远程──▶ REMOTE ──连续 2 次探测失败──▶ DEGRADED
                    ▲                             │
                    └──连续 3 次成功──恢复─────────┘
                                   （恢复后再稳定 300s，才卸载本地模型）
```

| 参数 | 值 | 含义 |
|------|-----|------|
| 心跳间隔 | 5s | 探测节奏，日志独立成文件不混主日志 |
| 降级阈值 | 连续 2 次失败 | 触发降级，立刻后台预热本地三模型 |
| 恢复阈值 | 连续 3 次成功 | 才敢相信节点真的回来了 |
| 卸载延迟 | 300s 稳定期 | 恢复后本地模型再扛 5 分钟，确认稳定才卸载 |

几个细节值得展开：

- **请求级 fallback**：降级判定靠心跳，但心跳周期内的在途请求也会失败——没关系，单个请求失败时自动改走本地（本地懒加载阻塞式完成，不报错），同时把失败反馈给状态机加速降级判定。**上层永远看不到"远程挂了"这个异常，只看到结果稍慢了一点。**
- **300 秒防抖**：家庭网络抖两下很常见。没有这个窗口，节点每次闪断都会引发"本地加载 → 卸载 → 再加载"的资源颠簸。宁可多留 5 分钟内存，不折腾。
- **启动跳过本地预加载**：如果配置了远程且节点健康，主控启动时干脆不加载本地模型——避免"每次重启都白白加载、几分钟后又卸载"的浪费。
- **版本指纹校验**：切换远程时对比两侧模型指纹（repo + snapshot 哈希）——不一致会黄条警告但不阻断（模型能跑，结果可能有细微差异，知情即可）。

**一句话：远程节点对主控来说是一个"最好在场、不在场也行"的可选项，而不是单点依赖。**

## 形态二：走出局域网——P2P 打洞直连 + 中继兜底

局域网直连上线后，真正的考验来了：**Mac Mini 在家庭宽带后面（CGNAT，运营商级 NAT，没有公网 IPv4）**。当我人在外面、MacBook 不在家里路由器下时，HTTP 直连根本摸不到 Mac Mini。这也是绝大多数"用闲置家用机器"场景的共性困境。

### 为什么不直接用现成的内网穿透

| 方案 | 问题 |
|------|------|
| 端口映射到公网 | CGNAT 下不可行；就算可行，把推理服务暴露公网 = 攻击面 |
| frp / nps 类中继 | 流量全程过 VPS；默认明文，要自己叠 TLS；VPS 能看到全部内容 |
| Tailscale 类 overlay | 很优秀，但控制面在第三方（或需自建 headscale）；手机端要装系统级 VPN 客户端；无法以"库"的形式嵌进阅读 App；故障面无法收敛进我自己的降级链路 |

最后一条是本质原因：在我的架构里，**远程链路的任何失败都必须坍缩成同一个异常**（`RemoteUnavailable`），才能喂给上一节的状态机触发降级。传输层必须是自己的代码，才能保证这一点。于是自研了一套三角色协议（规范全文 210 行，含测试向量，三端实现以它为唯一权威）：

```
 手机(Legado+remote-link SDK) ──┐
                               ├─ 打洞直连 UDP（常态，VPS 零流量）
 MacBook 控制台 backend ────────┤      ▲ 信令 / 打洞协调 / 中继兜底
                               ▼      │
                           relayd（VPS，2C/1G 小鸡即可）
                               ▲      │
 MacMini backend(同款代码) ─────┘──────┘（gateway 节点角色）
```

| 角色 | 位置 | 职责 |
|------|------|------|
| relayd | 一台便宜 VPS | 信令中枢 + STUN + 打洞协调 + 中继兜底，内存占用 60-80MB |
| gateway | Mac Mini（backend 进程内） | 向 relayd 注册；应答打洞；接受会话；转发请求到本机推理 API |
| client | MacBook backend / 手机 SDK | 发起打洞；建立会话；发送推理请求 |

### 打洞：常态路径，流量端到端

流程四步，全部自动：

1. client 向 relayd 查询节点（`lookup`），relayd 生成一次性会话 ID，把客户端公网端点下发给 gateway；
2. 双方对着彼此的公网端点互射 3 个打洞包（间隔 100ms）——包带 HMAC(PSK) 认证，无会话状态下也能识别"这是自己人"且防伪造；
3. 任意一方收到对端打洞包即洞通，在该 UDP 四元组上完成端到端加密握手，之后的流量**直接在两台设备之间流动，VPS 零参与**；
4. 1.5 秒没打通？立刻降级走中继兜底，**功能不受影响**；中继期间后台低频重试打洞，一旦成功，新请求自动切回直连。

这里值得把"被远程连接"的端口问题说透，因为它容易被误读成两个极端。先说事实：**打洞成功后，节点的端口确实经 NAT 映射到了公网**——而且家用 NAT 多为 Endpoint-Independent 映射，任何知道这个公网端点的主机都可以往它发包。但这不等于"暴露了一个服务"，安全边界在应用层，不在 NAT 层：

- **这个端口不是配置出来的，是打出来的**：节点没有公网地址（CGNAT 后照常工作），路由器上也没有任何手工配置的映射规则——映射是节点的出站流量（信令注册、STUN 探测、打洞包）在 NAT 上自动撞出来的，随会话生灭：会话空闲 60 秒即关闭，STUN 每 60 秒刷新一次映射。
- **认证前，节点对外界是"死"的**：打洞包必须带 HMAC(PSK) 签名，会话必须通过 Noise NNpsk2 握手；未通过认证的包被静默丢弃，一个响应字节都不回。从公网扫描这个端点，看到的只是一个毫无响应的地址——端口在，服务对陌生人不存在。

传统"暴露端口"是开一个静态监听、被动接受任意来源敲门、靠服务自身鉴权扛住全世界；这里的端口是动态的、临时的、扫描无响应的。至于中继兜底路径，client 和 gateway 同样是各自主动出站连接 relayd，由 relayd 把两条连接配对成管道——整套系统唯一固定在公网监听的端口是 relayd 的 41000，它不在节点上，且只见密文。

NAT 映射会过期——gateway 每 60 秒经 STUN 刷新一次端口映射，前缀变化后直连短暂失效、中继兜底、随后自动恢复。

### 中继兜底：VPS 只见密文

中继兜底的关键设计是**relayd 是一个纯字节管道**：中继数据连接建立后，relayd 对流经的字节**完全不解析**，只做双向转发。端到端加密在 client 和 gateway 之间建立，密钥由双方协商——**VPS 上看不到任何明文，连"这是哪个业务请求"都不知道**。

配对用一次性凭证（sid，16 字节随机）：配对成功即失效，错误 sid 直接断开，30 秒未配对超时清理。加上准入封禁（同 IP 5 分钟内握手失败 10 次 → 封 10 分钟），relayd 在公网上是一个相当无聊的目标：没有账号体系、没有明文、没有可枚举的资源。

### 最重要的一条设计：传输层承载 HTTP 语义，而不是重新发明业务协议

三端约定只传输两种消息：`api.req`（方法/路径/请求体）和 `api.resp`（状态码/响应体）。gateway 收到后原样转发给本机 backend 的 HTTP API。

这条决策的收益是指数级的：**主控侧的远程客户端一行代码不用改**——向量化、重排序、OCR、健康探测、节点配置、更新重启……所有现有和未来的 API 自动获得 P2P 传输能力。传输层与业务层彻底解耦，后文手机 TTS 能"顺手"接进来，靠的也是它。

对应的用户交互也收敛成一个动作：控制台远程页的「切换远程」按钮悬浮出两个选项——**切换 P2P 连接**（免 URL，PSK/节点 ID 等四项配置齐备即可）或**切换远程链接**（HTTP 直连，局域网形态）；再点当前模式即关闭。管道选择是一个 fail-closed 的枚举（`p2p` / `http`），配置缺失时哪个管道都不会开。

## 安全账本

把一台家用机器变成"可以被异地访问的推理服务"，安全设计必须摊开来讲：

- **全链路 Noise NNpsk2**（X25519 + ChaCha20-Poly1305 + SHA-256）：PSK 认证（预共享密钥 32 字节，部署时自动生成）+ 前向保密（会话密钥仅由临时密钥派生，连接结束即销毁）。无域名、无证书、无 CA——PSK 模式对私有部署是刚刚好的复杂度。
- **三种独立加密会话**：信令连接、直连数据会话、中继数据会话的密钥互不相同，互不牵连。
- **防重放**：每方向维护帧计数器做 nonce——TCP 上隐式携带（字节流严格有序，乱序即断连），UDP 上显式携带（容忍乱序丢失，但重复计数器一律丢弃并设水位剪枝）。这套设计在实现中还揪出过一个"剪枝后重放绕过"的边界 case，加了专项回归测试。
- **打洞包 HMAC 认证**：打洞阶段还没有会话加密，包的真实性由 HMAC(PSK) 保证，伪造包直接丢弃。
- **UDP 分片逐片加密**：大消息（OCR 图片、TTS 音频）拆分片传输，每个分片独立加密为一个 UDP 帧——分片头不泄露消息结构。
- **relayd 准入封禁**：见上文，公网扫描者的握手失败会快速触发封禁。
- **手机侧网关仅监听 127.0.0.1**：阅读 App 内嵌的本地网关不暴露给局域网。

## 自愈：任何一端重启，都不用管

分布式系统的高可用不在"不断"，在"断了能自己爬起来"。这套链路对三种故障都有预案，**双侧零人工**：

| 故障 | 自愈机制 |
|------|---------|
| VPS 重启 | relayd 由 systemd 管理（开机自启 + 崩溃自动拉起） |
| 节点断线/重启 | gateway 感知信令断开后指数退避自动重连（1s → 2s → … → 30s 封顶），重连后重新注册并刷新 STUN 映射 |
| 客户端侧 | 下次请求时自动重建路径（打洞或中继） |

对主控来说，哪怕整条链路全断，兜底就是开头讲的状态机：降级本地、节点回来再切回远程——**推理服务永远可用，区别只是跑在哪台机器上。**

## 白送的副产品：手机朗读

传输层与业务解耦之后，新业务的接入成本低得感人。第二个跑在这条加密隧道上的业务是 **TTS（文本转语音）**：节点上跑一个轻量 TTS 服务（kokoro-onnx，懒加载 + LRU 缓存，同文本二次合成 <50ms），手机上的开源阅读 App Legado 通过内嵌的 remote-link SDK 接入——SDK 在手机本地起一个 `127.0.0.1` 的 HTTP 网关，Legado 的 HTTP-TTS 引擎配一个 URL 即可：

```
http://127.0.0.1:18888/tts?text={{speakText}}&speed={{speakSpeed}}
```

效果：**手机在任何网络下读小说，语音合成发生在几千公里外的 Mac Mini 上，流量端到端加密，VPS 只见密文；打洞成功时，连 VPS 都不经手一个字节。** 对阅读 App 来说，它只是在调一个本地 URL，P2P、加密、打洞、中继兜底全部被 SDK 吞掉了。

这也是"传输承载 HTTP 语义"决策的又一次兑现：TTS 是一个全新的业务，三端协议一行没改。

## 部署速览与成本

三端部署，全部一等入口：

```bash
# VPS（一次性，自动生成 PSK 并打印；重复部署沿用；支持 --ssh-port/--dry-run/--restart）
./deploy-relayd.sh <VPS_IP>

# 节点机（Mac Mini 等；全自动：venv → 依赖 → 配置 → 模型下载 → 独立会话启动）
./start-remote-node.sh

# 主控（MacBook）：控制台远程页 → 填 RELAY_HOST / PSK / 节点 ID → 「切换 P2P 连接」
# 手机（Legado）：RemoteLink 设置页录入同样三项 → 新建 HTTP-TTS 引擎
```

| 成本项 | 数值 |
|--------|------|
| VPS | 2 核 1G 的小鸡即可（relayd 常驻 60-80MB 内存；只放行 TCP+UDP 41000 一个端口） |
| 常态流量 | 打洞成功后端到端，VPS 零流量；中继兜底才有流量过 VPS |
| 节点机 | 能跑三个模型即可（16GB 的 Mac Mini 富余） |
| 主控收益 | 远程托管期间释放约 5-6GB 内存 |

我的实际部署：搬瓦工 2C/1G 的 VPS + 家里的 Mac Mini。STUN 实测 5/5 健康（NAT 类型为 Endpoint-Independent，打洞成功率高）；家里 NAT 类型差的读者也不必担心，中继兜底期间功能完整，只是延迟以实测为准（改善NAT 类型的一个思路：光猫改桥接、路由器拨号）。

## 收尾

把这套东西串起来看，它回答了开头的三笔账：

- **内存账**：三模型搬去节点，主控释放 5-6GB；节点挂了自动降级回本地，永远可用；
- **成本账**：VPS 只承担信令和兜底中继，1G 小鸡绰绰有余；常态推理流量端到端，不过 VPS；
- **安全账**：节点藏在家用 NAT 后即可工作（异地依赖的那台 VPS 只做信令与兜底中继），通信端口是打洞撞出的临时 NAT 映射，未认证流量静默丢弃（公网扫描无响应）；中继只见密文；全链路 Noise 加密，PSK 准入 + 封禁；

而它真正的设计骨架只有两句话：**传输层承载 HTTP 语义，业务与管道解耦；一切失败坍缩为同一个异常，喂给状态机统一降级。** 前者让手机 TTS 这样的新业务"白送"，后者让远方的节点成为一个"最好在场、不在场也行"的优雅可选项——基础设施做到了这个份上，上层的分析 Agent 才能毫无心智负担地享受它。
