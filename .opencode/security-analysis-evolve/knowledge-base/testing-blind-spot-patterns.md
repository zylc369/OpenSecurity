# 测试盲区模式清单（写测试前自检）

> 自包含: 不依赖其他文档即可理解。适用于任何 fake/mock 测试体系。
> 核心命题: **测试全绿 ≠ 被测链路可用**。每个 fake 都可能把某层"项目胶水代码"
> 短路——胶水层的引用错误只有真调用能发现。

---

## 使用场景

写新测试 / 改造测试为 fake 形态 / 回归"为什么测试全绿但生产炸了"时，
逐条对照本清单检查测试设计是否留下盲区。

## 模式 A: patch 粒度作弊——替换了被测方法本身

**什么场景**: 测试想控制某个行为，把**承载该行为的方法**整体替换成 lambda。
**怎么识别**: patch 的目标是"要验证的逻辑"本身（而非它的协作者）。
自问一句: *被 patch 的方法里如果藏着 bug，我的测试能发现吗？* 不能 = patch 错层。
**怎么防**: 只替换协作者（依赖注入点、外部库、更外层服务），被测方法保持原样执行。
合法形态: `patch _model_inference 返回桩`（协作者）/ `psutil.virtual_memory = fake`（外部库）。
作弊形态: `patch _warm_local = lambda: ...`（被测逻辑本身）。

## 模式 B: 运行时才解析的名称引用，无静态防线

**什么场景**: 函数体内引用 `self`（在 @staticmethod 里）或引用不存在的
模块级/类级名称（`SOME_CONST`、`ClassName.method` 改签名后消费方未同步）。
import 不报错、单测没覆盖到那条调用路径 → 生产首次调用才炸 NameError。
**怎么识别**: grep/AST 扫描两类形态: ① `@staticmethod` 体内引用 `self`
（嵌套函数参数含 self 的子树除外）; ② 函数体内的大写裸名在模块顶层与
函数局部均无绑定。
**怎么防**: 把 AST 契约扫描纳入回归（每次全量跑自动执行）。
低成本高收益: 扫描零外部依赖、秒级、一次封死整类缺陷。
类型检查器（pyright/mypy）可抓"类构造在布尔上下文恒真"等语义型同款。

## 模式 C: 入口点（HTTP 端点/MCP 工具/IPC 命令）没有全枚举兜底

**什么场景**: 端点级测试"改哪测哪"——新增端点或改路由文件时，
没有机制保证每个入口至少被真实调用过一次。
**怎么识别**: 对照入口注册清单（如 `app.routes`）与测试覆盖清单，
未被任何测试请求过的入口 = 盲区。
**怎么防**: 全枚举冒烟——遍历注册表逐个请求，断言非 5xx。
一个用例覆盖现在和未来所有入口（新端点自动纳入）;
5xx 断言恰好抓 NameError/ImportError 级（400/404 是校验层正常工作，合法）。

**变体——同一功能多种入口形态**: 入口不只有 HTTP 一种形态。
`detect_py_deps` 的检测能力同时暴露为 HTTP 路由（`/api/deps`）和
CLI 子命令（`detect_py_deps.py scan`），HTTP 冒烟全部通过时 CLI 入口
仍可能是坏的（OOP 重构把函数收进类，CLI `_main()` 里的裸调用漏改，
NameError → exit 1 → 消费方 fail-closed 把链路故障误报为"依赖缺失"）。
入口形态清单: HTTP 路由 / MCP 工具 / IPC 命令 / CLI 子命令（`__main__`）/ 定时任务。
**怎么防（双静态+动态）**: ① 契约扫描覆盖 CLI 入口函数（`main`/`_main`）
体内裸函数调用的可解析性（模块 def/class/import 绑定 + 内置之外即违规）;
② 为每个**真实存在的消费链**做一次消费行为测试——插件自举检查走 CLI
就测 CLI（venv python 直跑断言 exit 0），不要只测自己熟悉的 HTTP 形态。
冒烟遍历 `app.routes` 前先问: 这个代码还有别的入口注册表吗（argparse
子命令表、MCP `@mcp.tool` 清单、IPC handler 表）？逐一对照。

## 模式 D: 配置的值测试 ≠ 消费行为测试

**什么场景**: 测了配置 getter 的返回语义（env=0 → False），
没测消费方行为（该值如何改变 server 启动分支）。getter 对了、
消费处写成 `if ConfigManager():`（构造恒真）→ 值测试照样全绿。
**怎么识别**: 列出关键配置开关（dev/resident/remote 等），
逐个检查: 是否存在断言"值 X → 消费方行为 Y"的用例。
**怎么防**: 每个关键开关配一条消费侧行为断言
（如 dev=0 → create_app 不调 ensure_vite_dev; 拦截点设在协作者方法，
不真 spawn 进程）。

## 模式 E: 生成物内容零覆盖

**什么场景**: 代码生成配置文件（plist/compose/模板/env 片段），
只测"生成不报错"，不测"内容含关键键"。生成物是纯函数输出——
最便宜可测的对象，恰恰最常被跳过。
**怎么识别**: grep 生成函数（返回 str/XML/dict 的 `_content`/`_render`/
`_template` 类），检查是否有内容断言（解析产物断言键存在）。
**怎么防**: 生成 → 解析 → 断言关键键。不需要真实执行下游
（launchd 不会真加载，只验证生成的 XML 含必需键）。

## 模式 F: 组合矩阵只测对角线

**什么场景**: 平台分支（mlx/ollama、posix/win）× 开关（远程开/关）
= 2×2 组合，只测了对角线两格。调用形态（类访问/实例访问）×
API 定义（缺 @staticmethod）同理——所有调用方恰好都用类访问时，
实例访问形态的缺陷不可见。
**怎么识别**: 对含分支 × 开关的公开 API 列组合矩阵，标已测格;
存在整行/整列未覆盖 = 盲区。
**怎么防**: 至少每行每列各覆盖一次（不必全积）;
staticmethod 装饰器缺失可用 AST 扫描兜底（首参非 self 且无装饰器）。

## 模式 G: 循环体逐段故障点——只包了主段的 try

**什么场景**: 后台循环（心跳/轮询/reaper）里，主逻辑段有异常兜底，
但循环控制段（sleep 参数求值、配置重读）裸奔——瞬时异常穿透循环，
整个后台任务永久死亡且无日志。
**怎么识别**: 检查每个 `while True` 循环: try 覆盖了哪些段？
循环内每一次外部交互（读配置/sleep 参数/队列操作）都是独立故障点。
**怎么防**: 循环内逐段 try + 日志（异常吞掉继续下一轮）;
CancelledError 必须 re-raise（生命周期信号非错误，勿吞勿打日志刷屏）。

## 模式 H: 验证目标文件含不可见字节——grep/git diff 静默失效

**什么场景**: 对存量文本文件（.md/配置/源码）做 grep 断言或 git diff
审计时，文件含 NUL/控制字节/零宽字符（源材料提取、字节级粘贴可带入）。
**怎么识别（三联征，出现任一即停）**: ①`grep -c <词>` 对明知存在的词
返回 0（BSD grep 遇 NUL 整文件拒搜，NUL 之前的行也搜不到）;
②`file <f>` 报 `data` 而非 text; ③`git diff` 只输出 `Binary files differ`
（行级 diff 丢失，审计链路断裂）。
**怎么防**:
- 前置: 对即将 grep 断言的文件先 `file` 一眼，报 data 即扫描——
  `$PYTHON_CMD -c "d=open('<f>','rb').read(); print('NUL',d.count(b'\x00'),'CTRL',sum(1 for b in d if b<0x20 and b not in (9,10,13)))"`
- 修复纪律: 消除不可见字节前必须 `git show <commit>:<path>` 做字节级
  考古——Read 工具不显示 NUL，按"显示出来的样子"重打原文会篡改语义
  （不可见字节本身可能是知识内容，如以字面 `\x00` 表达协议终止符;
  正确修法是改为可见转义形态，不是删除）。
- .md 检查惯例: 人工读之外加字节扫描——grep 对含 NUL 文件静默假阴性、
  人眼/LLM 对不可见字节天然失明，两条既有防线都挡不住它。

## 模式 I: 自我声称的子声称不同构——"已修复/全绿"里藏未验证项

**什么场景**: 汇报"已修复 X / 测试全绿 / 已验证 Y"时。一个复合声称由
多个子声称组成（修复 = 机制正确 + 语义保留 + 范围完整; 全绿 = 断言有效
+ 断言通过），声称者往往只验证了其中一部分就把整体标为完成。
**怎么识别**: 把声称拆成子声称清单，逐条问"这一条有独立证据吗"。
两类高危形态: ①断言含恒真兜底（`cond or x is not None`）——它的 PASS
不携带任何信息; ②"保留了原语义"类语义声称没有对照源（未做原文比对
就打 ✓）。
**怎么防**: 汇报完成度按子声称列证据，答不出对照源的子声称如实标
"未验证"; 声称"修复 N 处"后逐一核对是否全部落盘（说了没做是执行遗漏，
与做错同等危险）; 弱断言要么修强要么删掉，不留在绿色数字里充数。

## 模式 J: Python 类体绑定 + 方法内裸名——类命名空间不在查找链

**什么场景**: 类体内直接绑定 `logger = logging.getLogger(...)` 或嵌套
`def _helper()`，然后同类方法内用裸名访问（`logger.warning(...)` 或
`target=_worker`）。Python 的方法名字查找链是 local → enclosing →
global → builtins，**类命名空间不在其中**——裸名运行时 NameError。
**为什么测试抓不到**: 高发于异常处理器（`except: logger.warning(...)`）
——正常路径不执行; Thread `target=_worker` 只在下载/后台路径触发;
且异常处理器内的 NameError 会**覆盖原异常**（火上浇油）。
**怎么检查**: `pyright`（`reportUndefinedVariable`）静态全抓; 人工 grep
类体缩进的 `logger =` / `def _` 绑定与方法内裸名引用的位置关系。
**怎么防**: 模块级统一定义 logger（`logger = logging.getLogger(__name__)`
放 import 区后），类内一律裸名引用; 同类 staticmethod 调用必须
`ClassName._helper(...)` 限定; 引入 pyrightconfig.json 并保持
UndefinedVariable = 0 作为回归线。

**变体: try 内 import + except 引用同模块属性**——`try: import httpx`
失败时 except 元组 `(httpx.HTTPError, ...)` 求值即 NameError（import
失败不绑定名字，except 匹配前先求值类型表达式），被吞的降级路径
自己炸掉。**pyright/mypy 对此保守**（流分析把 import 当无条件绑定，
抓不到）; PyCharm 的流分析建模了 import 失败场景，能报
"可能在赋值前引用"。防御: import 单独一层 try/except ImportError
降级返回，使用 import 的代码放第二层 try——except 引用时名字必已
绑定，结构上消除 NameError。

## 模式 K: E2E 测试与生产共享端口/sock——"生产恰好死"才通过

**什么场景**: 测试用例起真实服务实例（E2E），但端口与 sock 路径写死
与生产相同。生产存活时测试实例 bind 失败/请求打到生产 → ReadTimeout
一片红; 生产恰好死亡时全绿——**绿是环境巧合不是质量证明**。
**怎么识别**: 测试起服务后 `ps eww <pid>` 看 bind 路径是否含沙箱
前缀; 或直接问"生产活着的机器上跑这个测试会怎样"。
**怎么防**: E2E 用例必须显式设置沙箱根，且**只读测试专用变量**——
沙箱值绝不能从生产运行变量取（"生产变量存在时沿用"的 default 写法
是静默旁路：agent/生产 shell 里该变量有值时，沙箱设置被整体旁路）。
设置后加**防假隔离一票否决**（解析值等于生产默认路径即拒绝运行），
再断言四要素落沙箱: home / sock / 端口段 / 配置文件。
**易漏点**: 挂在"不可沙箱化的根"下的文件（如代码根目录下的 .ai_env
配置——代码本体不能复制进沙箱）不随沙箱根走——需独立重定向（env
覆盖优先 + 缺省回落原路径）并在测试启动时复制副本; 写-还原式配置
用例必须落副本而非真实文件（中途被杀时还原不执行，必然残留）。

## 模式 L: 平台门控分支 × 资源对象语义——类型全绿/本地全绿 ≠ 真机正确

**什么场景**: 改动位于平台门控分支内（`if os.name == "nt"` /
`sys.platform != "win32"` 才执行），且涉及资源对象的"值转换"（用
int()/str()/bytes() 包裹句柄、文件、socket、连接、锁等对象）。
高发于"消除静态告警"的修复——为让实参类型匹配 stub 注解而把对象
转换为裸值。
**根因机制**: 资源对象的**值等价 ≠ 语义等价**。示例: pywin32 句柄对象
（PyHANDLE）是 int 子类，`int(handle)` 值恒等，但对象引用被丢弃后其
析构自动 CloseHandle 提前触发，句柄号被系统复用 → 后续操作作用于
错误对象（症状可为 WinError 10038 "not a socket" / ERROR_INVALID_HANDLE
/ 静默串扰）。既有防线对该类改动全部无信息: 类型检查不建模对象生命
周期与析构副作用（`int(资源对象)` 在类型学上合法）; 本地测试跑不到
门控分支（对象在本地平台不存在，无法模拟）。
**怎么识别**: ① diff 审计时对"平台门控分支内的改动"单独标记;
② 对每处"消静态告警"的修复先分类: 类型层修复（cast/ignore/注解——
运行时零改动）还是运行时层修复（转换/重构——改变行为）;
③ 凡把对象包进 int()/str()/bytes() 的调用点，查该对象是否带
`__del__`/close/GC 副作用。
**怎么防**:
1. 修复分层: 消静态告警默认留在类型层（cast/ignore，运行时零改动）;
   跨到运行时层的动作须独立论证——**类型描述现实，不得为满足类型声明
   改造现实**; 资源对象生命周期（析构/close 副作用）列为必查项。
2. 资源对象红线: 句柄/文件/socket/连接/锁禁止用值转换消类型告警，
   一律 cast/ignore。
3. 验证路由: 本地不可执行分支的改动 → 最保守修法 + 验收记录单列
   "待真机（CI）裁决"，不得混入"全绿"总述; 能模拟化的先做模拟单测
   （如 patch(os.name) 模拟 nt 分支）并与 CI 断言配对。
4. 结论口径: 平台盲区改动的"通过"必须带覆盖边界声明（哪些分支被执行、
   哪些没有）——整体绿数字不能代替分支级覆盖声明。
5. 防御分支的失败语义: 为类型收窄引入的 None/异常分支，必须同时回答
   "真发生时怎么办"——跳过会导致挂死/数据丢失的（信号/分发类不可替代
   动作）→ fail-loud（raise）; 存在无损恢复动作的 → 自愈兜底（恢复
   优先）; 纯值等价的 → 静默收窄即可。禁止只为收窄而写分支、不定语义。

## 排查指引（"全绿但生产炸"时）

1. 炸点在哪个入口/链路 → 沿链路找 fake 注入点，确认炸的层是否被 fake 短路（模式 A/C）
2. NameError 型 → 检查是否为静态可抓形态（模式 B），补进契约扫描
3. 配置相关 → 区分值语义与消费行为（模式 D）
4. 后台任务静默死亡 → 循环逐段检查 try 覆盖（模式 G）
5. grep 断言与肉眼/Read 结果矛盾 → 先查文件不可见字节（模式 H），再怀疑逻辑
6. "当时明明说修好了" → 拆子声称找未验证项与执行遗漏（模式 I）
7. 类型检查与本地测试全绿、但目标平台（另一 OS）运行异常 → 查平台门控
   分支内的"值转换"改动与资源对象生命周期（模式 L）
