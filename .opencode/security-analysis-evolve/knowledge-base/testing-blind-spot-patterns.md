# 测试盲区模式清单（写测试前自检）

> 自包含: 不依赖其他文档即可理解。适用于任何 fake/mock 测试体系。
> 核心命题: **测试全绿 ≠ 被测链路可用**。每个 fake 都可能把某层"项目胶水代码"
> 短路——胶水层的引用错误只有真调用能发现。

---

## 使用场景

写新测试 / 改造测试为 fake 形态 / 回归"为什么测试全绿但生产炸了"时，
逐条对照本清单检查测试设计是否留下盲区。

## 模式 A: patch 粒度作弊——替换了被测方法本身

**什么场景**: 测试想控制某个行为，把**承载该行为的方法**整体替换成 lambda。
**怎么识别**: patch 的目标是"本次要验证的逻辑"本身（而非它的协作者）。
自问一句: *被 patch 的方法里如果藏着 bug，我的测试能发现吗？* 不能 = patch 错层。
**怎么防**: 只替换协作者（依赖注入点、外部库、更外层服务），被测方法保持原样执行。
合法形态: `patch _model_inference 返回桩`（协作者）/ `psutil.virtual_memory = fake`（外部库）。
作弊形态: `patch _warm_local = lambda: ...`（被测逻辑本身）。

## 模式 B: 运行时才解析的名称引用，无静态防线

**什么场景**: 函数体内引用 `self`（在 @staticmethod 里）或引用不存在的
模块级/类级名称（`SOME_CONST`、`ClassName.method` 改签名后消费方未同步）。
import 不报错、单测没覆盖到那条调用路径 → 生产首次调用才炸 NameError。
**怎么识别**: grep/AST 扫描两类形态: ① `@staticmethod` 体内引用 `self`
（嵌套函数参数含 self 的子树除外）; ② 函数体内的大写裸名在模块顶层与
函数局部均无绑定。
**怎么防**: 把 AST 契约扫描纳入回归（每次全量跑自动执行）。
低成本高收益: 扫描零外部依赖、秒级、一次封死整类缺陷。
类型检查器（pyright/mypy）可抓"类构造在布尔上下文恒真"等语义型同款。

## 模式 C: 入口点（HTTP 端点/MCP 工具/IPC 命令）没有全枚举兜底

**什么场景**: 端点级测试"改哪测哪"——新增端点或改路由文件时，
没有机制保证每个入口至少被真实调用过一次。
**怎么识别**: 对照入口注册清单（如 `app.routes`）与测试覆盖清单，
未被任何测试请求过的入口 = 盲区。
**怎么防**: 全枚举冒烟——遍历注册表逐个请求，断言非 5xx。
一个用例覆盖现在和未来所有入口（新端点自动纳入）;
5xx 断言恰好抓 NameError/ImportError 级（400/404 是校验层正常工作，合法）。

**变体——同一功能多种入口形态**: 入口不只有 HTTP 一种形态。
`detect_py_deps` 的检测能力同时暴露为 HTTP 路由（`/api/deps`）和
CLI 子命令（`detect_py_deps.py scan`），HTTP 冒烟全部通过时 CLI 入口
仍可能是坏的（OOP 重构把函数收进类，CLI `_main()` 里的裸调用漏改，
NameError → exit 1 → 消费方 fail-closed 把链路故障误报为"依赖缺失"）。
入口形态清单: HTTP 路由 / MCP 工具 / IPC 命令 / CLI 子命令（`__main__`）/ 定时任务。
**怎么防（双静态+动态）**: ① 契约扫描覆盖 CLI 入口函数（`main`/`_main`）
体内裸函数调用的可解析性（模块 def/class/import 绑定 + 内置之外即违规）;
② 为每个**真实存在的消费链**做一次消费行为测试——插件自举检查走 CLI
就测 CLI（venv python 直跑断言 exit 0），不要只测自己熟悉的 HTTP 形态。
冒烟遍历 `app.routes` 前先问: 这个代码还有别的入口注册表吗（argparse
子命令表、MCP `@mcp.tool` 清单、IPC handler 表）？逐一对照。

## 模式 D: 配置的值测试 ≠ 消费行为测试

**什么场景**: 测了配置 getter 的返回语义（env=0 → False），
没测消费方行为（该值如何改变 server 启动分支）。getter 对了、
消费处写成 `if ConfigManager():`（构造恒真）→ 值测试照样全绿。
**怎么识别**: 列出关键配置开关（dev/resident/remote 等），
逐个检查: 是否存在断言"值 X → 消费方行为 Y"的用例。
**怎么防**: 每个关键开关配一条消费侧行为断言
（如 dev=0 → create_app 不调 ensure_vite_dev; 拦截点设在协作者方法，
不真 spawn 进程）。

## 模式 E: 生成物内容零覆盖

**什么场景**: 代码生成配置文件（plist/compose/模板/env 片段），
只测"生成不报错"，不测"内容含关键键"。生成物是纯函数输出——
最便宜可测的对象，恰恰最常被跳过。
**怎么识别**: grep 生成函数（返回 str/XML/dict 的 `_content`/`_render`/
`_template` 类），检查是否有内容断言（解析产物断言键存在）。
**怎么防**: 生成 → 解析 → 断言关键键。不需要真实执行下游
（launchd 不会真加载，只验证生成的 XML 含必需键）。

## 模式 F: 组合矩阵只测对角线

**什么场景**: 平台分支（mlx/ollama、posix/win）× 开关（远程开/关）
= 2×2 组合，只测了对角线两格。调用形态（类访问/实例访问）×
API 定义（缺 @staticmethod）同理——所有调用方恰好都用类访问时，
实例访问形态的缺陷不可见。
**怎么识别**: 对含分支 × 开关的公开 API 列组合矩阵，标已测格;
存在整行/整列未覆盖 = 盲区。
**怎么防**: 至少每行每列各覆盖一次（不必全积）;
staticmethod 装饰器缺失可用 AST 扫描兜底（首参非 self 且无装饰器）。

## 模式 G: 循环体逐段故障点——只包了主段的 try

**什么场景**: 后台循环（心跳/轮询/reaper）里，主逻辑段有异常兜底，
但循环控制段（sleep 参数求值、配置重读）裸奔——瞬时异常穿透循环，
整个后台任务永久死亡且无日志。
**怎么识别**: 检查每个 `while True` 循环: try 覆盖了哪些段？
循环内每一次外部交互（读配置/sleep 参数/队列操作）都是独立故障点。
**怎么防**: 循环内逐段 try + 日志（异常吞掉继续下一轮）;
CancelledError 必须 re-raise（生命周期信号非错误，勿吞勿打日志刷屏）。

## 排查指引（"全绿但生产炸"时）

1. 炸点在哪个入口/链路 → 沿链路找 fake 注入点，确认炸的层是否被 fake 短路（模式 A/C）
2. NameError 型 → 检查是否为静态可抓形态（模式 B），补进契约扫描
3. 配置相关 → 区分值语义与消费行为（模式 D）
4. 后台任务静默死亡 → 循环逐段检查 try 覆盖（模式 G）
