# 复盘方法论 — 写《复盘报告》与提炼进化候选的方法

> 适用场景：被要求复盘一次任务或一段使用过程、输出《复盘报告》、提炼进化候选清单时读本文件。
> 触发形态：收到"复盘/反思/总结教训"指令，或准备把历史失败模式写成改进项前。

---

## 1. 三层因果（逐层写，不跳层）

按三层组织复盘叙事，每层回答一个问题：

| 层 | 回答的问题 | 写什么 | 常见错误 |
|---|---|---|---|
| 表象层 | 发生了什么 | 只写可观察事实与数据：对话轮次、耗时、失败次数、同方向连续失败数、卡住时长、工具调用统计 | 把判断混进事实（"表现很差"） |
| 决策层 | 当时为什么这样选 | 每个关键决策点写：当时的可选集、选了哪条、依据什么信号、忽略了什么信号 | 用事后视角评价（"本应该…"） |
| 结构层 | 什么缺失让该决策成为必然 | 指向具体缺失项：规则/知识/工具/流程，能落到文件或条目 | 停在"不够谨慎/不够聪明"（无落点） |

判据：每条改进候选必须能指到结构层缺口；指不到，说明还停在表象层或决策层，继续挖。

## 2. 反事实写法

对每个关键决策点写一句"如果当时做 X，会怎样"：

- X 必须是当时可执行的选项：当时能查到的知识、能调用的工具、能改的规则
- 正例："如果开工时委派 memorist 检索该方向历史记录，会提前发现已有连续失败记录，可省去重复试错"
- 反例："如果当时更聪明/更冷静"——不可执行的选项是懊悔，不是反事实，不要写进报告
- 多个反事实指向同一处缺失 → 该缺失是高价值改进候选

## 3. 改进项四要素

每条改进项必须同时具备：

1. **少**：一次复盘产出保持克制，列主次，先落地 1-2 条关键项；宁可分多期，不铺开
2. **有主**：落到具体载体——`文件路径 + 章节`或`agent + 规则片段`；"提升警惕"这类无主陈述无效
3. **有期限**：写清先于什么发生（例："下次同类任务开工前"、"下个需求周期"），不写"尽快"
4. **要复查**：写清验证方式与闭环标记——何时检查、用什么命令或步骤确认生效、完成后在哪里标记状态

## 4. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 只列现象不挖结构层 | 复盘变成流水账，无改进产出 | 每条现象追到结构层缺口 |
| 改进项写成愿景 | 无法执行、无法复查 | 落到文件+规则+期限+验证方式 |
| 反事实写成懊悔 | 无行动价值 | 只写当时可执行的替代选项 |
| 否定结论不标未测清单 | 后续把"未验证"当"已确认"复用 | 结论随附证据等级+已验证范围+未测清单 |
| 一次产出过多改进项 | 注意力分散，全部悬空 | 少而准，分批落地 |

## 5. 报告完成检查

- [ ] 三层因果逐层写完，改进候选全部指到结构层
- [ ] 每条反事实的 X 是当时可执行选项
- [ ] 每条改进项四要素齐全（少 / 有主 / 有期限 / 要复查）
- [ ] 结论带证据等级与未测清单，无"永远/不可能"类封闭结论
