# 复盘方法论 — 写《复盘报告》、做机制审计与提炼进化候选的方法

> 适用场景：被要求复盘一次任务或一段使用过程、输出《复盘报告》、提炼进化候选清单时读本文件；做机制贡献审计、评审 prompt / 知识库类提交时同样适用。
> 触发形态：收到"复盘/反思/总结教训"指令，准备把历史失败模式写成改进项前，或被要求核查"某机制在任务中的贡献占比"、评审一次进化提交时。

---

## 1. 三层因果（逐层写，不跳层）

按三层组织复盘叙事，每层回答一个问题：

| 层 | 回答的问题 | 写什么 | 常见错误 |
|---|---|---|---|
| 表象层 | 发生了什么 | 只写可观察事实与数据：对话轮次、耗时、失败次数、同方向连续失败数、卡住时长、工具调用统计 | 把判断混进事实（"表现很差"） |
| 决策层 | 当时为什么这样选 | 每个关键决策点写：当时的可选集、选了哪条、依据什么信号、忽略了什么信号 | 用事后视角评价（"本应该…"） |
| 结构层 | 什么缺失让该决策成为必然 | 指向具体缺失项：规则/知识/工具/流程，能落到文件或条目 | 停在"不够谨慎/不够聪明"（无落点） |

判据：每条改进候选必须能指到结构层缺口；指不到，说明还停在表象层或决策层，继续挖。

## 2. 反事实写法

对每个关键决策点写一句"如果当时做 X，会怎样"：

- X 必须是当时可执行的选项：当时能查到的知识、能调用的工具、能改的规则
- 正例："如果开工时委派 memorist 检索该方向历史记录，会提前发现已有连续失败记录，可省去重复试错"
- 反例："如果当时更聪明/更冷静"——不可执行的选项是懊悔，不是反事实，不要写进报告
- 多个反事实指向同一处缺失 → 该缺失是高价值改进候选

## 3. 改进项四要素

每条改进项必须同时具备：

1. **少**：一次复盘产出保持克制，列主次，先落地 1-2 条关键项；宁可分多期，不铺开
2. **有主**：落到具体载体——`文件路径 + 章节`或`agent + 规则片段`；"提升警惕"这类无主陈述无效
3. **有期限**：写清先于什么发生（例："下次同类任务开工前"、"下个需求周期"），不写"尽快"
4. **要复查**：写清验证方式与闭环标记——何时检查、用什么命令或步骤确认生效、完成后在哪里标记状态

## 4. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 只列现象不挖结构层 | 复盘变成流水账，无改进产出 | 每条现象追到结构层缺口 |
| 改进项写成愿景 | 无法执行、无法复查 | 落到文件+规则+期限+验证方式 |
| 反事实写成懊悔 | 无行动价值 | 只写当时可执行的替代选项 |
| 否定结论不标未测清单 | 后续把"未验证"当"已确认"复用 | 结论随附证据等级+已验证范围+未测清单 |
| 一次产出过多改进项 | 注意力分散，全部悬空 | 少而准，分批落地 |

## 5. 报告完成检查

- [ ] 三层因果逐层写完，改进候选全部指到结构层
- [ ] 每条反事实的 X 是当时可执行选项
- [ ] 每条改进项四要素齐全（少 / 有主 / 有期限 / 要复查）
- [ ] 结论带证据等级与未测清单，无"永远/不可能"类封闭结论

## 6. 审计取证方法

三类审计场景的取证路径：机制贡献归因、提交评审、检索质量复测。

### 6.1 机制贡献审计（三源交叉）

| 源 | 位置 | 取证内容 |
|---|---|---|
| 会话时间线 | 任务目录 `logs/timeline.log`、`logs/plugin.log` | `tool.before/after` 序列——还原每步工具调用、耗时、失败重试，统计各机制实际调用（知识库读取、记忆库检索/写入、子 agent 委派） |
| 记忆库直读 | 记忆库 SQLite（默认 `~/bw-security-analysis/db/knowledge/knowledge.db`） | `answers` 表按时间/关键词查条目与写入记录；`answer_vectors_rowids` 判断条目是否已建向量索引 |
| 配置核对 | `agents/*.md` frontmatter、`agents-rules/` 片段挂载、插件片段展开 | 工具在/不在的原因（permission deny、片段是否挂载）、展开行数复算 |

归因判据：机制"没起作用"先区分**没有**（库中无对应内容）与**错过**（有内容但未检索到 / 未消费）——两者的修复方向不同。

### 6.2 检索质量复测（区分"没有"与"错过"）

用目标技术栈的正确关键词（英文标识符原样保留）重新检索记忆库：命中 → 原调用属检索时机/关键词问题；未命中 → 查存储与向量索引状态。复测委派带记忆库工具的 agent（如 memorist）执行，要求逐字返回 id + question，禁止用其他方式（直查数据库、按 id 反查）代答——否则测的不是检索本身。

### 6.3 prompt / 知识库提交评审清单

- **展开行数复算**：文件行数 − 占位符行数 + 各片段行数（与改动者声称值逐一比对）
- **占位符计数**：`{{buwai-rule:...}}` 逐 agent 计数，展开后零残留
- **残留词扫描**：改动涉及的术语旧词全仓 grep——**"全仓"口径 = `agents/` 全部文件（含子 agent：memorist / searcher / fresh-eyes / knowledge-scout）+ `agents-rules/` + 插件中的引用**，不止被改动的文件
- **索引可达性**：新增知识库文件有索引行指向、索引路径可解析
- **状态行一致性**：需求文档 / progress 的状态与实际落地一致；已完成项的"范围外/待后续"记录勾销

### 6.4 索引触发条件质量判据

触发行写**代码形态 / 可观察形态**，不写主题词（判据见 `$SHARED_DIR/knowledge-base/knowledge-writing-guide.md` §2.5）。命中触发条件即必须读取——修订索引与读取规则时不得设置任何豁免（如"认为已掌握可跳过""只读部分章节"）。触发条件过宽 × 文档体量大时，核对触发是否需细化，而不是放宽读取要求。

## 7. 关联

- 复盘产出的知识要沉淀入库时，按 `$SHARED_DIR/knowledge-base/knowledge-writing-guide.md` 执行
- 复盘识别出的缺失若涉及插件/脚本/规则改动，进入进化流程（需求文档 → 审计 → 实施）
