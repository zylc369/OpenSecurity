# 整库蒸馏方法论

> 给定一个完整素材库（Git 仓库、题目集、离线文档目录），把它全量精读、验证、提炼、沉淀到本体系知识库的六阶段流程。
> 与散篇信源扫描（`knowledge-sourcing-guide.md`）互补: 那是"追新宽度"，本文是"整库榨干深度"。
> 命令入口: `/knowledge-distill`。不依赖主 prompt 上下文即可理解。

---

## 0. 适用判定

- **走本流程**: 素材是一个结构化集合（题目集/CTF 题库、漏洞复现集合、内部报告库），量级通常 ≥10 篇，有既定边界
- **不走本流程**: 单篇/散篇 writeup → 走 `$AGENT_DIR/knowledge-base/knowledge-sourcing-guide.md` 的信源扫描
- 素材含非知识成分（源码、附件）时，蒸馏对象是 writeup/分析文档，源码用于验证而非直接沉淀

---

## 1. 阶段一: 素材获取与盘点

**目标**: 拿到全部素材、摸清结构、确认总量。**禁止在盘点完成前开始精读**（防止结构误判导致重复劳动）。

1. Git 仓库: 克隆到临时区 `$TMPDIR/opencode/<仓库名>`，`--depth 1`; 含 LFS 的仓库先 `GIT_LFS_SKIP_SMUDGE=1` 跳过大文件，需要时按文件单独 smudge。克隆前 `du` 评估体积，>2GB 先看有没有可跳过的二进制目录
2. 结构识别: 找出素材组织约定（每题一个目录？writeup/源码/solve 脚本的相对位置？多语言版本如何对应？）
3. 分类统计: 按方向（binary/mobile/web/crypto/ai-security/forensics/其他）计数列表格
4. **计数交叉验证**: 分项加总 == 文件系统实际目录数。逐目录 ls 核对，防止统计口径错漏
5. 归档规划: 全部源素材归档到 `docs/资料/writeup-sources/<来源名>/<方向>/<题目>/`（写入是产出原始资料，属允许的 docs/ 例外）。归档前后各跑一次文件计数比对。归档名做跨平台扫描: Windows 非法字符 `< > : " / \ | ? *`、保留名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）、尾部空格/点; Linux 仅禁 `/` 与 `\0`

**检查点**: 盘点表（方向 × 数量 × 目录清单）+ 计数验证记录。

## 2. 阶段二: 全量精读与 gap 判定

**目标**: 每篇素材的技术点清单化，与本体系知识库对照出 gap 清单。

1. 按方向分批精读，**单批 ≤10 篇**（上下文保护）; 每篇读主语言版本即可，其他语言版本只在对不上时交叉
2. 每篇列技术点清单: 攻击技术、工具用法、框架行为、环境差异、失败弯路
3. **gap 两维判定**（逐条执行，禁止跳过）:
   - 方向级: 该技术领域在整个知识库无对应文件 → 看目录即可判定
   - 技术点级: 已有文件里该技术未覆盖/覆盖不全/不准确 → **必须读对应知识库文件的实际内容对照判定，禁止只看文件名索引或 grep 关键词就判"已覆盖"**（关键词命中 ≠ 内容覆盖; 反向也成立: 关键词不命中也可能已有等价知识，只是术语不同）
4. 产出 gap 清单，每条标注: gap 类型（方向级/技术点级）、目标落位文件与小节、置信度、预验证级别（Tier 1-4 见下）

**检查点**: gap 清单表格 + 每条已读过哪个知识库文件哪些章节（可复查）。

## 3. 阶段三: 验证分级（Tier 1-4）与降级

**目标**: writeup 不是真理——每条待沉淀知识在写入前按分级验证。

**铁律: writeup 可能有已证伪或想当然的内容**。凡"机制断言"（某 API 返回什么、某指令行为如何）必须对照原题源码/原始响应核实，不接受转述。

| 级别 | 含义 | 适用 |
|------|------|------|
| Tier 1 | 源码级核实: 读 challenge 源码/配置/原始流量，逐条比对 writeup 断言 | **默认必做**，每条知识至少 T1 |
| Tier 2 | 本地仿真: 复制关键约束做最小复现（过滤器正则 fullmatch、payload 编译） | 可仿真的纯逻辑知识 |
| Tier 3 | 完整复跑: solve 脚本/利用链在本地环境全链执行（QEMU、Docker `--platform`、本地服务） | 可获得运行环境的 |
| Tier 4 | 多版本探针: 写可运行探针在多个软件版本上断言（浏览器类多 Chrome 版本） | 行为随版本可能变化的 |

降级规则:
- 外部依赖不可得（如依赖 sage 编译）→ 降级为 solve 脚本静态对照（脚本阶段与 writeup 逐段比对），在 progress 记录降级原因
- 全链复跑不通 → 对**核心断言**写最小独立验证程序（例: 全链 exploit 跑不通时，用最小 C 程序验证那个系统调用的语义），不能整链验证就验证最有价值的断言
- 源码/原始响应均不可得（闭源素材、纯转述 writeup）→ 该条知识标注"仅 writeup 转述核实"降置信度，或放弃沉淀——不允许假装做过 T1
- 复跑环境坑: QEMU 本地 TCG 模式 boot 慢（超时给足 240s+）; Docker amd64 镜像在 Apple Silicon 上须显式 `--platform linux/amd64`; 探测脚本改端口常量无效——探针通常自起 server，要改 goto 目标 URL 做负向测试

**检查点**: 每条 gap 的验证级别 + 验证结果记录进 progress。

## 4. 阶段四: 写入（完整进化流程 Phase 2-5）

**目标**: 蒸馏产出按体系规范落地——这不是轻量沉淀，是带需求文档的正式进化任务。

1. 写需求文档 + progress 到 `$OPENCODE_ROOT/requirements/evolve/`: 需求文档含 gap 落位总表（字段同本文件阶段二第 4 条: gap 类型/目标落位文件与小节/置信度/预验证级别）与 §3.1 分步实施; progress 每步记录验证证据
2. 沉淀前必读 `$SHARED_DIR/knowledge-base/knowledge-writing-guide.md`，全部规范适用（零来源叙事、三问、双键、排版纪律）
3. 归属判定: 通用 → `$SHARED_DIR/knowledge-base/`，方向专属 → 各方向 `$AGENT_DIR/knowledge-base/`，不确定放通用层
4. 文件操作纪律: 新文件预估 >80 行才建; 补章节插在收尾节（决策/注意类）**之前**，编号单调（可用 Nn. 形式如 8a/14a）; 优先 Edit 局部插入而非尾部追加
5. agent prompt 知识库索引表同步加行（触发条件写代码形态/可观察形态，不写主题词）; 加行后做展开行数检查（<450 行; 目标 prompt 存量已超限的，如实记录行数并转瘦身需求承接，不阻塞当前蒸馏任务）
6. 产出可运行探针/脚本时: 自包含（自起依赖服务）; 失败路径符合契约（输出 JSON + 非零 exit，**禁止永久挂起**——事件不触发的分支要有超时兜底）; README 含依赖安装步骤（node_modules 类被 gitignore 的要写明 `npm install`）与判据说明
7. 工程坑（执行时直接命中）:
   - 同一文件多次 Edit 必须跨消息串行，并行必失败
   - oldString 失配时先用 `python repr()` 精确字节比对（不可见字符/全角空格）
   - 长文档（>300 行）禁全量重写，分段 Edit

**检查点**: 需求文档 + progress 就位; prompt 索引行在位且展开行数合规。

## 5. 阶段五: 回归检查清单

**目标**: 全量扫描（不只扫本次新增），防止结构性与规范性缺陷。

1. 叙事词扫描（词边界正则，对本次全部触碰文件）: `\bCTF\b|\bwriteups?\b|比赛|赛事|实测|亲测|复盘|验证过`。**必须带 `\b`**——无词边界时 `reactFiber` 之类标识符子串会对 `ctF` 产生假阳性; 判定残留前逐个人工确认
2. 章节结构: 编号单调无重号（含 Nn 延伸号）、收尾节（决策/注意）仍在文件尾
3. prompt 索引: 新增文件都有索引行、触发条件可命中
4. 交叉引用: `$AGENT_DIR`/`$SHARED_DIR` 变量形式、路径真实存在
5. 归档完整性: 归档文件计数 == 阶段一盘点计数
6. 探针契约: README 判据完整、失败路径有兜底
7. git diff 审查: 删除行逐条确认（应全为叙事修正/结构修复，核心内容零删除）

**检查点**: 上述 7 项全部留痕（progress 记录扫描命令与结果）。

## 6. 阶段六: 独立复审（直接触发）

**目标**: 结构性问题（重号、错章节、引用缺失）自查难发现——自审收敛后**立即派发独立复审，不询问用户**。

执行:
1. 前置: 自审已按"2 轮审计+修复 → 纯审计轮零问题"收敛
2. 用 task 工具派发独立复审子任务（`subagent_type: security-analysis-evolve` 的 fresh 实例——无本会话上下文，独立视角），派发 prompt 用下方模板（替换 `<改动范围>`）:

```
任务: 复审一次知识蒸馏的产出（你是独立复审者，不带任何既有结论）。

改动范围: <文件清单或 git diff 范围>

审查维度:
1. 章节路由正确性: 重号/错章节/编号单调/收尾节位置——知识库读者是按章节号检索的 LLM，结构错位直接导致路由失败
2. 叙事词残留: 对改动范围内文件跑词边界正则 \bCTF\b|\bwriteups?\b|比赛|赛事|实测|亲测|复盘|验证过
3. 探针/脚本工程质量: 失败路径契约（不挂起）、README 自足性（fresh clone 可跑）
4. 引用路径: $AGENT_DIR/$SHARED_DIR 变量形式且真实存在
5. 技术内容抽查: 抽 3-5 条新写入知识核对内部一致性与代码示例可执行性

输出: findings 按严重度分级（中/低/信息级——文档类复审不产生高级，因无运行时风险），每条含文件:行号与修复建议。没有问题则明确说零问题。
```

3. 收到 findings: 全部修复（不设严重度门槛）→ 修复项逐一回归验证 → progress 记录
4. **修复完成后不再递归复审**（一轮独立复审即收敛，防无限循环）

**检查点**: 复审 findings + 修复记录 + 回归结果进 progress。

---

## 7. 完成报告要素

向用户汇报必须含: 素材总量与方向分布、gap 清单与落位汇总表、验证分级统计（T1/T2/T3/T4/降级 各多少条）、复跑成功清单、降级项及原因、独立复审 findings 数与修复状态、归档位置、遗留事项（prompt 踩线、无法验证项等）。
