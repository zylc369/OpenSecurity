# 隐蔽载体解码

> 触发场景：目标线索仅一个句柄（`@handle`）或一个短语，需要从公开平台内容中定位并提取隐藏编码，再交给密码分析层。覆盖：平台判存指纹 → 内容抓取 → 编码识别 → 多级链流程 → 解码自检。
>
> 密码分析层（Bacon 之后的标准算法）见 `crypto-methodology.md` §1 路由；本文件管"编码在哪、怎么稳定取到、怎么解出参数"。

---

## 1. 触发场景识别

- 目标描述只有一个 `@xxx` 句柄或短语，无文件附件
- `@` 前缀 = 平台账号句柄的通用语义；`主题词.archive` / `.daily` / `.edits` 后缀是 Instagram 存档号亚文化命名，其他平台罕见
- 内容形态描述词（"笔记/短行/caption"）指向社媒帖子的文本
- **推测不等于事实**：句柄语义只是押注依据，必须用 §2 指纹表逐平台验证存在性——哪个平台有这个句柄，哪个就是载体平台；单平台扑空时换平台而不是换解法

## 2. 平台判存指纹表（2026-08 实测）

平台对不存在资源的响应与真实资源有稳定差异，用指纹避免逐个试错：

| 平台 | 探测方法 | 存在 | 不存在 |
|------|---------|------|--------|
| Instagram | `GET /<name>/embed/` 的响应字节数 | ≈620KB | ≈217KB（错误模板） |
| Instagram | 无头浏览器渲染 `/<name>/`（桌面 UA + 禁自动化特征头） | 渲染出 bio/帖子网格 | "Profile isn't available" |
| Instagram 帖子 | Googlebot UA（`Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)`）直抓 `/p/<code>/` | 200 ≈750KB，含 og:description（日期/点赞数/完整 caption）+ 评论文本 | — |
| Instagram 原图 | `GET /p/<code>/media/?size=l` | 302 → 1080px JPEG | 404 |
| Telegram | `GET t.me/<name>` 的 `og:title` | 账号名/频道名 | `Telegram: Contact @xxx` 模板 |
| 自建短链 | `GET <域名>/<slug>`（follow 重定向） | 302 → 真实目标 | 307 → 站内 /404 |
| 通用短链/托管 | og:title + 字节数 | 内容特征 | 软 200 壳页（Linktree/Notion/Sites 等模板，内容仅几十 KB 且标题为泛化词） |

**注意**：Instagram 私有 API（`/api/v1/*`）对无会话请求返回 401/429，不要反复重试；用上表的公开端点已覆盖账号/帖子/图片三类数据。关注列表、Notes 等 app 内数据无公开途径，不要死磕——设计良好的目标不会把关键数据放在登录墙后。

## 3. 文本载体编码识别

对抓到的长文本（caption/简介/评论）按序检查：

### 3.1 首字母双符号收敛 → Bacon 型

**识别信号**：每行首词只落在两个集合（如 "Old/Only" vs "Books/Beneath/Before/Between/Broken/Beyond"）——先枚举全部首词确认恰好收敛为两类，再进入解码。

**解码（bit 串→字符、值 26-31 扩展、行数整除检查）见 `classical-crypto.md` §6**——Bacon 解码的唯一维护点，本文件不保留解码实现。本层职责是稳定产出 bit 串：剔除平台注入行后重数行数（5 整除），集合成员按首词前缀判定（剥离标点）。

### 3.2 单元收敛之外的载体信号

- 非重复行中**完全相同的行出现 ≥2 次**：构造者的强调信号，通常是玩法说明而非数据
- 行内标点/词数/长度的不一致分布：次级编码载体（先用主载体，主载体解通后再查）

### 3.3 元提示（构造者的自证话语）

载体文本中"异常直白"的句子往往是玩法说明书，逐句显式消化再继续：

| 元提示形态 | 含义 |
|-----------|------|
| "字母表不是终点 / beyond Z two marks" | 值 26/27 是 base32 数字（'2'/'3'） |
| "保留分隔符 / a small mark separated" | 解出的数字是断句符，把串拆段 |
| "顺序不保证 / rarely survive in the right order" | **拼接顺序可能错**，立即验证（§4.2） |
| "丢一个字符就失效 / one character is lost" | 解码结果可能缺位，先定序再补位 |
| "重复出现的数字" | 日期/编号重复是参数线索（如同日发布的多条内容） |

## 4. 多级链标准流程

```
句柄 → §2 判存定位平台 → 抓全部内容（bio/帖子/caption/图/日期）
  → §3 编码识别与解码 → 中间串语义断句（分隔符拆段）
  → 段重组为 资源定位符（域名/路径/用户名）→ §2 判存验证
  → 命中资源（存档/加密样本）→ 交密码分析层
```

- 中间串"部分像域名/单词、部分乱码"→ 大概率分段顺序错（§4.2），不要直接拿去探测
- 断句后的段组合若有多种，按"已知真实存在的域名模式"（组织短链域名、drive/存盘路径）优先排序，用 §2 指纹批量判存

### 4.1 抓取注意

- 帖子按时间排序用平台短码序（§4.2），不是页面展示序也不是字典序
- 每条内容的发布日期/编辑标记都要记录（元提示的"重复数字"常指日期）
- 图片做基础检查（文件尾附加数据/EXIF/嵌入压缩包）即可，场景类照片 OCR 命中率低，3 次无产出即止损转向文本载体

### 4.2 排序坑：短码按 base64url 字母表序

多条内容同日发布时，恢复时序必须按短码的 **base64url 字母表序**（`A-Z` < `a-z` < `0-9` < `-` < `_`），**不是 ASCII 字典序**——两套序对 `数字 vs 小写字母` 的结论相反：

```python
B64URL = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_"
def sort_key(shortcode):           # Instagram 帖子码、多数平台短 ID 通用
    return tuple(B64URL.index(c) for c in shortcode)
# 例：'3' 的序是 55，'c' 的序是 28 → 'c' 开头的码更早
# ASCII 字典序则 '3'(0x33) < 'c'(0x63)，结论相反！
codes = ["DbOB3vgTD62", "DbOBcQRTTc-"]
print(sorted(codes, key=sort_key))  # DbOBcQRTTc- 在前（正确时序）
```

## 5. 解码自检三问（方法论纪律，本节为唯一详细版）

解码结果"一部分有意义、一部分无意义"时，**先回答三问再使用结果**：

1. **部分正确是否被外推？** 前段解出有意义词（组织名/单词）只证明该段分组对齐正确，不证明全串正确——无意义段恰好在标记错误起点（常见：从某条内容开始顺序错了）
2. **源文本的元提示消化完了吗？** 显式列出所有元提示（§3.3 表）并逐条回答"这条我处理了吗"——顺序/缺失/分隔/表外字符/重复行各是一类参数信号
3. **参数空间枚举了吗？** 解码参数 = {拼接顺序} × {分组起点} × {符号映射极性} × {字母表变体}。结果用不通时，优先在参数空间内换组合重解，而不是拿可疑结果去外部资源探测

**成本对照**：在错误解码结果上做外部探测，单次假设成本 = 探测请求数 × 平台数；在参数空间内重解，成本 = 本地一次重跑。两者相差几个数量级。

## 6. 失败回退

- 载体平台扑空 → 换平台（§2 全表过一遍），不要在单平台加码
- 解码串无法定位任何资源 → 回 §5 三问，重点验证顺序（§4.2）
- 全部公开途径穷尽 → 输出中间结论（已确认的解码串 + 已排除方向清单）交人工环节（需要登录态的数据由持有账号者补齐），禁止原地循环
