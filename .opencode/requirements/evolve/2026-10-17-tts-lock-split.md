# TTS 合成锁拆分（本地信号量 / 远程独立 / 缓存细粒度）—— 需求文档

> 2026-10-17 | 状态: 待确认 | 前置: 会话讨论确认的并发模型（并发度由资源能力决定, 超出的排队）

## §1 背景与目标

**现状问题**：`TtsService.synthesize` 全程持一把互斥锁（`self._lock`），
本地合成与远程合成**共用同一把锁**：
- 远程请求在"等网络回包"期间仍持锁 → **任何其它 TTS 请求（本地/远程）全部被堵在门外**
  （实例：节点冷启动 34.5s 期间，另开一段本地试听也要等到它结束）
- 预热请求当时**被迫绕锁**（打补丁）——正确做法是"远程域本就不该与本地共锁"

**目标**（按资源分域）：
- 本地推理域：容量 1 队列（GPU 单实例的物理现实）——本地合成 + 远程回退本地都经它
- 远程域：独立（不占本地队列; 节点侧自排队）——transport 并发安全已验证
- 缓存：细粒度锁（仅包字典读写）
- **行为兼容**：同输入同输出; 对外接口不变; 串行不变量（对话不交错）保持

## §2 技术方案

### §2.1 结构（`services/tts_service.py`）

```
新增:
  _cache_lock: threading.Lock        # 只包缓存 get/set/清理（微秒级临界区）
  _local_sem:  threading.Semaphore(1)  # 本地推理域（容量 1 队列; 语义=排队取号）
  TtsQC._check_lock: threading.Lock    # scripts/tts_qc.py——check 全程持
    （funasr/Paraformer 单实例访问的串行不变量; 拆锁前由合成大锁"顺带"保证,
      拆锁后必须显式——否则并发 check 引入 ASR 模型竞态）
移除:
  _lock 的大包大揽（原"全程持锁"）
```

### §2.2 `synthesize` 重构（伪代码）

```
查缓存（_cache_lock）→ 命中直接返回
use_remote?
  ├─ True: 试远程（无主锁——transport 层并发安全, 节点侧自排队）
  │         ├─ 成功且质检过 → 写缓存（_cache_lock）→ 返回
  │         └─ 失败/质检不过 → note_request_failure → 落本地
  └─ False → 落本地
本地（本地路径与 fallback 统一入口）:
  with _local_sem:            # 排队取号; 同一时刻只有一人在与 worker 对话
      wav = _synth_qc_local(...)
  写缓存（_cache_lock）→ 返回
```

### §2.3 不变量保持清单

| 不变量 | 由什么保证 | 说明 |
|---|---|---|
| 与 worker 对话不交错 | `_local_sem(1)` | 同一时刻仅一个请求持有本地名额 |
| 质检（funasr）并发 | `TtsQC._check_lock` | 拆锁前由大锁顺带串行; 拆锁后显式补——模型访问层串行同哲学 |
| 缓存一致性 | `_cache_lock` | 所有读写/超限清理都走它 |
| fallback 风暴背压 | `_local_sem(1)` | 多个远程同时失败 → 本地自然排队 |
| 失败计数线程安全 | `RemoteLinkService` 内部锁 | 已核（note_request_failure 自持锁） |
| 远程并发安全 | transport 既有设施 | 已核（msg_id 映射/session 锁/线程安全提交） |

### §2.4 边界与取舍

- **不做**远程主动限流（节点侧自排队）——若未来节点压力大再引入可配置远程信号量（YAGNI）
- **不改**缓存键与质检流程; **不改**远程/本地的语义选择（should_use_remote）
- 日志口径：原"获得合成锁（含排队）"改为"本地队列等待 Xms"（远程路径无此等待）
